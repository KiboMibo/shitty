# Диагноз: TUI-приложение «не запускается» в панели после сплита

Разведка, только чтение. Продуктовый код не тронут, коммитов нет. Все числа
ниже сняты на `master` (`6628ba59`), бинарь `.build/st` (Metal, macOS 25.5),
`.build/st_test` пересобран под текущее дерево.

---

## 1. Наблюдаемое поведение

**Формулировка пользователя неточна: TUI запускается и работает.** Перестаёт
работать окно.

Что происходит на самом деле, подтверждено прогоном:

1. `cmd+d` делит вкладку. Новая панель создаётся корректно: форкается настоящий
   потомок, у него правильный `winsize` и правильное окружение.
2. Пользователь запускает TUI. Процесс стартует, живёт, рисует в свой pty.
3. **В момент, когда TUI переключается на альтернативный экран (`\e[?1049h`),
   рендерер начинает отвергать каждый кадр. Окно перестаёт обновляться —
   целиком, обе панели.** Картинка застывает на том, что было до запуска TUI.
4. Приложение уходит в бесконечный цикл «отвергнутый кадр → `requestFrame()` →
   отвергнутый кадр», ограниченный только vsync: ~1.5–2 % CPU вместо 0 %.
5. Состояние **не транзиентное**: само по себе оно не рассасывается. Снимается
   только событием, которое повреждает *все* строки *всех* панелей — ресайз
   окна, смена шрифта, либо полноэкранный вывод в соседнюю панель.

Измерения (см. §5):

| Состояние | %CPU | CPU time за 8 с |
|---|---|---|
| одна панель, TUI на альт-экране | 0.0 | +0.00 с |
| две панели, обе на основном экране | 0.0 | +0.00 с |
| **две панели, TUI на альт-экране в любой из них** | **1.5–2.1** | **+0.13 с** |
| после полного повреждения соседней панели | 0.0 | +0.00 с |

Проверено настоящим `vim -u NONE`: процесс `/usr/bin/vim -u NONE` жив во второй
панели, окно при этом стоит и жжёт CPU.

**Важная поправка к постановке задачи.** Дефект **не** специфичен для новой
панели. После сплита он одинаково воспроизводится при запуске TUI в *исходной*
панели (§5, прогон Б). «В исходной панели всё работает» — это про состояние
*до* сплита, когда панель одна.

## 2. Гипотезы

### Г1. Начальный `winsize` слейв-pty равен 0×0 — TUI отваливается на `TIOCGWINSZ`

*За:* `PtyImpl::spawn()` (`lib/shitty/pty.cpp:875`) действительно нигде не
выставляет winsize до `fork()`; `posix_openpt` + `open(slave)` дают 0×0, а
`handle->resize()` вызывается уже в родителе, после `fork`
(`lib/shitty/session.cpp:451-452`) — гонка с `execvp` формально есть.

*Против:* по этому же пути идёт и первая панель. Кроме того, между `spawn` и
вводом пользователем команды TUI проходят секунды, а шелл перечитывает размер
на каждом приглашении.

*Чем проверял:* запуск `.build/st -panes -e probe.sh`, где `probe.sh` пишет
`stty size`, `tty`, `TERM` в лог; сплит вызван через lldb (§5).

*Результат:* панель 1 — `24 80`, панель 2 — `53 34` (окно 70×53, вертикальный
сплит пополам: 34 ≈ 70/2). `TERM=xterm-256color`, `TERM_FEATURES` на месте,
`pgrp == tpgid` (потомок — передний план своего tty).

**Вердикт: отвергнута.** Латентная гонка в `spawn()` реальна и её стоит закрыть
отдельно (§8), но к этому дефекту отношения не имеет.

### Г2. Ввод не маршрутизируется в новую панель

*За:* `refocus()`/`focusedTerminal_` — нетривиальный код.

*Против:* `SessionSetImpl::key()` (`session.cpp:1265`) безусловно уходит в
`activeTerminal()`, который есть `focusedTerminal_`; `splitFocused()` зовёт
`refocus()` перед возвратом. Юнит-тест
`SessionSet::TheSplitChordsDivideAndBothPanesTakeInputOfTheirOwn` это пинит.

*Чем проверял:* чтение кода + юнит-тесты уже в наборе.

**Вердикт: отвергнута.**

### Г3. Потомок второй панели не форкается / падает сразу

*За:* `fork()` во второй раз происходит уже в многопоточном процессе (drain-поток
поднимается в `PtyImpl::engage()` после первого `spawn`), — асимметрия
«первая панель / все следующие» существует.

*Против:* между `fork` и `execvp` потомок зовёт только async-signal-safe вызовы.

*Чем проверял:* `pgrep -P <app>` после сплита.

*Результат:* `/bin/sh -i` (позже `/usr/bin/vim -u NONE`) живёт своим pid'ом,
логи из потомка пишутся.

**Вердикт: отвергнута.**

### Г4. Рендерер не выводит непервую панель

*За:* `render_metal.mm` держит удержанные ячейки по панелям, `A6-4`.

*Против:* сразу после сплита обе панели видны и рисуются.

**Вердикт: отвергнута в исходной формулировке**, но привела к Г5.

### Г5. Смена экрана (pri↔alt) меняет «форму» кадра, и рендерер требует полных строк ото ВСЕХ панелей, включая молчащую

*За:* `update.shapes` — это указатель на `Screen`; альт-экран — **другой**
объект `Screen`; молчащая панель отдаёт `retainedOutput()` с `damagedRows = 0`.

*Чем проверял:* чтение кода + три прогона на живом приложении с замером CPU и
`sample`, плюс проверка «расклинивания» (§5).

**Вердикт: подтверждена. Это корневая причина.**

## 3. Корневая причина

Четыре факта, которые вместе дают дефект:

**(1) Альт-экран меняет идентичность `Screen`.**
`lib/shitty/vterm.cpp:3704` и `:3739` — `cf = frame_alt`; `:3756` — `cf =
frame_pri`. `VtermImpl::output()` кладёт `terminalUpdate.shapes = frame`, то
есть текущий `cf` (`vterm.cpp:2743`). Значит `\e[?1049h` и `\e[?1049l` меняют
`update.shapes` — первое, что делает любой TUI.

**(2) Молчащая панель отдаёт ноль строк.**
`ApplicationImpl::presentTerminal()` берёт у панели, которой нечего сказать,
`retainedOutput()` (`application.cpp:574`). `VtermImpl::retainedOutput()`
(`vterm.cpp:2748`) явно ставит `quiet.damagedRows = 0` (`:2757`), а
`fillTerminalUpdate()` кладёт `update.rowCount = frame.damagedRows`
(`vterm.cpp:2500`). Итог: `rowCount == 0`, `gridRows == rows_ > 0`.

**(3) Рендерер отвергает весь кадр, если хоть одна панель не отдала все строки.**

`lib/shitty/render_metal.mm:1089-1120`:

```cpp
bool shapeChanged = panes.length() != count;
for (size_t pane = 0; pane < count; ++pane) {
    ...
    shapeChanged = previous.shapes != update.shapes || previous.columns != ... ;
}
if (shapeChanged) {
    for (size_t pane = 0; pane < count; ++pane) {
        const TerminalUpdate& update = frame[pane].update;
        if (update.rowCount != update.gridRows) {
            return false;               // <-- render_metal.mm:1113
        }
        ...
    }
}
```

Дословно то же самое в `lib/shitty/render_reference.cpp:832` и `:842`.

`shapeChanged` смешивает два разных вопроса: «переехала ли раскладка ячеек»
(число панелей, `gridColumns`/`gridRows`, `cellOffset`, длина `cells`) и
«сменилась ли идентичность экрана одной панели» (`shapes`). Второе не двигает ни
одного смещения в `cells`, но требование выставляется на **все** панели кадра.

**(4) Отказ рендерера — вечный цикл, а не восстановление.**
`lib/shitty/application.cpp:601-604`:

```cpp
if (!composer.renderer->update(frameUpdates.data(), frameUpdates.length())) {
    composer.window->requestFrame();
    return false;
}
```

`consume()` при этом не зовётся, поэтому терминал не теряет свой pending-вывод и
на следующем кадре отдаёт ровно то же; молчащая соседка отдаёт ровно те же ноль
строк; `panes` в рендерере не обновляется (`panes.clear()` — уже после
проверок), поэтому `previous.shapes` навсегда остаётся старым экраном.
Инвариант замкнулся сам на себя.

Эта петля в кодовой базе уже описана — в `render_vk.cpp:2252-2281`, там, где
Vulkan-бэкенд сознательно **не** отвечает `false` на многопанельный кадр:
«Refusing quietly is the one answer that *is* a lie. The caller answers a false
with `requestFrame()` and does not consume the terminal output, so the same
frame comes back: an unlit window asking for another one for as long as the
split lives, with nothing in the log to say why». Metal и reference попадают
ровно в неё через `shapeChanged`.

**Файлы и строки корневой причины:**

| Файл:строка | Роль |
|---|---|
| `lib/shitty/render_metal.mm:1113` | отказ кадра из-за чужой панели (продуктовый путь macOS) |
| `lib/shitty/render_reference.cpp:842` | то же в эталонном рендерере |
| `lib/shitty/application.cpp:601-604` | отказ превращается в бесконечный `requestFrame()` |
| `lib/shitty/vterm.cpp:2757` | `retainedOutput()` обнуляет `damagedRows` |
| `lib/shitty/vterm.cpp:3704,3739,3756` | `cf` меняется на альт-экране — источник смены `shapes` |

## 4. Почему первая панель работает, а новая — нет

Это не свойство «новой» панели. Это свойство **числа панелей**.

**Одна панель.** `count == 1`. Единственная панель кадра — та самая, что
переключилась на альт-экран, и она полностью повреждена (свежий экран). Значит
`rowCount == gridRows`, проверка проходит, кадр садится. Никакой молчащей
соседки в кадре нет — некому отдать ноль строк. Именно поэтому «до сплита всё
работает».

**Две панели.** В кадре есть панель, которая ничего не сказала: она сидит на
приглашении шелла и её `output()` возвращает `nullptr`. Приложение берёт у неё
`retainedOutput()` — и это ноль строк по построению. Пока хоть одна панель в
кадре молчит, любая смена `shapes` у любой другой панели отвергает весь кадр.

**Почему сам сплит при этом виден.** В момент `cmd+d` `shapeChanged` тоже
истинно (`panes.length() != count`), но `splitFocused()` зовёт
`applyLayout(tree)` (`session.cpp:744`), который прогоняет `paneResized()` по
**всем** панелям вкладки (`session.cpp:854`) — а ресайз повреждает все строки.
Новая панель повреждена целиком по рождению. Поэтому в этом одном кадре все
панели отдают полные строки, и он садится. Это ровно то, что чинил коммит
`98a08f42` («перестроенная вкладка должна кадру все строки всех панелей») —
для перестройки набора панелей, но не для смены `shapes` внутри панели.

**Симметричность.** Экспериментально подтверждено (§5, прогон Б): TUI, запущенный
после сплита в **исходной** панели, вешает окно точно так же. Пользователь
просто пробовал новую — она получает фокус сразу после `cmd+d`.

**Выход из альт-экрана — то же самое.** `\e[?1049l` тоже меняет `cf`, поэтому
даже TUI, который каким-то образом отрисовался, повесит окно при выходе
(подтверждено, §5, прогон Б, шаг 4).

## 5. Воспроизведение

Тестовый режим (`st_test`) для этого непригоден: после сплита он умирает —
см. §8, находка Т1. Поэтому воспроизведение — на настоящем бинаре, а сплит
инициируется вызовом `SessionSetImpl::splitFocused()` через lldb (клавиатурный
`cmd+d` из скрипта недоступен: у `osascript` нет Accessibility).

### Минимальный сценарий (то, что я гонял)

`probe.sh` — то, что запускается в каждой панели:

```sh
#!/bin/sh
D=/tmp/panes-probe
mkdir -p $D/reg; touch $D/reg/$$
n=$(ls $D/reg | wc -l | tr -d ' ')
echo "pane $n pid=$$ tty=$(tty) size=$(stty size) TERM=$TERM" >> $D/log
while [ ! -f $D/go$n ]; do sleep 0.2; done
# минимальный «TUI»: только переход на альтернативный экран
printf '\033[?1049h\033[H\033[2JHELLO FROM PANE %s\r\n' "$n"
sleep 3600
```

```sh
mkdir -p /tmp/panes-probe; rm -rf /tmp/panes-probe/*
./.build/st -panes -e /path/probe.sh &   # APP=$!

# --- контроль: одна панель ---
touch /tmp/panes-probe/go1
ps -o %cpu,time -p $APP          # 0.0, время стоит  -> кадр сел

# --- сплит ---
SLIDE=$(lldb -p $APP -b -o "image list -o -f" | grep '\.build/cas' | awk '{print $2}')
# this: брейкпоинт на SessionSetImpl::visiblePanes (nm: 0x1000838dc + SLIDE),
#       разбудить кадр записью в /dev/ttysNN, прочитать x0
# сплит: expr ((unsigned char(*)(void*,unsigned char))(0x100083a60+SLIDE))(this, 0)

# --- дефект ---
touch /tmp/panes-probe/go2
ps -o %cpu,time -p $APP          # 1.5-2.0 %, время растёт -> кадры отвергаются вечно

# --- расклинивание (доказательство механизма) ---
printf '\033[2J\033[H' > /dev/ttys<панель-1>
for i in $(seq 1 60); do printf 'line %s\r\n' "$i"; done > /dev/ttys<панель-1>
ps -o %cpu,time -p $APP          # снова 0.0, время стоит
```

### Сценарий, который должен стать падающим тестом

Питоновский `tst/*.py` сегодня написать нельзя (§8, Т1). Правильное место —
`session_ut.cpp`/`render_reference_ut.cpp` через эталонный рендерер:


## 6. Предлагаемое исправление

### Вариант 1 (рекомендую как принципиальный) — расщепить `shapeChanged`

`shapeChanged` сегодня отвечает сразу на два вопроса. Их надо развести:

* **раскладка ячеек переехала** — изменилось `count`, чей-то
  `gridColumns`/`gridRows`, чей-то `cellOffset`, либо длина `cells`. Тогда
  смещения всех панелей в общем векторе недействительны, и требование «все
  строки ото всех панелей» верно как есть;
* **сменилась идентичность экрана одной панели** — `previous.shapes !=
  update.shapes` при неизменных размерах и смещении. Ни один байт `cells` не
  переезжает; недействительны только удержанные ячейки и полосы (strips) *этой*
  панели. Полные строки надо требовать **только с неё**.

Набросок для `render_metal.mm` (в `render_reference.cpp` — зеркально):

```cpp
    // раскладка: то, что двигает смещения в общем векторе ячеек
    bool layoutChanged = panes.length() != count || cells.length() != cellCount;
    for (size_t pane = 0; pane < count && !layoutChanged; ++pane) {
        const PaneRender& previous = panes[pane];
        const TerminalUpdate& update = frame[pane].update;
        layoutChanged = previous.columns != update.gridColumns
                     || previous.rows != update.gridRows
                     || previous.cellOffset != offsetOf(pane);
    }
    for (size_t pane = 0; pane < count; ++pane) {
        const TerminalUpdate& update = frame[pane].update;
        // панель «протухла», если переехала раскладка кадра или сменился
        // её собственный Screen: и то и другое обесценивает её удержанное
        const bool stale = layoutChanged
                        || panes.length() != count
                        || panes[pane].shapes != update.shapes;
        if (!stale) {
            continue;
        }
        if (update.rowCount != update.gridRows) {
            return false;
        }
        for (size_t index = 0; index < update.rowCount; ++index) {
            if (update.rows[index].cells == nullptr || update.rows[index].row != index) {
                return false;
            }
        }
    }
    if (layoutChanged) {
        cells.clear();
        cells.zero(cellCount);
    }
```

Что проверить исполнителю: `assignStrips()`/`PaneArenaMirror` должны выдать
свежее поколение для панели, у которой сменился `shapes`, без общего
`cells.zero()`. Если поколение сегодня завязано на общий сброс — это надо
починить явно, иначе панель на альт-экране получит чужие полосы.

**Риски:** трогается горячий путь обоих рендереров и логика удержания
(`A2`/`A3`/`A6-4`); «неполный кадр после смены экрана» — ровно тот класс, где
ошибка не даёт ни падения, ни артефакта в тесте, только чужие пиксели.
Обязательна проверка паритета Metal ↔ reference.

### Вариант 2 (минимальная кровь, лечит и второй путь) — сделать повтор осмысленным

Сейчас на отказ `application.cpp:601-604` просит новый кадр, ничего не изменив,
— повтор гарантированно даёт тот же отказ. Достаточно перед `requestFrame()`
полностью повредить все видимые панели, и повторный кадр удовлетворит проверку
без каких-либо правок в рендерерах:

```cpp
    if (!composer.renderer->update(frameUpdates.data(), frameUpdates.length())) {
        // Отказ рендерера означает «твой кадр неполон», и повтор без
        // изменений — тот же отказ. Единственный ответ, который может
        // сделать следующий кадр другим, — отдать всё целиком.
        for (const SessionPane& pane : framePanes) {
            pane.terminal->exposeAll();   // новый метод интерфейса Vterm
        }
        composer.window->requestFrame();
        return false;
    }
```

`Vterm::expose()` для этого **не годится**: `VtermImpl::expose()`
(`vterm.cpp:2338`) — это только `redraw()`, то есть `outputPending = true`, без
повреждения строк. Нужен публичный метод поверх уже существующего приватного
`VtermImpl::exposeFrames()` (`vterm.cpp:3144`), который зовёт
`frame_pri->expose()` и `frame_alt->expose()`.

*Плюс:* тем же движением чинится второй экземпляр той же ошибки —
`ApplicationImpl::frame()` (`application.cpp:663-667`) после пересоздания
рендерера зовёт `expose()` только у **активного** терминала, а у свежего
рендерера `panes` пуст, то есть `shapeChanged` истинно и полные строки нужны ото
всех. На окне с двумя панелями потеря поверхности сегодня, по чтению кода,
приводит к тому же вечному отказу (отдельно не проверял — нужен способ уронить
поверхность).

*Минус:* один потерянный кадр и полная перерисовка всех панелей на каждом
переключении экрана. Для 2–4 панелей это шум, но это регресс по объёму работы на
кадр, и его стоит померить тем же прибором, что и волна 8 (`biasStrips()`).

*Риск:* маскирует отказы, которые полным экспозом не лечатся (например
`gridColumns == 0`) — они останутся вечным циклом, как и сейчас. Стоит добавить
счётчик подряд идущих отказов и диагностику в stderr после N подряд, чтобы
следующий такой дефект был виден в логе, а не в проценте CPU.

**Рекомендация:** вариант 2 сейчас (корректность, малый радиус, чинит два пути),
вариант 1 следом, если замер покажет, что лишний полный кадр заметен.

## 7. Что нужно покрыть тестом

Ключевое: **ни один тест сегодня не собирает кадр из двух панелей, где одна
молчит.** Всё, что есть, — юнит-тесты раскладки и ввода с фальшивым pty.

1. **Кадр садится при смене экрана у одной панели из двух** (эталонный
   рендерер). Сценарий из §5: панель A уходит в `\e[?1049h`, панель B молчит,
   `update(panes, 2)` должен вернуть `true`, а в модели — альт-экран у A и
   удержанное содержимое у B. Зеркальный тест на `\e[?1049l`.
2. **То же для любой другой смены `shapes`**, не связанной с альт-экраном
   (смена размера шрифта у одной панели, если такое достижимо), — чтобы фикс
   был про механизм, а не про 1049.
3. **Отказ рендерера не должен быть вечным.** Оракул на «после смены формы
   в N-панельном окне кадр садится не позже второго вызова `presentTerminal()`».
   Именно этого оракула не хватало: сегодня отказ ничем не наблюдается.
4. **Паритет Metal ↔ reference** на многопанельном кадре со сменой экрана
   (`test_gpu_parity.py` сегодня однопанельный).
5. **Пересоздание рендерера при двух панелях** (§6, вариант 2, «второй путь»):
   после сброса `composer.renderer` кадр должен сесть.
6. **Настоящий потомок во второй панели.** `winsize` и `TERM` у панели,
   рождённой сплитом, — сегодня это проверено только руками (мною: `53 34`,
   `xterm-256color`). Нужен тест на настоящем pty, как в `pty_ut.cpp`.
7. **Начальный `winsize` до `exec`** (Г1, латентно): `pty_test_helper` в режиме,
   который печатает `TIOCGWINSZ` сразу после старта, без ожидания SIGWINCH.
   Сегодня `ResizeReachesChildAsWinch` печатает `ready` **до** ресайза, то есть
   начальный размер не наблюдается вообще.
8. **Разблокировать панели в тестовом режиме** — предпосылка для 1–5 на уровне
   `tst/*.py`. См. §8, Т1.

## 8. Обнаружено (побочно)

**Т1. Тестовый режим ломается на первом же сплите — панели непокрываемы.**
`lib/shitty/test_mode.cpp:2333` для *каждой* команды вычисляет
`SessionKit& activeKit = kitFor(sessions->activeTerminal());`, а `kitFor`
(`:2162`) при отсутствии кита делает `raiseError`. Киты заводятся только по
`composer.newTabListeners` (`:2229`), а `splitFocused()` этот список не
публикует. Итог: после `cmd+d` любая следующая команда убивает процесс.
Проверено:

```
FRONTEND_KEY_EVENT 'D' modifiers=8  ->  сплит происходит
следующая команда              ->  RuntimeError: no harness kit for this session
                                    процесс завершился
```

Нужны: регистрация кита для панели, рождённой сплитом, адресация панелей
(`WINSIZE_PANE i`, `SCREEN_TEXT_PANE i`) и команда `SPLIT V|H` (сегодня чорд
приходится слать через `FRONTEND_KEY_EVENT`, что работает, но лечит только
половину). Без этого §7.1–7.5 в `tst/` не написать.

**Т2. Начальный `winsize` слейва не выставляется вообще.**
`PtyImpl::spawn()` (`pty.cpp:875-921`) форкает с pty 0×0 и полагается на
`handle->resize()` **после** `fork` (`session.cpp:452`). Потомок, который читает
`TIOCGWINSZ` сразу после `exec` (`st -e vim`, `st -e htop`), может увидеть 0×0.
Лечится передачей `winsize` в `openpty()`/`TIOCSWINSZ` на слейве до `fork`, то
есть протаскиванием `PtySize` в `spawn()`. На текущий дефект не влияет, но это
готовая мина под `-e`.

**Т3. `-dump` при нескольких сессиях затирает сам себя.**
`Vterm::create()` (`vterm.cpp:9928-9938`) на каждый терминал открывает
`composer.opts->dump` с `O_TRUNC` и своим дескриптором. Две панели (или две
вкладки) пишут в один файл с двух независимых позиций.

**Т4. `splitFocused()` молча берёт нулевой прямоугольник.**
`session.cpp:731-736`: `PixelRect area;` инициализируется по умолчанию, и если
раскладка не вернула только что посаженную панель, `openSession()` получит
`0×0`-геометрию вместо диагностики. Сегодня недостижимо, но это тихий отказ.

**Т5. Vulkan-бэкенд панели не рисует вовсе.**
`render_vk.cpp:2252` при `count > 1` делает `raiseError` — сплиты на Wayland
роняют приложение с сообщением. Это осознанное решение, задокументированное на
месте; упоминаю, чтобы не искали второй раз.

**Т6. `Vterm::expose()` не то, чем кажется.** `vterm.cpp:2338` — это только
`redraw()` (взвести `outputPending`), без повреждения строк. Единственный
вызов из продукта (`application.cpp:666`, после пересоздания рендерера) на
основании имени ожидает «отдай всё», а получает «скажи, что тебе есть что
сказать». См. §6, вариант 2.
