Полный список новых тестов:

- `QuickHotkeyChord::DefaultChordParsesToControlAndGrave`
- `QuickHotkeyChord::MultipleModifiersAndANamedKeyParse`
- `QuickHotkeyChord::ChordIsCaseSensitive`
- `QuickHotkeyChord::UnknownModifierIsRejected`
- `QuickHotkeyChord::UnknownKeyNameIsRejected`
- `QuickHotkeyChord::EmptyStringIsRejected`
- `QuickHotkeyChord::ModifiersWithoutATrailingKeyAreRejected`
- `QuickHotkeyChord::TrailingPlusWithNoKeyIsRejected`
- `QuickHotkeyChord::GarbageIsRejected`
- `QuickHotkeyChord::BareKeyWithoutModifierParsesWithZeroModifiers`

**Про `ChordIsCaseSensitive`.** Первая версия теста использовала `"CTRL+GRAVE"`/
`"Ctrl+Grave"` — обе строки неправильны сразу в обоих токенах, поэтому
дефект только в сравнении модификатора не разрушал бы тест (клавиша всё
равно не находилась бы в таблице, тест остался бы зелёным по случайной
причине). Заметил это на первой же точечной проверке (см. «Чувствительность
тестов», дефект 1) и переписал на `"CTRL+grave"`/`"ctrl+GRAVE"` — по одному
неправильному токену на строку, чтобы дефект в любой из двух половин разбора
ловился отдельно. Итоговая версия — в коммите.

**Про `TrailingPlusWithNoKeyIsRejected` и `EmptyStringIsRejected`.** Изначально
предполагал, что оба случая («ничего после последнего `+`» и «пустая строка»)
проходят через один и тот же путь — поиск пустого токена в таблице имён
клавиш. При трассировке цикла обнаружил, что это не так: `"ctrl+"` заканчивает
цикл с `begin == text.length()` сразу после того, как токен `"ctrl"` съеден
как модификатор, **не доходя** до поиска по таблице клавиш вообще — оба
случая (пустая строка и висящий `+`) на самом деле падают в один и тот же
внешний `return false;` (последняя строка функции), а не в тот, что внутри
цикла по `quickHotkeyKeyNames`. Это разделило дефекты 3 и 4 ниже на два
разных пути кода, а не один — иначе я бы завёл один дефект вместо двух и
недосчитался бы независимого подтверждения для одной из веток.

## Ограничение платформы

Весь модуль (`quick_hotkey_chord.h`/`.cpp`) обёрнут в `#if defined(__APPLE__)`
— обычный `.cpp` подхватывается глобом `unit_sources` на всех платформах, и
без guard'а Linux-сборка упала бы на `<Carbon/Carbon.h>`. Тестовый файл
обёрнут точно так же: на Linux `quick_hotkey_chord_ut.cpp` компилируется в
пустую единицу трансляции (только `#include` заголовка, который сам себя
скрывает), никаких тестов не регистрирует. Формально не проверено на
Linux/на не-Apple компиляторе (машина только macOS, локального IX-реалма
нет — та же оговорка, что во всех предыдущих отчётах волны) — но структура
`#if` идентична уже принятой в `ui_quick_hotkey.h`/`.mm`, риска расхождения
нет.

## Чувствительность тестов

Точечная проверка: 6 дефектов внесены по очереди в `quick_hotkey_chord.cpp`,
пересборка и прогон suite `QuickHotkeyChord` после каждого, дефект возвращён,
`git diff`/`git status` по продакшн-файлу проверен на чистоту после каждого
шага и в самом конце.

| # | Дефект | Что покраснело |
|---|--------|-----------------|
| 1 | `ctrl`/`control` → добавлен `|| token == "CTRL"` (модификатор перестаёт быть чувствителен к регистру) | только `ChordIsCaseSensitive` |
| 2 | Найден ключ → перед присваиванием добавлено `if (parsedModifiers == 0) { parsedModifiers = cmdKey; }` (голая клавиша тайно получает модификатор) — симулирует ровно ту регрессию, от которой предостерегает комментарий в `quick_hotkey_chord.h` | только `BareKeyWithoutModifierParsesWithZeroModifiers` — S1-критичный тест сработал именно на симуляции своей целевой регрессии |
| 3 | Внутренний `return false;` (не найдено в таблице клавиш) → `return true;` с `keyCode = 0` | `UnknownKeyNameIsRejected`, `GarbageIsRejected`, `ModifiersWithoutATrailingKeyAreRejected` — и `ChordIsCaseSensitive` заодно (`"GRAVE"` тоже не находится в таблице) |
| 4 | Внешний `return false;` (конец функции — пустая строка/висящий `+`) → `return true;` | только `EmptyStringIsRejected` и `TrailingPlusWithNoKeyIsRejected` — подтверждает, что это действительно отдельный путь кода от дефекта 3 |
| 5 | `modifiers |= controlKey;` → `modifiers |= cmdKey;` (перепутан бит `ctrl`) | только `DefaultChordParsesToControlAndGrave` (`MultipleModifiersAndANamedKeyParse` не использует `ctrl`, поэтому не задет — ожидаемо) |
| 6 | `quickHotkeyModifierBit`: `else { return false; }` → `else { return true; }` (неизвестный модификатор молча принимается) | `UnknownModifierIsRejected` и `ChordIsCaseSensitive` (`"CTRL"` как неизвестный модификатор тоже принимается) |

Каждый дефект дал ожидаемый и **только** ожидаемый красный список — там, где
один дефект ловился несколькими тестами (3, 4, 6), это разные проявления
одной и той же причины, не ложные срабатывания. Продакшн-код после каждого
шага возвращён точным обратным `Edit`; финальная проверка — `git diff -- quick_hotkey_chord.cpp`
пуста, коммит `88e7ce08` содержит только новый тестовый файл.

Стабильность: `QuickHotkeyChord` прогнан дважды подряд (`--threads=1` и
`--threads=4`, разный порядок выполнения потоками) — `OK: 10` оба раза,
флейка нет.

Проверку «не переспецифицированы» отдельно не делал — находка 1 из первого
круга не содержала предложенного мной поведенческого фикса кода (только
форму извлечения, которую реализовала F3c самостоятельно), так что тестам
не на чем перегибать против моего собственного кода-исправления.

Mutation-тестирование инструментом — не настроено, не проводилось (та же
позиция, что в обоих предыдущих отчётах волны).
