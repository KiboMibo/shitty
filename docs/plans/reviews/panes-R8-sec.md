## Резюме

Волна 8 разводит ввод между несколькими терминалами в одном окне. Клавиатурная половина этой развязки сделана правильно и по конструкции: единственный ответ на вопрос «куда идёт нажатие» — `focusedTerminal_`, и он переставляется до того, как нажатие уходит в терминал. Окна, в которое можно было бы напечатать пароль «мимо», я не нашёл — но нашёл другое: **на пути закрытия панели уборщик освобождает арену умирающей панели прямо внутри `retire()`, а вызывающий код через две строки дёргает виртуальный метод по тому же указателю.** Это чтение и вызов по освобождённой памяти, и запускает его в том числе программа внутри панели — просто завершившись.

Остальные находки — про то, что при нескольких панелях один и тот же ресурс окна (буфер обмена, drag-and-drop, захват указателя) остался «одним на окно» и не спрашивает, какая панель его просит.

**Вердикт: выкатывать нельзя до устранения S1.** S1 чинится в одном файле и подтверждён обратной пробой; остальное — не блокирует.

## Находки

### S1. Use-after-free при закрытии панели: арена освобождается внутри `retire()`, а `refocus()` зовёт по ней виртуальный метод

- **Серьёзность:** блокирующая
- **Класс:** обращение к освобождённой памяти (CWE-416)
- **Где** (база `e74011b8`):
  - `lib/shitty/session.cpp:467-491` — `SessionSetImpl::retire()`, строка 489 `reaper_->wake()`
  - `lib/shitty/session.cpp:545-565` — `SessionSetImpl::closePane()`
  - `lib/shitty/session.cpp:620-643` — `SessionSetImpl::refocus()`, строки 633-634 — сам разыменованный указатель
  - `lib/shitty/session.cpp:891-933` — `runReaper()`, `reapReady()`, `canReap()`
  - `ext/plt/fiber.cpp:226-233` и `274-289` — `FiberImpl::wake()` и `SchedulerImpl::resume()`: почему `wake()` — это не «пометить готовым», а немедленное переключение
- **Кто может:** локальный пользователь окна — закрыв панель по `cmd+w`; и **программа внутри панели** — просто завершившись: выход дочернего процесса приходит через `ptyEof()` → `closeEndedSessions()` (`session.cpp:944-967`) в тот же `closePane()`.
- **Путь:**
  1. `closePane(pane)` (`session.cpp:545`) вызывает `retire(pane)`.
  2. `retire()` кладёт арену панели в могилу и на строке 489 будит уборщика: `reaper_->wake()`.
  3. `wake()` у запаркованного файбера — **синхронное переключение**, а не постановка в очередь: `FiberImpl::wake()` (`ext/plt/fiber.cpp:226`) при `data->parked` зовёт `scheduler.resume(*this)`, а `resume()` (`ext/plt/fiber.cpp:274`) делает `host->switchTo(...)` прямо на стеке вызывающего. Уборщик исполняется **внутри** `retire()`.
  4. `runReaper()` просыпается после `park()`, видит `graveCount_ != 0` и `count_ != 0` и идёт в `reapReady()` → `canReap()`. `canReap()` (`session.cpp:924`) отказывает только когда `composer.renderer != nullptr && focusedTerminal_->presentationChanged()`; в остальных случаях — `delete grave.arena`, то есть `~VtermImpl` и освобождение памяти под терминалом умирающей панели.
  5. Управление возвращается в `closePane()`. `focusedTerminal_` всё ещё **имя только что освобождённого терминала** — между `retire()` и `refocus()` его никто не трогает.
  6. `refocus()` (`session.cpp:633-634`): `if (focusedTerminal_ != nullptr && focusedTerminal_ != terminal) focusedTerminal_->focus(false);` — виртуальный вызов по освобождённой памяти.
- **Чем грозит:** в лучшем случае — падение окна на `cmd+w` или на `exit` в панели (это уже потеря всех остальных сессий окна). В худшем — виртуальный вызов по объекту, чей vtable-указатель к тому моменту перезаписан следующей аллокацией того же аллокатора; чем именно он перезаписан, решает поток данных из pty, то есть частично та самая программа, которая закрытие и вызвала. Обычный прогон этого не показывает: пул отдаёт память `free()`, содержимое остаётся читаемым, vtable цел — и вызов «работает».
- **Чем подтверждено (воспроизведение, база `e74011b8`, дерево `/tmp/r8sec`):**
  1. Обычный прогон чистый: `SHITTY_PTY_TEST_HELPER=$PWD/.build/pty_test_helper .build/unit_tests --threads=1` → `OK: 892`, код выхода 0. (В задаче названо 888 на этой же голове; у меня на `e74011b8` набор насчитывает 892 теста. Расхождение в четыре теста я не разбирал — на выводы оно не влияет, но числа сверять стоит по своему дереву, а не по этому отчёту.)
  2. Тот же бинарь под заливкой освобождённой памяти падает:
     ```
     MallocScribble=1 MallocPreScribble=1 SHITTY_PTY_TEST_HELPER=$PWD/.build/pty_test_helper \
         .build/unit_tests --threads=1
     # код выхода 139 (SIGSEGV), обрыв в наборе SessionSet
     ```
  3. Я прогнал **каждый** из 46 тестов набора `SessionSet` по отдельности под заливкой. Падают ровно четыре, и все четыре — про закрытие **панели**, а не вкладки:

     | тест | код выхода под `MallocScribble` |
     |---|---|
     | `SessionSet::AShellThatExitsTakesItsPaneAndLeavesTheTabStanding` | 139 |
     | `SessionSet::ClosingAPaneGivesItsRoomToTheSurvivorAndKeepsTheTab` | 139 |
     | `SessionSet::ClosingTheLastPaneOfATabClosesTheTab` | 139 |
     | `SessionSet::TheCloseChordTakesThePaneAndOnlyThenTheTab` | 139 |
     | `SessionSet::CloseTabDestroysItsWholeArena` (закрытие вкладки) | 0 |
     | `SessionSet::ClosingATabTakesEveryPaneInIt` (вкладка из трёх панелей) | 0 |
     | `SessionSet::ADragKeepsReachingThePaneItsPressLandedIn` | 0 |
     | остальные 39 | 0 |

     Разделение ровное и говорящее: закрытие **вкладки** идёт через `close()` (`session.cpp:504`), который после последнего `retire()` уходит в `activate()`, а тот переставляет `focusedTerminal_` на живую вкладку до всякого `refocus()`. Закрытие **панели** такой переустановки не делает — и падает.
  4. Обратная проба, доказывающая, что падает именно этот указатель, а не что-то рядом. Во временную копию `session.cpp` (собрано, прогнано, **в дерево не закоммичено и откачено**) в конец `retire()`, до `reaper_->wake()`, добавлено:
     ```cpp
     if (focusedTerminal_ == grave.terminal) {
         focusedTerminal_ = nullptr;
     }
     ```
     После пересборки все четыре теста под `MallocScribble` дают код выхода 0, и весь набор целиком проходит под заливкой без падения (`OK: 890, ERR: 2` — обе ошибки к панелям отношения не имеют, см. ниже про артефакт заливки). Эта правка — диагностический зонд, а не предлагаемое исправление: она снимает падение, но оставляет открытым вопрос, каким должно быть поведение `canReap()` при `focusedTerminal_ == nullptr`.
- **Что предлагаю:** снять имя раньше, чем уборщик может освободить то, на что оно указывает. Порядок в `retire()` — единственное, что здесь ломается, и чинится он там же:
  - минимальная правка: в `retire()`, до `reaper_->wake()`, обнулять `focusedTerminal_`, когда он равен `sessions[index].terminal`, и не звать `focus(false)` по `nullptr` в `refocus()` (проверка там уже есть);
  - лучше — оба сразу: `retire()` не должен оставлять живое имя мёртвой панели, а `refocus()` не должен полагаться на то, что `focusedTerminal_` жив. Второе полезно и само по себе: `canReap()` (`session.cpp:929`) читает `focusedTerminal_->presentationChanged()`, то есть спрашивает про «наследника» через указатель, который в момент вызова из `retire()` называет как раз **предшественника** — с точки зрения того, ради чего эта проверка написана, она в этот момент отвечает не на свой вопрос;
  - если хочется убрать сам класс, а не случай: не будить уборщика синхронно из середины мутации модели. `retire()` мог бы отложить `wake()` до того же `eofWake_`-подобного цикла, которым уже пользуется `ptyEof()` — тогда никакой освободитель не исполняется внутри `retire()` вообще.
- **Как проверить:** `MallocScribble=1 SHITTY_PTY_TEST_HELPER=$PWD/.build/pty_test_helper .build/unit_tests SessionSet:: --threads=1` завершается с кодом 0 (набор `SessionSet` не форкает настоящий шелл, поэтому баннера libmalloc в нём нет и результат читается без оговорок). Отдельно — **добавить** тест, который закрывает сфокусированную панель двухпанельной вкладки и требует, чтобы `activeTerminal()` после этого был терминалом выжившей панели, а счётчик уничтоженных `StubHandle` (он уже есть в харнессе, `session_ut.cpp:66-68`) увеличился ровно на один. Такой тест падает на текущей реализации только под `MallocScribble`, поэтому одного его мало — прогон под заливкой нужен в критерии приёмки явно.

### S2. Захват указателя пережидает события, которые жест заканчивают

- **Серьёзность:** важная
- **Класс:** маршрутизация ввода не в ту панель / состояние, не сбрасываемое при потере контекста
- **Где** (база `e74011b8`): `lib/shitty/session.cpp:258-264` (поля `pressedPane_`, `pressedButtons_`, `draggedSplit_`), `1303-1312` (`pointerTarget()`), `1332-1377` (`pointerButton()`), `1390-1407` (`focus()`, `pointerPresence()`).
- **Кто может:** пользователь окна — непреднамеренно; любая последовательность, где нажатие есть, а отпускания окно не получает.
- **Аспекты:**
  1. **`focus(bool)` (строка 1390) и `pointerPresence(bool)` (1398) не сбрасывают ни `pressedPane_`, ни `pressedButtons_`, ни `draggedSplit_`.** `pointerPresence(false)` чистит только `overDivider_`. Сам терминал в этот момент своё указательное состояние сбрасывает — `VtermImpl::hide()` (`vterm.cpp:8998-9006`) зовёт `input.focus(false)` именно ради «held buttons, an open selection», — но состояние `SessionSetImpl` живёт отдельно и переживает это.
  2. **Последствие застрявшего нажатия.** Пока `pressedButtons_ != 0`, ветка переноса фокуса в `pointerButton()` (строка 1354, `if (input.pressed && pressedButtons_ == 0)`) больше не срабатывает никогда, а `pointerTarget()` (1303) возвращает `terminalOf(pressedPane_)` независимо от того, где указатель. Клик в соседнюю панель перестаёт и переносить фокус, и доходить до своей панели: он уходит в ту, где нажатие когда-то началось.
  3. **Смена вкладки при зажатой кнопке.** Аккорды идут через `InputBindings` впереди `SessionSetImpl` (`session.cpp:975`, «Behind InputBindings») и во время перетаскивания не блокируются. После `cmd+2` `pressedPane_` продолжает называть панель **фоновой** вкладки: движения и отпускание уходят туда. Программа в невидимой вкладке получает отчёты мыши, а завершившееся там выделение пишет primary-выделение окна (`vterm.cpp:6848-6849`) — то есть содержимое вкладки, на которую пользователь в этот момент не смотрит, оказывается в primary, откуда его достаёт следующий средний клик.
  4. **`draggedSplit_` — индекс узла, не привязанный к дереву** (строка 263, ставится в 1358). Тот же `cmd+2` посреди перетаскивания шва оставляет его выставленным, и `dragDivider()` (1242) пройдётся по швам **новой** активной вкладки, подхватив тот, у которого совпал индекс узла. Памяти это не портит — индекс всегда приходит из живого `layout()` текущего дерева, — но двигает шов не там, где начинали, и рассылает `SIGWINCH` шеллам, которых пользователь не трогал.
- **Чем грозит:** ввод мыши (выделение, отчёты протокола мыши, primary-выделение) адресуется панели, которой пользователь в этот момент не управляет и, в случае 3, даже не видит. Клавиатуры это не касается — она идёт по `focusedTerminal_` и остаётся правильной.
- **Чем подтверждено:** двумя временными тестами на существующем харнессе `session_ut.cpp` (собраны, прогнаны, откачены). Оба падают на `e74011b8`; их можно взять как есть в задачу `F-S2`:
  ```cpp
  STD_TEST(R8SecPressSurvivesTabSwitch) {
      Harness harness;
      harness.options.panes = true;
      harness.sessions->splitFocused(SplitDirection::Vertical);
      harness.newTab();
      harness.sessions->splitFocused(SplitDirection::Vertical);
      harness.sessions->activate(0);

      harness.pointerPress(10, 10);                       // нажатие в левой панели вкладки 0
      Vterm* const heldInTabZero = harness.sessions->activeTerminal();

      harness.nextTab();                                  // отпускания не было
      Vterm* const beforeClick = harness.sessions->activeTerminal();
      STD_INSIST(beforeClick != heldInTabZero);

      harness.pointerPress(10, 10);                       // клик в другой панели видимой вкладки
      STD_INSIST(harness.sessions->activeTerminal() != beforeClick);   // падает
  }

  STD_TEST(R8SecPressSurvivesWindowFocusLoss) {
      Harness harness;
      harness.options.panes = true;
      harness.sessions->splitFocused(SplitDirection::Vertical);

      harness.pointerPress(10, 10);
      Vterm* const left = harness.sessions->activeTerminal();
      harness.windowFocus(false);
      harness.windowFocus(true);

      harness.pointerPress(70, 10);                       // клик в правой панели
      STD_INSIST(harness.sessions->activeTerminal() != left);          // падает
  }
  ```
  Вывод прогона на `e74011b8`: `OK: 0, ERR: 2` — оба `STD_INSIST` про перенос фокуса не выполняются, то есть клик в соседнюю панель после «застрявшего» нажатия действительно не переносит фокус и уходит в старую панель.
- **Что предлагаю:** сбрасывать `pressedPane_`, `pressedButtons_` и `draggedSplit_` там же, где сбрасывается `overDivider_` — в `pointerPresence(false)` и в `focus(false)`; и дополнительно гасить их при смене активной вкладки (`activate()`, `session.cpp:575`), потому что жест, начатый в другой вкладке, закончиться в этой не может по смыслу. `draggedSplit_` стоит хранить не одним индексом, а парой «вкладка + узел» либо гасить при любой мутации дерева.
- **Как проверить:** внести оба теста выше в `session_ut.cpp` и добиться, чтобы они проходили; дополнительно — тест, что после `nextTab()` при зажатой кнопке движение указателя не доходит до заглушки `StubHandle` панели фоновой вкладки.
- **Оговорка, от которой зависит способ починки:** насколько часто окно реально теряет отпускание — вопрос к бэкенду окна, а не к этому коду, и я его не измерял (см. «Не проверено»). Пункт 3 от этого не зависит: смена вкладки аккордом при зажатой кнопке достижима без всякой потери событий.

### S3. Перетаскивание файла всегда попадает в сфокусированную панель, а не в ту, куда целились

- **Серьёзность:** важная
- **Класс:** доставка данных не в ту панель
- **Где** (база `e74011b8`): `lib/shitty/drop_target.cpp:71-96` — `VtermDropTarget::dropped()` берёт `composer.sessions->activeTerminal()`; `dragOver()` (строка 71) получает координаты `i32, i32` и **отбрасывает их обоими безымянными параметрами**.
- **Кто может:** пользователь окна; источником данных при этом может быть любое приложение, умеющее drag-and-drop.
- **Путь:** файл отпущен над панелью B → `dropped()` → `activeTerminal()` = панель A → `dropUriList()`/`dropText()` (`vterm.cpp:2561`, `2618`) → `PasteOutput` в pty панели A.
- **Чем грозит:** путь к файлу в shell-квотировании уезжает в шелл, на который пользователь не целился. Исполнения не происходит: обе двери ведут в `PasteOutput` с bracketed paste (`dropText()` — `vterm.cpp:2573`, `dropUriList()` — через `dropBuffered()`, `vterm.cpp:2521-2526`), а `buildQuotedEntry()` (2586) добавляет разделитель, а не перевод строки. Но если панель A стоит на приглашении, ожидающем ввод (пароль `sudo`, подтверждение `y/n`, открытый `ssh`), туда уходит текст, предназначавшийся не ей.
- **Оговорка:** код `drop_target.cpp` волной 8 не менялся (`git log -- lib/shitty/drop_target.cpp` — последний коммит `74166c4f`, «Move sources into lib and bin directories»). До сплитов «активный терминал» и «терминал под курсором» совпадали всегда, и это был правильный код. Неправильным его сделала эта волна, не тронув.
- **Что предлагаю:** дать `SessionSet` публичный ответ «какой терминал под этим пикселем» (внутри он уже есть — `paneAt()`, `session.cpp:1177`, и `terminalOf()`, 1195) и брать его в `dropped()` по координатам отпускания; `dragOver()` те же координаты уже получает и может подсвечивать целевую панель.
- **Как проверить:** **добавить** тест: две панели, фокус в левой, отпускание с координатами внутри правой — байты должны появиться в `written` правой заглушки `StubHandle` и не появиться в левой.

### S4. `OSC 52` на запись не спрашивает, какая панель просит

- **Серьёзность:** замечание
- **Класс:** данные между панелями / подмена буфера обмена
- **Где** (база `e74011b8`): `lib/shitty/vterm.cpp:6844-6854` — `osc_CLIPBOARD_WRITE()` пишет в `composer.window->primary()`/`secondary()` без единой проверки; на чтение (`osc_CLIPBOARD_QUERY`, строка 6805) стоит `composer.opts->allowOsc52Read`, по умолчанию `false` (`options.h:113`, `options.cpp:129`).

- **Чем грозит:** программа в одной панели подменяет буфер обмена окна ровно перед тем, как пользователь вставит его в другую панель. Чтения чужого буфера по умолчанию нет — это проверено и закрыто опцией.

Это довод за опцию, а не блокер.
- **Что предлагаю:** отдельная опция по образцу `allowOsc52Read` — например `osc52WriteFocusedOnly`, при которой запись принимается только от терминала, равного `focusedTerminal_`. Решение продуктовое, поэтому пишу как предложение, а не как требование.

### S5. С `-allowWindowOps` любая панель перекраивает всё окно

## Проверенное и чистое

Поимённо — то, куда я заглянул и где ничего не нашёл. База всюду `e74011b8`.

**Клавиатура и фокус (главный вопрос ревью).**

- `SessionSetImpl::key()` и `text()` (`session.cpp:1163-1169`) не имеют собственной логики выбора: обе идут в `activeTerminal()`, а он — единственное поле `focusedTerminal_` (`session.cpp:1063-1070`). Второго ответа на вопрос «куда идёт нажатие» в коде нет.
- `focusedTerminal_` присваивается ровно в двух местах — `activate()` (`session.cpp:596`) и `refocus()` (`session.cpp:636`), и обе точки стоят до того, как что-либо доставляется. Окна «фокус уже уехал, а ввод ещё идёт по-старому» я не нашёл.
- Клик переносит фокус **до** доставки нажатия: `pointerButton()` зовёт `focusPane(pane)` на строке 1366, а до терминала нажатие доходит только на 1376. Обратного порядка нет.
- `splitFocused()` (`session.cpp:645-687`) ставит фокус на новую панель через `tree.split()` и подтверждает `refocus()` до `publishSessionsChanged()`; на исключении из `openSession()` откатывает дерево и снова зовёт `refocus()` (строки 669-673) — нового терминала, в который мог бы уйти ввод, при неудачном запуске не остаётся.
- `focusNeighbour()` (`session.cpp:689`) и `focusPane()` (`session.cpp:698`) обе заканчиваются `refocus()`; `PaneTree::focus()` (`pane_layout.cpp:190`) молча игнорирует панель не из этого дерева, а не выставляет мусорный индекс.
- Переключение вкладки: `activate()` (`session.cpp:575-618`) сначала прячет все панели, не принадлежащие входящей вкладке, и только потом показывает свои и зовёт `refocus()`. Фоновая вкладка не считает себя сфокусированной — за это отвечает разделение `show()`/`focus()`, и оно соблюдено.
- `focus(bool)` окна (`session.cpp:1390`) уходит только в сфокусированную панель; соседи остаются видимыми и нефокусированными. `focused_` и `pointerPresent_` переигрываются в `refocus()` (строки 641-642), так что панель, родившаяся после того, как окно получило фокус, узнаёт о нём.
- Аккорды сплитов заперты дважды: `InputBindingsImpl::find()` пропускает строку с `panes = true` при выключенной опции (`input_bindings.cpp:211-213`), и `splitFocused()` отказывает по той же опции (`session.cpp:648`). Пока опция выключена, `cmd+d` остаётся программе внутри — то есть чужой аккорд не отбирается.
- Предредактирование IME (`input_router.cpp:71`) идёт в `activeTerminal()` — то есть в ту же панель, что и клавиши; расхождения между обычным вводом и композицией нет.
- Прямоугольник кандидатного окна IME считается по **сфокусированной** панели, а не по последней в списке: `application.cpp:575-576` берёт `anchored` там, где `pane.focused`, а `application.cpp:592-593` прибавляет к вставкам окна происхождение именно этой панели.

- Склад ячеек: интерфейс `CellExtraClient` (`cell_extra_store.h:44-53`) перечисляет клиентов сам, а не доверяет тому, кто позвал `collect()`, и отвязка вынесена в деструктор. Тот дефект волны 7 в этом дереве закрыт; новых чтений освобождённого пула через склад при делении и закрытии я не нашёл. `resizeExtraStore()` (`session.cpp:493-502`) вызывается и при появлении панели, и при её смерти, так что бюджет не «только растёт».

**Арифметика геометрии.**

- `PaneTree::place()` (`pane_layout.cpp:258-296`): зазор ограничен размером (`min<u32>(divider, extent)`), поэтому `usable = extent - gap` не уходит в минус; доля считается в `u64` (`scaled`), остаток деления отдаётся дальней панели, так что панели и зазор всегда складываются обратно в исходный прямоугольник. Приведения к `u16` безопасны, пока окно меньше 65536 пикселей по стороне.
- Вырожденная панель нулевой ширины или высоты не даёт деления на ноль: `paneGeometry()` (`session.cpp:833-843`) берёт `max<u32>(1, ...)` и по сетке, и по знаменателю глифа, а все четыре отображения в `mouse_frontend.cpp` (66-110) делят только на `max(1, glyph...)` и берут ширину/высоту как `max(1, ...)`.
- Отрицательные координаты указателя обрабатываются правильно: `toContentBox()` (`session.cpp:1171`) даёт отрицательный `x` для точки в хроме, а сравнения в `paneAt()` (1188) и `dividerAt()` (1232) идут в `int` после продвижения `u16` — панель под такой точкой не находится, а не находится «нулевая».
- Клампы перетаскивания шва (`session.cpp:1259-1279`): ранний выход при `extent <= 0` делает знаменатель `span` заведомо ненулевым; нижняя граница `min(floorPixels, extent)` не даёт клампу перевернуться на окне меньше минимума; верхняя граница даёт долю не больше `shareScale`, а `setShare()` (`pane_layout.cpp:307`) дополнительно зажимает в `[1, shareScale-1]`, то есть панель нулевой доли получить нельзя.
- `dividerGrab()` (`session.cpp:1200-1213`) никогда не возвращает меньше одного пикселя, так что полоса захвата не может стать пустой.
- `pressedButtons_ = 1u << (unsigned)(input.button)` (`session.cpp:1336`) не может сдвинуть за разрядность: `plt::PointerButton` (`ext/plt/input.h:162-177`) — восемь значений, максимум 7.
- `windowPane()` (`pane_layout.cpp:38-54`) и `contentBox()` (`session.cpp:791-808`) вычитают вставки с насыщением — резерв шире окна даёт пустой прямоугольник, а не огромный.

**Данные между панелями.**

- Хит-тест гиперссылок `OSC 8` не дотягивается до соседа: `resolveHyperlink()` (`vterm.cpp:2462-2470`) идёт через `mouseCell()`, а тот (`mouse_frontend.cpp:83-90`) возвращает `false` для пикселя вне собственного прямоугольника панели, оба конца которого берутся с одной поверхности (`contentLeft()`/`contentRight()`, `mouse_frontend.h:70-97`). Соседняя панель не может ни прочитать, ни подсветить чужую ссылку.

- В диффе волны нет ни ключей, ни строк подключения, ни новых зависимостей — только код рендера, ввода и раскладки внутри репозитория.
