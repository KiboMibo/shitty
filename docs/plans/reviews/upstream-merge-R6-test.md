## 3. Четвёртая вырожденная фикстура: сумма двух равных слагаемых

### 3.1. Что найдено

`VtermHeadless::CountsBothScreensOnceThePaneHasEnteredTheAlternate` (`lib/shitty/vt_headless_ut.cpp:440`) проверяет

```c++
STD_INSIST(terminal.cellCapacity() == primaryCells + alternateCells);
```

где `primaryCells = columns * (rows + saveLines)` и `alternateCells = columns * rows`. В безголовой фикстуре `saveLines` — это `VtConfig::saveLines`, у которого **умолчание в структуре равно нулю** (`lib/vterm/vt_config.h:22`). Значит `primaryCells == alternateCells == 1920`, и сумма перестаёт говорить, **из какого экрана** взято второе слагаемое.

Проба (мутация `D1`), продуктовый код цел во всём остальном:

```diff
 size_t VtermImpl::cellCapacity() const {
     size_t count = frame_pri->info().cellCapacity;
     if (altScreenInitialized) {
-        count += frame_alt->info().cellCapacity;
+        count += frame_pri->info().cellCapacity;
     }
```

Результат: **`OK: 963`**. Ни один тест не покраснел. Это ровно тот дефект, ради которого сторож заводился, только в другую сторону: у продукта `saveLines` по умолчанию **500** (`options.cpp:119`, `bin/st/shitty.toml:182`), и там основной экран — это сетка плюс полтысячи строк истории, а альтернативный — только сетка. Двойной счёт основного раздувает общий бюджет хранилища на `columns * saveLines` на каждый терминал, побывавший на альтернативном экране, — «тихий» дефект того же класса, что и пропуск слагаемого, с обратным знаком.

Комментарий коммита `341935a1` этот ноль называет прямым текстом («saveLines is zero here, so both screens are 1920 cells») — четвёртый раз за волну описание вырожденности живёт в файле как объяснение фикстуры, а не как дыра. Это уже не совпадение, а привычка: `T5.2` §«Обнаружено» пункт 2 фиксирует то же самое про `application_ut.cpp:764`.

### 3.2. Что сделано

Фикстура переставлена на форму, в которой дефект вообще существует, — снимок `VtConfig` подменяется до создания терминала (тем же приёмом, что в `T5.5`, `vt_headless_ut.cpp:294`, потому что `Screen::createPrimary()` читает `saveLines` один раз, при постройке):

```c++
VtConfig scrollbackConfig = *composer.vtConfig.config;
scrollbackConfig.saveLines = 500;
composer.vtConfig.config = &scrollbackConfig;
```

и добавлено предусловие, которое не даст фикстуре тихо вернуться в вырожденную точку:

```c++
STD_INSIST(primaryCells != alternateCells);
```

Двухфакторная таблица, мутация × фикстура — целиком измеренная, не рассуждение:

| | фикстура `saveLines = 0` (было) | фикстура `saveLines = 500` (стало) |
|---|---|---|
| `D1` — второе слагаемое из `frame_pri` | **`OK: 963`** — зелено | `OK: 962, ERR: 1`, `terminal.cellCapacity() == primaryCells + alternateCells failed` — ровно этот тест |
| `M-B` — слагаемое выброшено (`false &&`) | `OK: 962, ERR: 1` | `OK: 962, ERR: 1` — прежняя сила сохранена |
| целый код | `OK: 963` | `OK: 963` |

Правый столбец — это и есть смысл правки: сторож не потерял ничего из того, что ловил, и приобрёл вторую мутацию, к которой был слеп.

### 3.3. Форма, по которой их искать

Все четыре случая волны — один и тот же приём, и признак у него общий: **в точке съёма проверяемое слагаемое равно нулю или равно своему соседу.**

| Задача | Что обнулилось/совпало |
|---|---|
| `T5.5` | обе границы нулевые — окновые и панельные инсеты неразличимы |
| `T5.3` (дедуп) | аргумент `roots` не проходился ни одним вызовом — дубликата не из чего сделать |
| `T5.2` | домашняя клетка — оба произведения `column*glyphWidth` и `row*glyphHeight` нули |
| `T5.3` (alt) — **этот** | `saveLines = 0` — оба слагаемых суммы равны |

Проверка стоит одной пересборки: сломать фикстуру при целом коде (или, что то же самое, поставить мутацию, которая меняет **какое** слагаемое берётся, а не **берётся ли оно вообще**) и посмотреть, покраснело ли.

## 4. `C8b`: дыра закрыта, и её основание уточнено

### 4.1. Уточнение метода

`T5.2` §4 объявила `C8b` («высота картинки в дампе изображения из `renderer.columns()` вместо `renderer.rows()`», `test_mode.cpp:2620`) незакрытой на том основании, что список красных имён при мутации **дословно совпал** с базовым.

Довод неполный. `tst/test_bitmap_font_render.py:59` утверждает размер дампа **точным равенством**:

```python
self.assertEqual((width, height), (2 * BORDER + 16, 2 * BORDER + 8))
```

При `columns=2, rows=1, px=py=8` высота под `C8b` стала бы `4 + 2*8 = 20` вместо `12`, и этот тест покраснел бы. Он не покраснел, потому что **уже красный**: на этой машине `load_font()` для BDF-штриха отвечает отказом (`RuntimeError: invalid font load response`), и все восемь тестов `test_bitmap_font_render` лежат в базовых 22 красных вместе с `test_synthesized_symbols`, `test_color_font_render`, `test_italic_overhang` и `test_soft_render` — то есть с **большей частью потребителей `render_image`**.

Отсюда правило, которое стоит внести в брифы: **«набор красных имён не изменился» доказывает отсутствие сторожа только среди тестов, которые в этом прогоне зелёные.** Мутация, чей единственный наблюдатель уже упал по другой причине, выглядит неотличимо от мутации, которую не наблюдает никто. У волны это уже второй случай, когда довод пришлось переоценить задним числом (первый — «CAS-хеши совпали», отозванный самой `T5.3`).

Практический вывод от этого не меняется: **в этой среде** `C8b` действительно не ловится ничем, и джобы, где BDF грузится, — единственное, что от неё защищало.

### 4.2. Сторож

Заведён `tst/test_render_image_geometry.py` — один тест, который снимает тот же размер с шрифта, который здесь **грузится**:

```python
metrics = terminal.load_font("monospace")     # px=10, py=19
width, height, _ = terminal.render_image("monospace")
self.assertNotEqual(metrics["px"], metrics["py"])
self.assertNotEqual(COLUMNS, ROWS)            # 11 x 7
self.assertEqual(width,  COLUMNS * metrics["px"] + 2 * BORDER)
self.assertEqual(height, ROWS    * metrics["py"] + 2 * BORDER)
```

Фикстура неквадратная по обеим осям и это **утверждается**, а не подразумевается: квадратная клетка спрятала бы перестановку метрик, квадратная сетка — перестановку счётчиков. Ровно та ошибка, которую разбирает §3.

Три мутации в `test_mode.cpp`, каждая — пересборка `st_test` и прогон:

| Мутация | Строка | Результат |
|---|---|---|
| `C8b` — высота из `renderer.columns()` | `:2620` | `FAIL`, `AssertionError: 213 != 137` |
| `C8` — ширина из `renderer.rows()` | `:2619` | `FAIL`, `AssertionError: 74 != 114` |
| `C8c` — `getPx()`/`getPy()` переставлены между осями | `:2619-2620` | `FAIL`, `AssertionError: 213 != 114` |
| откат всех трёх | — | `OK` |

Третья мутация в отчётах волны не значилась: перестановка **метрик глифа** — это ещё одна пара на том же вызове, и она была не покрыта наравне с `C8b`. Теперь покрыты обе пары.

Файл попадает в набор автоматически: `build.py:1046` берёт `tst/*.py` глобом, регистрировать нечего. Полный прогон после правки — `Ran 6400` вместо `Ran 6399`, красных ровно те же 22.

### 5.3. `[средняя, продуктовая — не чинил]` Половина `pointerPresence()` адресована не той панели

Подтверждено чтением кода, границы задачи не позволяют чинить.

```
lib/shitty/session.cpp:1474  pointerMotion   → pointerTarget(input.pixelX, input.pixelY)->pointerMotion(input)
lib/shitty/session.cpp:1550  pointerButton   → pointerTarget(input.pixelX, input.pixelY)->pointerButton(input)
lib/shitty/session.cpp:1561  scroll          → pointerTarget(input.pixelX, input.pixelY)->scroll(input)
lib/shitty/session.cpp:1586  pointerPresence → activeTerminal()->pointerPresence(present)     ← сюда
```

Три из четырёх входов указателя адресуются **панели под указателем**, четвёртый — **сфокусированной** панели. Указатель может стоять над несфокусированной панелью: движение фокус не двигает, это прямо утверждено тестом `T5.10` («Motion does not move the focus, which is what lets an unfocused pane hold a filter state at all»).

Что из этого следует наблюдаемого. `VtermInput::pointerPresence(false)` (`vterm.cpp:2231`) делает три вещи: сбрасывает фильтр движения, снимает `pointerPositionKnown` и зовёт `refreshHyperlinkAndRedraw()`. Значит при уходе указателя из окна:

- панель, над которой указатель **реально стоял**, ничего не узнаёт — подсветка гиперссылки под курсором (OSC 8) на ней **остаётся гореть** после того, как указатель ушёл из окна, и фильтр движения продолжает считать, что знает клетку;
- сфокусированная панель получает уведомление о событии, которого с ней не происходило.

Заявка волны 7 в борде это место называет, но описывает как «панель не узнаёт об уходе»; наблюдаемая половина — застрявшая подсветка гиперссылки — там не названа, и именно она даёт сторожа: `hyperlink(column, row)` есть в питоновском наборе (`tst/harness.py:940`), а `pointer_presence()` — тоже (`:866`), так что тест на это писать есть чем. Сторожа я **не заводил**: он краснел бы на текущем дереве, то есть был бы не сторожем, а красным тестом в зелёной ветке.

### 5.4. `[низкая]` Сторож резерва хрома односторонний: только горизонталь

`MouseFrontend::TheChromeReserveIsCountedOnceOnTheWayIntoAPanesGeometry` ставит резерв только слева (`ChromeSide::Left, 30`) и делит вертикальным сплитом. Проба: `.originY = (i32)(chrome.top) + area.y` → `.originY = area.y` даёт `OK: 962, ERR: 1`, и красный — **не** новый сторож, а старый `Composer::EveryPixelOfAComposersContentBoxAnswersFromItsOwnSide`. То есть ось Y защищена, но не тем тестом, чьё имя про «резерв считается один раз».

Дыры здесь нет, чинить нечего. Но форма знакомая — та же «половина пары выглядит как пара», о которой пишет `T5.2` §«Обнаружено» пункт 5 (для `C8`/`C8b`) и пункт 3 (для `showWindow()` против `WindowSizingRequests`). За волну это уже третье место такой формы, и все три нашлись не потому, что кто-то их искал, а потому, что рядом ставили мутацию.

## 7. Что осталось непроверенным и почему

**1. `vterm_boundary` и `check_includes.py` я не гонял.** Ни один из моих двух файлов не меняет включений: в `vt_headless_ut.cpp` правка внутри тела теста, `tst/*.py` этой проверке не подлежит. Состояние гварда — предмет `G15`, которая шла параллельно.

**2. Три оставшихся места вызова `grid_geometry.h` в `test_mode.cpp` (`C7`, `C7b`, `C9`) я не перемеривал.** `T5.2` называет их пойманными с большим запасом (3, 2 и **319** тестов), и запас такого размера не может быть артефактом среды: в отличие от `C8b`, чей единственный наблюдатель лежал, здесь наблюдателей сотни. Приоритет отдан `C8b`, где заявлен **ноль**.

**3. Шесть остальных сторожей я перепроверял по одной мутации, а не по всем заявленным.** Полностью, двумя мутациями, перепроверены `T5.1` и `T5.5`; у `T5.10` заявлено три мутации, я поставил одну (`resetMotion`), у `T5.2` — четыре (`C1`, `C2`, `C6`, `C6b`), я поставил `C1`. Основание для остановки: там, где я мерил обе, числа исполнителя совпали дословно, включая имена ловящих тестов; вероятность, что отчёт точен на проверенных и выдуман на непроверенных, мала. Полный перебор — ещё девять пересборок.

**4. Прогон `./build test` целиком не делался** — бриф называет его красным на `ui_sidebar_tabs_ut.cpp` из-за `TMPDIR` внутри дерева, и это территория `G16`. Я гонял цели по отдельности (`unit_tests`, `st_test`, `pt_test`, `toml_dump`), все зелёные.

**5. Сторож на застрявшую подсветку гиперссылки (§5.3) не заведён.** Он краснел бы на текущем дереве: это описание продуктового дефекта, а не регрессии. Заводить его надо вместе с починкой, в волне 7.

**6. Питоновский набор гонялся одним процессом, а не двадцатью группами.** Числа поэтому не сравнимы с числами волны напрямую (§1); все выводы взяты как `diff` списков имён внутри одной среды. Групповой прогон изменил бы только раскладку по джобам, но проверено это не было.

**7. Прогон на Linux/в docker не делался.** Всё измерено на Apple clang с libc++ — по `CLAUDE.md` это не свидетельство для компиляции, но мои правки не добавляют ни одного `forward`, ни одной новой зависимости и ни одного включения, так что класс расхождения, о котором предупреждает `CLAUDE.md`, здесь не задействован.
