## Резюме

Все четыре критерия приёмки волны выполнены, и три из них я перепроверил своими прогонами,
а не по чужому слову. Побайтовую неизменность однопанельного рендера удалось доказать сильнее,
чем это сделал исполнитель: скомпилированный MSL в обоих бинарниках **байт в байт один и тот же**
(sha256 `24f16a68…`, 49 974 байта), а эталонный рендерер на одном и том же кадре даёт
**один и тот же хеш изображения** до и после (`fnv1a=e9c703f2389655ef`, 45 738 байт пикселей).
Мутационные контроли проходят: центральное свойство `A3` и оба свойства панельного рендера
краснеют ровно там, где обещано.

Блокирующих находок нет. Главное, на что смотреть:

1. **Вывод исполнителя о чувствительности второго прибора у меня не воспроизвёлся.** В моей
   конфигурации ни «две панели», ни «искалеченное зеркало арен» не выходят из шума —
   ни +30%, ни +3.2%. Прибор чувствителен не сам по себе, а при том соотношении работ,
   которое было у исполнителя. Узкий прибор, чувствительный **всегда**, существует и стоит
   шесть строк: время одной `uploadArenas()`, на котором калечение зеркала даёт ×2.
2. **`uploadArenas()` нарушает контракт, записанный в шапке `render_arena.h`**, на пути отказа
   аллокации: сбрасывает только своё зеркало и оставляет второе с записью о копиях, которых
   не было. Воспроизведено принудительным отказом.
3. **Отказ Vulkan от двух панелей молчалив** и превращается в бесконечный цикл перерисовки.

### Важные

#### В1. `uploadArenas()` оставляет второе зеркало врущим, когда аллокация арены не удалась

`lib/shitty/render_metal.mm:409-436`.

**Что не так.** Шапка `render_arena.h:64-67` формулирует контракт прямо:

> The plan assumes every copy it names is then made. A caller that cannot make them (an
> allocation failed, the buffer was replaced and lost its contents) calls reset() so the next
> frame starts from nothing rather than from a mirror that was never written.

Вызывающий этот контракт нарушает на обоих путях отказа. Порядок в коде такой:

```
maskMirror.plan(...);          // :415
colorMirror.plan(...);         // :416  — план записан, копии ещё не сделаны
if (!ensureArenaBuffer(maskArena, ...)) { maskMirror.reset(); return false; }   // :419-422
if (!ensureArenaBuffer(colorArena, ...)) { colorMirror.reset(); return false; } // :429-432
... memcpy'и идут ниже, :449-465 ...
```

Если падает аллокация цвета — сбрасывается `colorMirror`, а `maskMirror` остаётся с записью
`uploaded = used` для кадра, в котором **ни одного `memcpy` не выполнилось**. Симметрично: если
падает аллокация маски, врать остаётся `colorMirror`, потому что его план записан строкой выше.

**Доказано принудительным отказом** (временная правка, откачена): заставил аллокацию цветовой
арены отказать на 40-м кадре и напечатал, что зеркало маски планирует и что реально копируется.

```
R6QA-COPY: frame 39 pane 0 mask copy [1875474,2804868) base 0 (used 2804868)
R6QA-FAIL: frame 40, forcing the colour arena allocation to fail; mask plan for pane 0 was [0,942030) base 0
R6QA-COPY: frame 41 pane 0 mask copy [942030,1868508) base 0 (used 1868508)
```

На кадре 40 зеркало маски запланировало **полную** перезаливку `[0, 942030)` — сменилось
поколение, все полосы переехали. Копия не состоялась: `uploadArenas()` вышел раньше. На кадре 41
зеркало считает первые 942 030 байт уже лежащими на устройстве и досылает только хвост.
Их там нет.

**Чем грозит.** Глифы рисуются из чужих байтов арены, пока не сменится поколение — то есть
искажённый текст без падения, без сообщения и без следа в тестах. Хуже всего вариант, когда
аллокация маски **удалась с заменой буфера** (`replaced == true`, зеркало перепланировано «всё
целиком»), а следом отказала аллокация цвета: тогда на устройстве совершенно пустой буфер,
а зеркало утверждает, что он полон.

Путь требует отказа `newBufferWithLength` (нехватка памяти) — поэтому «важная», а не блокирующая.
Но это ровно тот класс, ради которого `render_arena.h` и написал свой абзац про `reset()`.

**Предлагается.** На обоих путях отказа сбрасывать **оба** зеркала:

```cpp
if (!ensureArenaBuffer(maskArena, maskArenaCapacity, maskMirror.used(), replaced)) {
    maskMirror.reset();
    colorMirror.reset();   // его план тоже записан и тоже не будет выполнен
    return false;
}
...
if (!ensureArenaBuffer(colorArena, colorArenaCapacity, colorMirror.used() * sizeof(u32), replaced)) {
    colorMirror.reset();
    maskMirror.reset();
    return false;
}
```

Два слова кода. Отдать `F6`.

#### В2. Чувствительность второго прибора — свойство нагрузки, а не прибора; у меня она не воспроизвелась

`docs/reports/T8-renderer-contract-2026-08-19.md`, раздел «Замеры», инструмент 2.

**Что не так.** Отчёт утверждает: «прибор разрешает 3% и краснеет ровно на регрессии `A3`»,
и подпирает это двумя контролями — две панели +30%, искалеченное зеркало ещё +3.2%, «три группы
значений не пересекаются». Я собрал тот же прибор (время от входа в `updateOnce` до вызова
`draw()`; отдельно проверил, что стоп именно **до** `draw()`, иначе в выборку попадает ожидание
GPU и числа растут вдесятеро) и прогнал пять конфигураций по 500 кадров:

| конфигурация | медиана, мкс/кадр (прогоны) |
|---|---|
| база `650da24f`, одна панель | 3394 · 3414 · 3449 |
| после, одна панель | 3468 · 3395 · 3405 · 3369 · 3391 · 3408 |
| после, **две панели** | 3438 · 3456 · 3483 |
| после, одна панель, **зеркало арен искалечено** | 3408 · 3408 |
| после, две панели, зеркало искалечено | 3376 · 3454 |

**Все пять групп полностью перекрываются.** Ни +30%, ни +3.2% нет. Разбор кадра объясняет, почему:

| составляющая | одна панель | две панели |
|---|---|---|
| `assignStrips` (шейпинг и раздача полос) | 3286 мкс | 1637 + 1637 = 3274 мкс |
| `materializeCells` и остаток цикла | ~21 мкс | ~42 мкс |
| `uploadArenas` | 24-26 мкс | 72-74 мкс |

Кадр на 99% состоит из `assignStrips`, а он привязан к **`Screen`**, а не к панели: обе панели
временного вызова смотрят в один `Screen`, поэтому вторая шейпинг не повторяет. Отсюда и то,
что «две панели» ничего не двигают. У исполнителя тот же временный вызов — одна `TerminalUpdate`
на обе панели (это видно по его же трассе: `updates 840@0` и `840@840`), и его +30% — это второй
проход `materializeCells`, который в его конфигурации был большой долей от 295 мкс, а в моей —
0.6% от 3400.

**Чем грозит.** Формулировка «прибор разрешает 3%» читается как свойство прибора и будет
процитирована `T9`/`T10`, когда они снова полезут в этот замер. Она верна только при том
соотношении шейпинга и материализации, которое было у исполнителя; при вдвое большей сетке
или при живом шейпинге прибор не видит и двукратного подорожания стадии `A3` — то есть
повторяет судьбу первого, слепого прибора, только менее очевидно.

**Что при этом стоит и держится.** Регрессии на одной панели нет — это я подтверждаю
независимо, и на двух приборах сразу.

**Предлагается.** Записать в отчёт `T8` (или в борд) узкий прибор, у которого чувствительность
не зависит от нагрузки: время одной `uploadArenas()`. Мои числа:

| конфигурация | `uploadArenas`, мкс/кадр |
|---|---|
| база `650da24f`, одна панель | 23.7 · 24.3 · 24.2 |
| после, одна панель | 23.7 · 25.7 |
| после, одна панель, **зеркало искалечено** | **50.6 · 52.8** |
| после, две панели | 72.2 · 74.0 |
| после, две панели, зеркало искалечено | 90.1 · 92.6 |

Калечение зеркала на одной панели даёт **ровно ×2**, группы не пересекаются с большим запасом,
и прибор меряет ровно ту стадию, которую `A3` меняет. Шесть строк временной инструментации.

#### В3. Отказ Vulkan от двух панелей молчалив и оборачивается бесконечной перерисовкой

`lib/shitty/render_vk.cpp:2172-2190`, `lib/shitty/application.cpp:517-521`.

**Что не так.** `RendererImpl::update(const PaneUpdate*, size_t)` на `count != 1` делает
`return false` — без записи в лог, без `raiseError`, без единого следа в рантайме. Комментарий
рядом перечисляет, что нужно доделать, и это честно; но комментарий видит тот, кто открыл файл.
Вызывающий видит только `false`:

```cpp
const bool presented = composer.renderer->update(&pane, 1);
if (!presented) {
    composer.window->requestFrame();
    return false;
}
```

То есть окно бесконечно просит следующий кадр, ничего не рисует и молчит.

**Чем грозит.** Решение командира «сплиты на Wayland не включать» держится только на записи
в плане. Когда `T9` даст дерево панелей, первый же запуск со сплитом на Linux даст чёрное
или застывшее окно и загруженный CPU без единого сообщения — то есть час на диагностику того,
что уже написано в исходнике.

**Предлагается.** Одно из двух, на выбор `F6`/`T9`:
(а) на этом пути один раз `raiseError` из `fatal.h` с текстом «splits are not supported on this
backend» — решение окончательное и падение честнее чёрного окна;
(б) отличить «постоянный отказ» от «кадр не вышел» в контракте `Renderer::update`, чтобы
`presentTerminal()` не перезапрашивал кадр вечно.

Сегодня путь недостижим (двух панелей никто не отдаёт, файл на darwin не собирается), поэтому
«важная», а не блокирующая.

### Замечания

- **`lib/shitty/render_arena_ut.cpp:186-196`, `NeverMatchesAPaneWithoutAScreen` — тест
  пустой.** Он объявляет, что панель без экрана никогда не совпадёт с прошлым кадром, но
  просит `used = 0`, а при нулевом объёме копия пуста в обоих случаях, и `sendsNothing()`
  истинно всегда. Доказано мутацией **M-A**: убрал `|| previous.pane == nullptr` из сравнения
  в `render_arena.h:113` — **все 50 тестов остались зелёными**. Свойство, которое шапка
  заголовка называет прямо («Null is a legal value and simply never matches a previous frame»),
  не защищено ничем. Лечится сменой `{nullptr, 0, 0}` на `{nullptr, 0, 100}` и ожиданием
  `plan.sends(0, 0, 0, 100)` на **втором** кадре. Правку не вносил сам: `render_arena_ut.cpp` —
  файл волны 6, и `R6-test` идёт параллельно; конфликт дороже находки.

- **`lib/shitty/mouse_frontend.cpp:49-51` — комментарий врёт про количество.** Сказано, что
  смешанная протяжённость была «in three of the four mappings while the fourth — mouseCell —
  already compared surface against surface». Отображений с дефектом было **два**:
  `mouseProtocolPoint` и `mouseSelectionCell` — только они считали *протяжённость* как разность
  инсетов. `mouseCell` и `mouseAutoscrollDirection` сравнивали абсолютный край с абсолютным
  краем и были верны. Доказано мутацией **M-F**: вернул в `mouseAutoscrollDirection` дословно
  дореформенное `geometry.framebufferHeight - geometry.insets.bottom - 1` — **все 50 тестов
  зелёные**, потому что `contentBottom()` это то же выражение буква в букву. То же число стоит
  в сообщении коммита `c048d84a`. Читатель пойдёт искать регрессионный тест на автопрокрутку,
  которого не должно быть.

- **`lib/shitty/render_metal.mm:404-408` — «byte for byte and copy for copy» сказано сильнее,
  чем есть.** Новое сравнение требует ещё и совпадения указателя `Screen`, поэтому кадр,
  у которого сменился терминал при том же номере поколения, перезальёт арену там, где старый
  код этого не делал. Расхождение в безопасную сторону (лишняя заливка, а не чужие глифы), но
  равенством оно не является.

- **`lib/shitty/render_metal.mm:891` и `:637-677` — панель получает сетку размером с окно.**
  `cells.zero(cellCount * count)` и `buildCellUpdates()` отводят каждой панели полную сетку окна
  и полный список обновлений, независимо от того, какую долю окна панель занимает. Отчёт это
  вскользь отмечает в замерах («половина её сетки уходит за клип»), но в перечень того,
  что осталось за рамками, не вынесено. Для `T9` это прямой пункт работы: пока панель не знает
  своих `columns`/`rows`, кадр из N панелей стоит N окон.

- **`lib/shitty/render_metal.mm:771` — панель без обновлений не диспатчится вовсе**
  (`if (pane.updateCount == 0) continue;`), и её прямоугольник остаётся закрашенным фоном
  **первой** панели, который положил проход очистки. Сегодня недостижимо (панель одна),
  но в паре с уже названным долгом «очистка Metal не по прямоугольникам» это второй способ
  получить чужой цвет в чужой панели. Стоит записать рядом с первым.

- **Борд: «802 OK с хелпером»** — у меня 804. См. «Уточнение по базису».

## Побайтовость: чем именно она доказана

Это единственный критерий, который нельзя принять по тестам, потому что тесты проверяют
ожидания, а вопрос был про байты.

**Скомпилированный шейдер.** Достал из обоих бинарников `st` строку исходника MSL
(от `#include <metal_stdlib>` до нуля) и сравнил:

```
/tmp/r6qa/.build/st      len=49974 sha256=24f16a6802de3587…
/tmp/r6qabase/.build/st  len=49974 sha256=24f16a6802de3587…
```

Одинаковы побайтово. То есть коммит `58e93f89` действительно изменил только комментарии
`render.comp`, и **программа, которую исполняет GPU, после `T8` та же самая**. Раскладка
push-констант тоже не поехала: `static_assert(sizeof(PushConstants) == 116)` стоит и в
`render_metal.mm:128`, и в `render_vk.cpp:178`, оба зелёные.

**Эталонный рендерер.** Написал один и тот же временный тест в оба дерева: сетка 12×5,
`border = 3`, верхний резерв 5 (то есть инсеты не совпадают по осям — иначе перепутанные
оси не видны), 60 клеток с разными цветами фона и текста, bold и italic, буквы алфавита;
после рендера — FNV-1a по всем пикселям.

```
после (8490b1df): R6QA-IMAGE-HASH 126x121 bytes=45738 fnv1a=e9c703f2389655ef
база (650da24f):  R6QA-IMAGE-HASH 126x121 bytes=45738 fnv1a=e9c703f2389655ef
```

**Положительный контроль оракула:** сдвинул синий канал фона на единицу — хеш стал
`750da6907e0b50f0`. То есть оракул не «всегда одинаков», он чувствителен к одному биту цвета.

`MTL_SHADER_VALIDATION=1` — ни одной жалобы валидаторов.

## Замеры: продуктовый путь

Нагрузка: `cat` файла 100 МБ ASCII восемь раз (800 МБ) внутри собственного окна `st`,
`-geometry 80x24`; калибровка до 80×24 на этом дисплее не доходит — окно выходит 724×436 px,
что само по себе объясняет расхождение абсолютных чисел с отчётом.

**Первый прибор — стенное время процесса — слеп, и это я подтверждаю независимо.** Одна
и та же сборка, одна и та же нагрузка: 14.48, 14.70, 14.88, 15.24, 15.81, 15.84, 16.06, 16.11,
16.11, 18.38, 18.71, 20.58, 33.99, 39.44 с. Разброс превышает 100% при том, что различие,
которое ищут, — единицы процентов. База даёт 14.95 / 16.36 / 16.32 с, после — медиана около
16.1 с; две панели — 15.84 … 18.71 с. Прибор действительно не увидел бы и двукратного
подорожания рендера, ровно как написал исполнитель.

**Второй прибор — кадр на CPU — регрессии не показывает** (таблица в находке В2): база
3394-3449 мкс, после 3369-3468 мкс. **Третий, узкий — `uploadArenas` — тоже:** 23.7-24.3 мкс
до, 23.7-25.7 мкс после, и он же честно краснеет вдвое на искалеченном зеркале.

Вывод по замерам: **регрессии на одной панели нет**, подтверждено двумя независимыми приборами
на двух деревьях; точка остановки плана не наступила. Возражение — не к числам, а к тому,
как в отчёте описана чувствительность (находка В2).

## Качество нового модуля зеркала арен

`render_arena.h` `T9` и `T10` возьмут как готовый кирпич, поэтому смотрел отдельно. Модуль
хороший: 128 строк, без состояния сверх необходимого, без аллокаций в кадре (`planned`
и `ranges` меняются местами через `xchg`), инвариант «поколение имеет смысл только рядом
с панелью» записан и в шапке, и в коде, и в тестах. Сравнение по трём полям сразу
(панель, поколение, база) — то, что нужно; поиск линейный и это оговорено.

Разобранные краевые случаи ведут себя корректно:

- панель ужалась без смены поколения — `uploaded` зажимается, копия пуста, `used()` обновляется
  (тест `ClampsTheTailToAShrunkPane`);
- одна панель дважды в кадре (один `Screen`, два прямоугольника) — базы разные, совпадения нет,
  каждая получает своё; проверено на живом кадре, трасса выше;
- панель ушла из кадра и вернулась — приходит целиком (`ForgetsAPaneThatLeftTheFrame`).

Претензии две, обе выше: контракт `reset()` вызывающий не соблюдает (В1), и один из десяти
тестов пустой (M-A). Плюс мелочь стиля: `used_` — публичное поле с подчёркиванием рядом
с публичным аксессором `used()` и публичными `ranges`/`planned` без подчёркивания; либо
всё приватное, либо подчёркивание лишнее.
