# QA-отчёт: window-chrome, финальный круг 4 (R3-qa-final, round 4)

**Дата:** 2026-08-17
**Область:** только поверхности F6 — гейт `if (quick && !window.visible) { return; }`
в `WindowImpl::requestRestore()` и `WindowImpl::requestFullscreen()`.
**Проверяемый коммит:** `1c8cfa5c`. Живая часть прогнана бинарём, собранным в
**изолированном worktree** на этом коммите (рабочее дерево не участвовало).
**Вердикт:** **готово**

## Резюме

F6 делает заявленное. `CSI 1 t` и `CSI 10;1 t` из потока данных не выводят
скрытое quick-окно; легитимный путь не задет — `CSI 1 t` на показанном
хоткеем окне оставляет геометрию и уровень нетронутыми; `quick = false` не
затронут, там `CSI 1 t` и `CSI 10;1 t` работают как раньше.

Два уточнения по существу, которых не было в отчёте исполнителя:

1. **Гейт в `requestFullscreen()` — дублирующая страховка, а не барьер.**
   Проверено диагностической сборкой с **отключённым** гейтом: скрытое
   quick-окно по `CSI 10;1 t` всё равно не появляется и не разворачивается.
   Довод R3-sec про отсутствие `FullScreenPrimary` подтверждён
   экспериментально. Это меняет оценку прочности — см. ниже.
2. **Соседние негейтированные операции проверены наблюдаемо** (`CSI 9;1 t`
   maximize, `CSI 3 t` move): скрытое окно не показывают. Вывод R3-sec, что
   их гейтировать не нужно, подтверждается не только чтением кода.

## Контроли доставки — без них замеры ничего не значат

«Окон 0 до и после» — сам по себе бессмысленный результат: он одинаков и когда
гейт работает, и когда escape вообще не дошёл до кода. Поэтому сначала два
контроля, что поток данных доходит до `VtermImpl::windowOperation` в этих
самых конфигурациях:

| Контроль | Результат |
|---|---|
| `quick = false`, окно **свёрнуто** (`AXMinimized = true`), затем `CSI 1 t` из потока | `AXMinimized` → **false** — окно развернулось, значит `CSI 1 t` доходит и `requestRestore()` работает |
| `quick = true`, окно показано хоткеем, затем `CSI 3;100;100 t` из потока | окно сдвинулось с `@0,33` на **`@100,583`** — значит escape-поток доходит и в quick-конфигурации |
| `quick = false`, `CSI 10;1 t` из потока | окно **ушло в фуллскрин** (`1728x1084@0,33` + системный слой `layer=26`) — значит `CSI 10;1 t` парсится и доходит до `requestFullscreen()` |

Только после этого нули ниже читаются как работа гейта.

## 1. `CSI 1 t` на скрытом quick-окне

`quick = true`, `allowWindowOps = true`, escape печатает сам дочерний шелл
(`-e /bin/sh -c "sleep 12; printf '\033[1t'; sleep 25"`) — то есть приходит
**из потока данных терминала**:

| Момент | Окон (AX) | CoreGraphics |
|---|---|---|
| до escape | 0 | пусто |
| после escape | 0 | пусто |
| +4 с | 0 | пусто |

## 2. `CSI 10;1 t` на скрытом quick-окне

| Момент | Окон (AX) | `AXFullScreen` | CoreGraphics |
|---|---|---|---|
| до escape | 0 | — | пусто |
| после escape | **0** | — | пусто |
| +4 с | 0 | — | пусто |

Не появилось и не развернулось.

### Чем именно это держится — гейтом или AppKit

Лид просил различить. Различил, и ответ — **AppKit, а не гейт**:

- Собрал диагностический вариант того же коммита с условием гейта,
  превращённым в тождественно ложное (`if (false && quick && !window.visible)`)
  **только в `requestFullscreen()`**. Скрытое quick-окно по `CSI 10;1 t`
  по-прежнему не появилось и не развернулось — 0 окон.
- Согласуется с поведением **показанного** quick-окна: оно проходит гейт
  беспрепятственно (`window.visible` истинно), и всё равно `CSI 10;1 t`
  оставляет `AXFullScreen = false` и ту же геометрию `1728x434@0,33`.
- Причина — `collectionBehavior` quick-окна (`CanJoinAllSpaces |
  FullScreenAuxiliary`, `platform_cocoa.mm:1179`) не содержит
  `NSWindowCollectionBehaviorFullScreenPrimary`, без которого
  `toggleFullScreen:` — no-op. Контроль на `quick = false`, где фуллскрин
  срабатывает, показывает, что дело именно в свойстве окна, а не в escape.

**Как это читать.** Гейт в `requestFullscreen()` сегодня ничего не
предотвращает — он дублирует ограничение AppKit. Это не повод его убирать:
он становится единственным барьером в тот день, когда кто-нибудь добавит
quick-окну `FullScreenPrimary` (например, чтобы фуллскрин по хоткею заработал),
и тогда защита не развалится молча. Но в оценке прочности S3-r его считать
нельзя: **защита от фуллскрина держится на `collectionBehavior`**, и если это
свойство когда-нибудь изменится, проверять надо будет заново.

Гейт в `requestRestore()`, в отличие от этого, несёт реальную нагрузку:
контроль выше показывает, что `requestRestore()` на обычном окне работает
(деминимизирует), значит на quick-окне его останавливает именно гейт.

## 3. Легитимный путь не задет — главное

`CSI 1 t` на окне, показанном хоткеем:

```
t=5  before esc: ax=1 fs=false layer=25 bounds=1728x434@0,33
t=14 after esc:  ax=1 fs=false layer=25 bounds=1728x434@0,33
t=18 settled:    ax=1 fs=false layer=25 bounds=1728x434@0,33
```

Геометрия и уровень идентичны до и после, окно не спряталось и не сдвинулось,
процесс жив. То же для `CSI 10;1 t` на показанном окне — без изменений.

## 4. `quick = false` не задет

| Escape | Результат |
|---|---|
| `CSI 1 t` (окно не свёрнуто) | без изменений, `layer=0 bounds=854x1073@869,39` |
| `CSI 1 t` (окно свёрнуто) | разворачивается, `AXMinimized` → `false` |
| `CSI 10;1 t` | уходит в фуллскрин: `1728x1084@0,33`, системный слой `layer=26` |

Штатное поведение обычного окна сохранено полностью — гейт под
`if (quick && ...)` для него никогда не истинен.

## 5. Соседние операции, которые F6 сознательно не гейтит

Проверены наблюдаемо на скрытом quick-окне (тот же метод, escape из потока
данных):

| Escape | Операция | Окон после |
|---|---|---|
| `CSI 9;1 t` | `requestMaximized(true)` → `[window zoom:]` | 0 |
| `CSI 3;100;100 t` | `requestMove()` → `setFrameOrigin:` | 0 |

Ни одна не выводит скрытое окно на экран — решение R3-sec не гейтить их
подтверждается замером, а не только чтением кода.

## Находки

Блокирующих нет. Важных нет.

### Замечания

- **Оценка прочности защиты от фуллскрина в отчёте F6 завышена.** Гейт в
  `requestFullscreen()` сегодня дублирует ограничение AppKit и сам ничего не
  предотвращает (разбор выше). Формулировка «закрыто гейтом» верна по
  результату, но неверна по механизму; если это попадёт в итоговый отчёт как
  «закрыли гейтом», следующий разработчик может снять
  `FullScreenAuxiliary`-ограничение, считая, что гейт его прикрывает — а
  прикрывать он начнёт только с этого момента и только при неизменном коде.
- **Поток данных по-прежнему может двигать показанное quick-окно.**
  `CSI 3;100;100 t` уводит его с положенного места (`@0,33` → `@100,583`) — то
  есть окно, которое человек вызвал хоткеем, программа в терминале может
  переставить куда угодно. Это заявленное и оговорённое в комментариях
  поведение (`CSI 3 t` двигает, но не показывает), `allowWindowOps` по
  умолчанию выключен — фиксирую как известный остаток, не как находку.
  Следующий показ по хоткею ставит геометрию заново, так что состояние
  самовосстанавливается.
- Методическое, в силе с круга 3: `./build test -k` собирает из **рабочего
  дерева**, поэтому при параллельной работе измерения надо привязывать к
  коммиту через worktree — как сделано здесь.

## Ручные проверки для человека — окончательный список

Восемь пунктов из `window-chrome-R3-qa-final-round2.md` остаются в силе без
изменений, плюс девятый — поверхности F6:

9. **Оконные операции из потока данных не должны выводить скрытое окно.**
   `printf 'quick = true\nallowWindowOps = true\n' > /tmp/q3.toml`,
   `./.build/st -config /tmp/q3.toml`, спрятать окно (или не показывать
   вовсе), затем из **другого** терминала не получится — escape должен уйти
   именно в этот терминал, поэтому проще запустить его так:
   `./.build/st -config /tmp/q3.toml -e /bin/sh -c "sleep 10; printf '\033[1t'; printf '\033[10;1t'; sleep 30"`.
   Окно за эти 30 секунд не должно появиться ни разу и не должно развернуться
   в фуллскрин. Затем показать его хоткеем и убедиться, что оно на месте
   вверху экрана и работает.

Для полноты картины при проверке пункта 5 (поверх фуллскрина) правило то же,
что записано в круге 3: всплывшее **поверх содержимого** чужого фуллскрина
окно **обычного** уровня — остаточный риск S3-r, поднимать до важной находки;
всплытие по хоткею — штатная работа фичи.
