## Находки

### Блокирующие

#### B4. Кадр восстанавливается в единицах чужого дисплея и затирает сохранённое состояние

`lib/shitty/ui_quick_hotkey.mm:269-330` (`applyQuickFrameToWindow()`),
`lib/shitty/application.cpp:663-673` (`toggleQuickWindow()`)

**Что не так.** `toggleQuickWindow()` сначала зовёт
`requestShowAt(ShowPlacement::TopOfActiveScreen)`, а тот резолвит «активный экран» как
**экран под курсором** (`WindowImpl::topOfActiveScreenFrame()` →
`screenUnderPointer()`, `ext/plt/platform_cocoa.mm:1409-1425`). Сразу после этого
`applySavedQuickFrame()` зовёт `applyQuickFrameToWindow()`, который берёт масштаб и границы
клэмпа из `window.backingScaleFactor` и `window.screen` — то есть из экрана, **куда окно
только что положили**, а не из того, на котором кадр сохранялся. Файл состояния
(`lib/shitty/quick_frame_store.h`) не хранит никакой привязки к экрану, и хранит размер в
backing pixels — величине, которая на разных дисплеях означает разное число точек.

**Доказательство.** Курсор переносился между дисплеями программно, показ каждый раз
происходил по маркер-файлу:

```
1 ручной кадр на Retina:        CG 1300,1400 1000×500
2 скрыто, файл:                 x=1300 y=-820 width=2000 height=936
   (курсор переведён на внешний экран)
3 показ:                        CG 1300,112 1044×492      ← окно на ДРУГОМ мониторе
4 скрыто, файл:                 x=1300 y=476 width=1044 height=460   ← исходный кадр стёрт
   (курсор переведён обратно на Retina)
5 показ:                        CG 1300,1113 992×492
```

Инструментальный лог из той же функции — обе развилки видны:

```
QA: saved=(1300,-820,2000,936) screenNil=0 screen=(0,0,3840,1050)    scale=1.0
    target=(1300,0,2000,968)  got=(1300,0,2000,968)
QA: saved=(1300,476,1044,460) screenNil=0 screen=(1015,-1117,1728,1084) scale=2.0
    target=(1300,-295,522,262) got=(1300,-295,522,262)
```

Первая строка: `2000×936` backing pixels Retina-экрана прочитаны при `scale = 1.0` как
`2000×936` **точек** — вдвое больше задуманного; `y = −820` (координата на встроенном экране)
клэмпнута в `0`, то есть в чужой экран. Вторая строка, после того как испорченное значение
попало в файл: `1044×460` прочитаны при `scale = 2.0` как `522×262` точки — вдвое меньше.
**Каждая смена дисплея умножает или делит кадр вдвое**, и каждое скрытие закрепляет результат
на диске.

**Чем грозит.** Дословный провал критерия `T3` «подвинуть и растянуть окно, спрятать,
показать — позиция и размер сохранились» на конфигурации «ноутбук + внешний монитор», то есть
на машине пользователя. Хуже того, это **порча данных**: пользовательская расстановка не
приближается, а теряется, и единственный выход — удалить файл состояния (способ,
задокументированный `F2b` в обоих `.toml`). При одном дисплее — и при двух, если курсор не
переезжает между показами — дефекта нет: замеры выше это подтверждают на обоих масштабах.

**Про статус «это уже отложено».** Решение `A6` и комментарий, который `F2` убрала из
`applySavedQuickFrame()`, действительно называли многомониторный случай открытым вопросом
и «best-effort: exact for a single/primary screen, approximate for a frame saved on a
secondary display». Но «approximate» описывает неточность, а замерено — удвоение с
последующим стиранием исходного значения. Новый комментарий в `ui_quick_hotkey.h:66-70`
формулирует поведение как «clamping into whichever screen the window is currently on», что
верно буквально и вводит в заблуждение по сути: «currently on» — это экран под курсором, а
не экран кадра. **Решение о том, блокер это для волны или отложенный пункт, за командиром;
приёмка обязана назвать это блокером, потому что это потеря пользовательских данных в
критерии приёмки.**

**Предлагается** (минимальный набор, каждый пункт самостоятельно уменьшает вред):

1. **Хранить размер в точках, а не в backing pixels.** Точки не зависят от дисплея, и вся
   арифметика единиц исчезает вместе с проблемой. Формат файла — `key=value`, миграция
   тривиальна (или просто новое поколение имён ключей).
2. **Выбирать экран по сохранённому кадру, а не по курсору:** найти в `NSScreen.screens`
   тот, чей `frame` содержит сохранённый origin, и клэмпить в него; `window.screen` в этот
   момент отвечает про экран, куда окно только что положил `requestShowAt`.
3. **Не записывать обратно кадр, который эта же функция только что подрезала.** Тогда даже
   при промахе с экраном пользовательская расстановка выживает, а не деградирует.

Пункт 3 стоит сделать даже если 1 и 2 отложат: он превращает блокер в косметику.

#### B5. Незащищённый бридж-каст в `ui_csd_tabs.mm` — падение воспроизведено

`lib/shitty/ui_csd_tabs.mm:138-143`

Отдельное поручение круга. Полный обход дерева
(`grep -rn "renderContext()"` по `lib/`, `ext/`, исключая `.build`) даёт четыре места, где
`renderContext().window` кастуется к `NSWindow*`. Три — в `ui_quick_hotkey.mm` (строки 101,
207, 273) — после `F2` проверяют `context.backend != plt::RenderBackend::Cocoa` **до** каста.
Четвёртое — нет:

```cpp
NSWindow* CsdTabsUi::nativeWindow() const {
    if (composer.window == nullptr) {
        return nil;
    }
    return (__bridge NSWindow*)(composer.window->renderContext().window);
}
```

`WindowHeadlessImpl::renderContext()` (`ext/plt/platform_headless.cpp:393-399`) отдаёт
`.window = &target_` — **не** `nullptr`, поэтому оба вызывающих
(`CsdTabsUi::apply()`, `:181`, и `CsdTabsUi::applyTitlebarColor()`, `:236`), проверяющие
только `window == nil`, проходят проверку и посылают сообщение не-объекту.

**Доказательство.** Временный тест в `lib/shitty/application_ut.cpp` (дерево `72bc6bcf`):
headless-платформа, окно, `Options::transparentTitlebar = true`, `createCsdTabsUi()`. Прогон
`unit_tests` завершился **кодом 139 (SIGSEGV)**, оборвавшись сразу после
`Config::RejectsBrokenReloadWithoutPublishingIt` — то есть на следующей по алфавиту сюите,
пробной. Тест удалён, дерево чисто, `unit_tests` снова 688 OK / 3 ERR.

**Чем грозит.** Сегодня недостижимо: `createCsdTabsUi()` зовётся единственным местом
(`application.cpp:764`) под `#if defined(__APPLE__)`, где платформа всегда Cocoa, а файл
собирается только на darwin (`build.py:660-666`). Но `T5` (боковая панель) и `T6`
(автоскрытие оформления) на волне 4 владеют этим файлом и захотят headless-тесты — они
получат ровно ту мину, на которой `F2` уронила свои. Класс дефекта уже подтверждён дважды
на одной волне.

**Предлагается.** Перенести проверку в саму `nativeWindow()` — единственную точку каста в
файле: вернуть `nil`, если `renderContext().backend != plt::RenderBackend::Cocoa`. Оба
вызывающих уже корректно обрабатывают `nil`, менять их не нужно. Это две строки и закрывает
всю поверхность файла на будущее. Заодно стоит записать это правило рядом с правилом
«контракт против эскейп-хэтча», которое `F2` внесла в `renderContext()` (`c0e38a20`): там
сказано, **когда** тянуться через эскейп-хэтч, но не сказано, что перед кастом обязательна
проверка тега бэкенда, — а это ровно то, что оба раза забыли.

### Важные

#### I8. Продакшен-путь `B1` не покрыт ни одним тестом

После `F2` клэмп существует **в двух независимых реализациях**: `clampQuickFrame()`
(`application.cpp:591-607`, чистая, портируемая) и внутри `applyQuickFrameToWindow()`
(`ui_quick_hotkey.mm:296-320`, Cocoa). На macOS исполняется вторая — первая недостижима, она
запасная для не-Cocoa бэкендов. Оба новых теста `F2` и все три моих мутации бьют по
**первой**. То есть регрессионное покрытие `B1`, которое круг 1 требовал именно чтобы фикс
удержался, стоит не на том пути, который работает у пользователя.

Это не придирка: `B4` живёт как раз во второй реализации и никаким тестом не ловится. Мои
живые замеры на `scale = 2` показали, что арифметика второй реализации верна, но это ручной
прогон, который не переживёт следующую правку.

**Предлагается.** Вынести из `applyQuickFrameToWindow()` чистую функцию, считающую целевую
рамку из `(QuickFrame, visibleFrame, scale, titlebarHeight)` — без `NSWindow` — и покрыть
её тестами напрямую, включая кросс-масштабный случай. Тогда `clampQuickFrame()` либо
исчезает как дубль, либо становится её вырожденным вызовом.

#### I9. Комментарий `applyQuickFrameToWindow()` описывает не то, что делает код

`lib/shitty/ui_quick_hotkey.h:62-70`

«clamping into whichever screen the window is currently on» — читатель поймёт «в тот экран,
где окно стоит», а фактически это экран, **куда его только что положил `requestShowAt` по
положению курсора**, и именно из этого расхождения растёт `B4`. Круг 1 отдельно отмечал, что
врущий комментарий опаснее отсутствующего. Заодно из заголовка исчезло предупреждение,
которое было в прежнем комментарии `applySavedQuickFrame()` — про то, что клэмп
приблизителен для кадра со вторичного дисплея (открытый вопрос `A6`). Единственное
предупреждение об этом на весь путь пропало вместе с переписанной функцией.

#### I10. Живой прогон quick-окна нечем воспроизвести без правки кода

`dev/quick_window_probe.sh`

Скрипт `F2` — правильная работа, и его геометрическая часть незаменима. Но его способ
**драйва** (синтетические чорды) не сработал ни у `F2`, ни у меня: 0 из 22 при всех выданных
разрешениях. То, что сработало — маркер-файл плюс `SIGUSR1` — требует временной правки
`configuration.cpp`, и каждая следующая волна будет изобретать её заново.

**Предлагается** (решение командира, это изменение продукта, а не тестов): небольшая
отладочная точка входа, которую видно только под флагом сборки `SHITTY_FOR_TESTS` — тем же,
под которым уже живёт `takeTestFd()` (`application.cpp:714-716`). Тогда `st_test` умеет
переключать quick-окно по сигналу, живой прогон становится однострочником, и волны 4-8
экономят дни. Альтернатива дешевле: дописать рецепт с маркер-файлом в комментарий
`dev/quick_window_probe.sh` как известный обходной путь.

Заодно в том же комментарии стоит поправить две вещи, проверенные здесь:
`qwp_move`/`qwp_resize` **работают** — `kAXWindowsAttribute` пуст только пока окно скрыто;
и добавить проверку `pgrep -fl "Shitty.app"` перед прогоном, потому что продакшен-инстанс
пользователя забирает чорд себе.

### Замечания

- **`Z1`.** Строка про сброс кадра в `bin/st/shitty.toml:109-111` и
  `bin/pt/pretty.toml:109-111` называет имя файла жёстко (`shitty-quick-frame`), тогда как
  `defaultQuickFramePath()` (`lib/shitty/quick_frame_store.cpp:44`) выводит его из
  **фактического** пути конфига: при `-config myconf.toml` файл будет `myconf-quick-frame`.
  Для дефолтного конфига текст верен, для `-config` — вводит в заблуждение. Проверено живьём:
  конфиг `…/shitty.toml` дал `…/shitty-quick-frame`.
- **`Z2`.** `applyQuickFrameToWindow()` клэмпит размер **контента** по высоте видимой
  области, а рамку строит как контент плюс титлбар — значит рамка на 32 pt выше видимой
  области, `maxY` уходит в `visible.origin.y`, и окно встаёт нижним краем к нижней границе,
  торча титлбаром над верхней. Косметика на границе, самоустраняется на следующем цикле
  (точка становится устойчивой), но клэмпить стоило бы рамку, а не контент.
- **`Z3`.** Живая перезагрузка конфига (`SIGUSR1`), меняющая `quickCornerRadius` с
  положительного на `0`, оставляет окно в противоречивом состоянии: радиус слоя никто не
  переприменяет (`requestCornerRadius()` зовётся только из конструктора окна и из
  фуллскрин-чорда), а `CsdTabsUi::applyTitlebarColor()` после правки `F2b` снова начнёт
  писать непрозрачный фон — то есть «квадратные уши» вернутся до перезапуска. Узкий край,
  но условие пропуска в `F2b` читает `opts` на каждом вызове, а условие прозрачности
  вычисляется один раз при создании окна: две развилки на разных срезах времени.

## F2b — взята в область, принимается

Замеры `B1`/`B2`/`B3`/`B4` делались на `c0e38a20`, `ui_csd_tabs.mm` и `.toml` в них не

**Вывод исполнителя про `I7` перепроверен независимо, а не повтором его измерения.** Его
довод держится на одном замере `backgroundColor.alphaComponent == 0` в одной точке кода;
проверяемо строже и без измерения вообще, потому что порядок здесь полностью детерминирован:

1. Прозрачность окна ставится ровно при `radius > 0 && window.opaque`

2. Условие пропуска в `applyTitlebarColor()` — `!(composer.opts->quick &&
   composer.opts->quickCornerRadius > 0)` — совпадает с этим набором **буква в букву**.
3. `createCsdTabsUi()` идёт после `createWindow()` (`application.cpp:764` против `:741`),
   то есть был вторым и последним писателем; теперь при обеих опциях он не пишет вовсе.

Следовательно единственный писатель `window.backgroundColor` в этой конфигурации —
`requestCornerRadius()`, и значение — `clearColor`. Правило «у свойства один владелец»
выполнено не по очерёдности, а по конструкции. Замечание `Z3` — единственная щель, и она
про живую перезагрузку, а не про запуск.

`I5` закрыт: строка про сброс есть в обоих конфигах, формат `# CLI:` не тронут, добавленные
строки — чистый ASCII (em dash в них не требуется и не появился). Неточность про имя файла —

для волны или отложенный пункт.

**8. Один дисплей — контрольная проверка, что всё в порядке.**
Тот же конфиг, но не переводя курсор между экранами (или отключив второй монитор). Показать,
перетащить, растянуть, дальше 5-6 раз `ctrl+~` туда-обратно. **Смотреть:** окно должно
возвращаться ровно туда же, без сползания вниз. Приёмка намерила шесть циклов без сдвига и на
внешнем, и на встроенном экране — этот пункт для подтверждения глазами, если результат
покажется спорным.

**9. Два процесса на один файл состояния (`quickCompanion`).**
```
printf 'quick = true\nquickHotkey = "ctrl+grave"\nquickRememberFrame = true\n' > /tmp/w2cfg/quick.toml
printf 'quickCompanion = "/tmp/w2cfg/quick.toml"\nquickRememberFrame = true\n' > /tmp/w2cfg/main.toml
/tmp/w2c/.build/st -config /tmp/w2cfg/main.toml
```
Подвигать quick-окно, поскрывать и показать. **Смотреть:** должны появиться **два** файла
(`main-quick-frame` и `quick-quick-frame`) и процессы не должны мешать друг другу. По коду
пути расходятся (каждый берёт свой `configPath`), то есть гонки, ради которой в имя
временного файла кладётся pid, быть не должно вовсе — но это стоит увидеть. Приёмка этот
пункт не закрывала ни в одном круге.

## Рекомендации

1. **`F3`: `B4`** — как минимум пункт 3 из предложенного (не записывать обратно кадр, который
   этот же код подрезал): он превращает потерю данных в косметику одной правкой. Полное
   лечение — хранить размер в точках и выбирать экран по сохранённому кадру.
2. **`F3`: `B5`** — проверка `backend == Cocoa` внутри `CsdTabsUi::nativeWindow()`, две
   строки. Сделать **до** волны 4, иначе `T5`/`T6` наступят на это же.
3. **`F3`: `I9`** — поправить комментарий `applyQuickFrameToWindow()` в
   `ui_quick_hotkey.h:62-70` и вернуть в него предупреждение про вторичный дисплей, которое
   исчезло вместе с прежним комментарием `applySavedQuickFrame()`.
4. **`R2-test` или `F3`: `I8`** — вынести расчёт целевой рамки в чистую функцию и покрыть
   её тестами, включая кросс-масштабный случай. Сейчас регрессионное покрытие `B1` стоит на
   пути, который на macOS не исполняется.
5. **Командиру: `I10`** — решить, заводить ли отладочный переключатель quick-окна под
   `SHITTY_FOR_TESTS`. Без него каждая волна, которой нужен живой прогон, будет патчить
   `configuration.cpp` заново. Дешёвая альтернатива — дописать рецепт с маркер-файлом и
   поправку про AX в комментарий `dev/quick_window_probe.sh`.
6. **Командиру: пункт 4 списка для человека** — прозрачный титлбар при обеих опциях это
   решение `F2b` о внешнем виде чужого проекта. Стоит спросить пользователя прямо, а не
   считать закрытым.
7. **Правило к правилу.** `F2` записала в `renderContext()`, **когда** законно тянуться
   через эскейп-хэтч. `B5` показывает, что не хватает второй половины: **перед бридж-кастом
   обязательна проверка тега бэкенда, а не проверка на `nullptr`** — потому что ни один
   бэкенд `nullptr` не отдаёт. Два падения на одной волне (`F2` на своих тестах, приёмка на
   пробном) — достаточное основание, чтобы это было написано, а не подразумевалось.

## Ограничения этого круга, зафиксированные честно

- **Визуальное не проверено и не помечено ни закрытым, ни проваленным:** скругление,
  мерцание, стык с титлбаром, цвет полосы. Screen Recording этому окружению не выдан,
  `CGWindowListCreateImage` в этой версии macOS удалён («unavailable, please use
  ScreenCaptureKit»), `kCGWindowIsOpaque` в словаре `CGWindowListCopyWindowInfo` отсутствует.
- **Синтетические чорды не работают в этой сессии** — 0 из 22 при всех выданных разрешениях,
  на голом бинаре и на .app-бандле, на четырёх комбинациях источника и тапа, и через
  `postToPid`. Живые прогоны сделаны другим способом (маркер-файл плюс `SIGUSR1`), то есть
  **сам путь доставки чорда через Carbon в этом круге не проверялся** — проверялась логика
  за ним. Разбор чорда покрыт юнит-тестами `quick_hotkey_chord`, доставка остаётся за
  пунктами списка для человека.
- **Wayland-реализация `setCornerRadius()` не проверена компилятором** ни исполнителями, ни
  двумя кругами приёмки — кросс-компиляция из песочницы недоступна. Считать непроверенной до
  первого Linux-прогона.
- **Внешний CG-пробник деградирует в длинных сериях** — в серии из 26 циклов одно чтение
  вернулось пустым. Такие строки не усреднялись; каждый набор чисел в отчёте снят в начале
  своей сессии замеров.
- **Пункт 9 списка для человека** (`quickCompanion`, два файла состояния) не проверялся ни в
  одном круге.
- Временные инструментальные правки (`configuration.cpp`, `ui_quick_hotkey.mm/.h`,
  `application_ut.cpp`) откатаны во всех трёх деревьях; `git status` чист, `unit_tests` после
  откатов 688 OK / 3 ERR.
