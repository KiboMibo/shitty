# Секьюрити-ревью волны 3, круг 3: гейт `requestFocus()` из F5

**Дата:** 2026-08-17
**Область:** узкая, только по трём вопросам круга. Коммит `41016858` (F5), диапазон
`git diff 84ec3eec..41016858 -- ext/plt/platform_cocoa.mm`; для ответов прочитаны `vterm.cpp:6463-6522`
(полный список операций из потока), `parser.cpp:2026` (гейт), `docs/reports/F5-window-chrome-2026-08-17.md`
**Предыдущие круги:** `window-chrome-R3-sec.md`, `window-chrome-R3-sec-round2.md` (не редактировались)
**Метод:** только чтение кода, живых замеров в этом круге не делал — GUI занят приёмкой
**Вердикт:** **S6 закрыта. S3-r закрыта для `CSI 5 t`, но не для всей поверхности:** две операции из того же
потока (`CSI 1 t`, `CSI 10 t`) идут не через `requestFocus()` и гейтом не покрыты. Блокирующих находок нет

## Резюме

Строка стоит правильно и делает то, что задумывалось: путь `CSI 5 t` больше не выводит скрытое quick-окно, а
пере-поднятие уже показанного человеком окна работает — оба вывода получаются прямо из кода, без замеров.
Формулировку комментария исполнитель поправил верно: и про слой 0 у фуллскрин-окна, и про то, что
`FullScreenAuxiliary` — это членство на Space, а не привилегия стекинга.

Но инвариант, на который опирается F5, сформулирован не там, где нужно. «Единственный вызывающий
`requestFocus()` — это `VtermImpl::windowOperation`» — верно и проверяемо, только защищать надо не
`requestFocus()`, а свойство «ни одна операция из потока не выводит скрытое quick-окно на экран». Операций из
потока восемь, и по крайней мере две из них — `CSI 1 t` → `requestRestore()` → `[window deminiaturize:nil]` и
`CSI 10 t` → `requestFullscreen()` → `[window toggleFullScreen:nil]` — вызываются на скрытом окне без всякого
гейта. Показывают ли они его фактически, я по коду сказать не могу: это поведение AppKit, а не наше. Отсюда
единственная находка круга — **S7**, замечание с условием повышения и с двумя дешёвыми проверками.

## Ответы на три вопроса

### 1. Достаточно ли проверки именно в `requestFocus()` — нет, поверхность шире

Полный список того, что достижимо из `VtermImpl::windowOperation` (`vterm.cpp:6477-6522`), и что каждая
операция делает **на скрытом quick-окне**:

| Из потока | Метод `plt` | Что делает со скрытым окном |
|---|---|---|
| `CSI 5 t` | `requestFocus` (`:1395`) | **закрыто F5** — ранний выход при `quick && !window.visible` |
| `CSI 1 t` | `requestRestore` (`:1376`) | `[window deminiaturize:nil]`, затем `toggleFullScreen:` только при выставленном бите `FullScreen` и `zoom:` только при `isZoomed`. **Гейта нет.** Выводит ли `deminiaturize:` окно, которое не свёрнуто, а именно `orderOut`-нуто, — вопрос к AppKit; см. S7 |
| `CSI 10;1 t` | `requestFullscreen` (`:1419`) | `[window toggleFullScreen:nil]` при отсутствии бита `FullScreen` — то есть **всегда** на скрытом quick-окне. **Гейта нет.** См. S7 |
| `CSI 9;1..3 t` | `requestMaximized` (`:1413`) | `zoom:` при `isZoomed != value`. Гейта нет; `zoom:` по смыслу меняет рамку, а не порядок вывода, но это тоже поведение AppKit. Слабый кандидат, там же в S7 |
| `CSI 2 t` | `requestIconify` (`:1386`) | `miniaturize:` — **no-op**, бит `Miniaturizable` снят в конструкторе (замерено в круге 1) |
| `CSI 3 t` | `requestMove` (`:1390`) | `setFrameOrigin:` — не показывает. На скрытом окне эффект не выживает: `requestShowAt` всё равно ставит `setFrame:topOfActiveScreenFrame()` (`:1313`). На **видимом** quick-окне позволяет сдвинуть его поверх меню-бара (уровень 25 против 24, замерено в круге 1) — это не изменилось ни в F4, ни в F5 и остаётся частью того, на что пользователь соглашается, включая `allowWindowOps` |
| `CSI 4 t` / `CSI 8 t` | `requestResize` (`:1426`) | `dispatch_async` + `setContentSize:` — не показывает. Меняет сетку скрытого окна (шелл получит `SIGWINCH`); заметно, но не привилегия |
| `CSI 7 t` | `requestFrame` (`:1326`) | только display link, видимость не трогает |

Всё это — под `allowWindowOps` (гейт на входе в диспетчер, `parser.cpp:2026`; по умолчанию выключено,
`options.cpp:120`). Отдельно проверил `requestAttention` (`:1372`), который дёргается из потока **без**
`allowWindowOps` (`vterm.cpp:6373,6415,6424`): это `[NSApp requestUserAttention:NSInformationalRequest]` —
подскок иконки в Dock, окно не выводит.

### 2. Легитимный путь не сломан

Гейт читает `window.visible` — то же самое, что отдаёт `visible()` (`:1481`), то есть ровно то состояние, на
которое опирается `toggleQuickWindow`. Разбор по состояниям:

- окно показано хоткеем → `visible == YES` → гейт пропускает, `CSI 5 t` пере-поднимает. **Работает.**
- окно скрыто (`requestHide`, в том числе hide-on-blur) → `visible == NO` → отказ. Это и есть цель.
- до первого показа → `visible == NO` → отказ. Корректно.
- деградированный режим из F3a (хоткей не заработал, окно показано обычным `requestShow()`,
  `application.cpp:508-517`) → `visible == YES` → пере-поднятие работает. Корректно: это обычное видимое окно.
- свёрнутое в Dock (гипотетически, бит снят) → `visible` у свёрнутого окна остаётся `YES` → гейт пропускает,
  `makeKeyAndOrderFront` разворачивает. Тупика нет.

Одно осознанное следствие, которое стоит знать: после Cmd-H (`[NSApp hide:]`) окна приложения ordered out,
`visible` становится `NO` — значит программа в шелле, отправляющая `CSI 5 t`, чтобы обратить на себя внимание,
скрытое приложение больше не поднимет. Это ровно то ограничение, которое мы и вводили, но это изменение
поведения по сравнению с обычным окном терминала.

### 3. Инвариант «скрыто ⇒ уровень нормальный» и путь Cmd-H — S6 закрыта

Закрыта, причём **сильнее, чем через инвариант уровня**. Логика такая: `[NSApp hide:]` выводит окна приложения
из показа, поэтому `window.visible` становится `NO`; гейт в `requestFocus()` при этом отказывает независимо от
того, какой у окна остался `level`. То есть щели, которую я описывал в S6 («скрыто через `hide:`, уровень остался
25, `CSI 5 t` поднимает со статус-уровнем»), для пути `CSI 5 t` больше не существует, и замерять `[NSApp hide:]`,
чего ни я, ни исполнитель не смогли, для этого вывода уже не требуется.

Остаточный «уровень 25 у скрытого окна» после Cmd-H, если он действительно остаётся, сам по себе привилегии не
даёт: вернуть окно на экран может либо человек (unhide приложения, хоткей), либо `requestShowAt`, который
уровень 25 и так выставляет. Ничего, чего у пользователя не было, из этого не получается.

Оговорка о доказательности: утверждение «у скрытого через `hide:` приложения `NSWindow.visible == NO`» я взял из
семантики AppKit (app-hide = ordered out), а не из замера — замерить `[NSApp hide:]` пробником не удалось и в
этом круге я к нему не возвращался. Если это окажется не так, S6 придётся открыть заново; проверка человеком —
пункт 3 ниже, она дешёвая.

## Находка

### S7. Гейт поставлен на один метод, а не на свойство: `CSI 1 t` и `CSI 10 t` работают со скрытым quick-окном без проверки

- **Серьёзность:** замечание — **с условием повышения до важной**, см. ниже
- **Где:** `ext/plt/platform_cocoa.mm:1376-1384` (`requestRestore`, гейта нет),
  `ext/plt/platform_cocoa.mm:1419-1424` (`requestFullscreen`, гейта нет),
  `ext/plt/platform_cocoa.mm:1413-1417` (`requestMaximized`, слабый кандидат),
  `vterm.cpp:6477-6506` (операции 1, 9, 10)
- **Кто может:** всё, что пишет в PTY, при `allowWindowOps = true` (по умолчанию выключено) — те же предпосылки,
  что у S3
- **В чём дело:** F5 закрыл `CSI 5 t`, и обоснование в комментарии (`:1396-1407`) верно ровно для него. Но
  свойство, которое нужно защищать, — «поток не выводит скрытое quick-окно на экран», а не «`requestFocus()`
  имеет одного вызывающего». Две другие операции из того же диспетчера трогают скрытое окно без проверки:
  - `CSI 1 t` → `[window deminiaturize:nil]`. Если AppKit на не-свёрнутом, но `orderOut`-нутом окне делает
    `orderFront`, поток выводит окно в обход гейта — и это тот же остаток S3-r (нормальный уровень плюс
    постоянное членство `CanJoinAllSpaces | FullScreenAuxiliary`).
  - `CSI 10;1 t` → `[window toggleFullScreen:nil]`, причём на скрытом quick-окне условие
    `current != value` выполняется всегда. Если бы это срабатывало, последствие хуже исходной S3: не полоса на
    40% высоты, а весь экран с содержимым, которое определяет поток. **Есть весомый довод, что AppKit это
    отклонит:** конструктор выставляет `collectionBehavior` в `CanJoinAllSpaces | FullScreenAuxiliary`
    (`:1190`), то есть **без** `FullScreenPrimary`, а `toggleFullScreen:` адресован именно primary-окну.
    Довод сильный, но это семантика AppKit, а не наш код, и проверяется одним замером.
- **Чем это меньше, чем звучит:** обе операции требуют `allowWindowOps`; hide-on-blur по-прежнему не даёт
  окну висеть поверх чужого диалога; уровень при этом остаётся нормальным (`requestHide` его сбросил), так что
  превосходства над меню-баром и чужими панелями нет.
- **Условие повышения:** если проверка покажет, что `CSI 1 t` выводит скрытое окно — поднять до важной
  (это возврат S3-r в полном объёме, только через другую операцию). Если сработает `CSI 10 t` — важная
  безусловно, тут последствие сильнее исходной находки.
- **Как чинить:** не добавлять по гейту в каждый метод, а поставить инвариант в одном месте. Дешевле и понятнее
  — в `VtermImpl::windowOperation`: при `composer.opts->quick` игнорировать операции, которые могут вывести
  окно (`1`, `5`, `10`; по вкусу `9`), оставив запросы геометрии и `requestFrame`. Это одно место, читаемое
  правило и без правок в вендорном слое — то же соображение, по которому модуль хоткея вынесли из `ext/plt`.
  Альтернатива — тот же ранний выход `if (quick && !window.visible) { return; }` в `requestRestore`,
  `requestFullscreen` и `requestMaximized`; работает, но инвариант остаётся размазан по четырём методам, и
  следующая операция, добавленная в `windowOperation`, снова его нарушит.
- **Как проверить:** `quick = true`, `allowWindowOps = true`, окно скрыто → `printf '\e[1t'` и отдельно
  `printf '\e[10;1t'` не выводят окно на экран; окно, показанное хоткеем, после `printf '\e[1t'` остаётся на
  экране (регрессии быть не должно).

## Про формулировку комментария

Проверил по существу, а не на «стало другим»:

- «фуллскрин-окно приложения само сидит на обычном уровне 0 (measured live)» — верно, это мой замер из круга 2
  (`layer=0`, четыре прогона).
- «`FullScreenAuxiliary` — про членство на Space, а не про порядок стекинга», «поднятый уровень нужен, чтобы
  расчистить собственную статус-обвязку фуллскрин-приложения и меню-бар, а не его контент» — верно, это ровно
  то различение, которого не хватало в версии F4.
- Ссылка на прошлую неверную версию («an earlier version of this comment claimed the opposite — wrong») — по
  делу, полезна для истории.
- **Одна неточность:** в комментарии конструктора (`:1188-1189`, «which closes that path rather than relying on
  level alone») и в `requestShowAt` (`:1299`, «closed in F5») это сказано безоговорочно. По разбору выше это верно для `CSI 5 t`, но не для всей поверхности из
  потока. Предлагаю сузить формулировку до «closed for CSI 5t» и, если S7 будет закрываться, обновить.

## Требует человека

Две проверки, обе быстрые и обе без фуллскрина. Условия для всех: `quick = true`, `allowWindowOps = true`,
окно скрыто (не показано хоткеем).

1. **`CSI 1 t` (главное, S7).** `printf '\e[1t'` в шелле терминала. Что записать: появилось ли окно на экране.
   Появилось → S7 важная, чинить до мержа. Не появилось → S7 остаётся замечанием и закрывается формулировкой.
2. **`CSI 10;1 t` (S7).** `printf '\e[10;1t'`. Что записать: появилось ли окно и не развернулось ли оно
   в фуллскрин. Ожидание по коду — отклонено из-за отсутствия `FullScreenPrimary`; если развернулось, это
   важная находка.
3. **Cmd-H (подтверждение S6, дешёвое).** Показать окно хоткеем, нажать Cmd-H, затем `printf '\e[5t'` — окно
   не должно появиться. Это подтверждает предпосылку «после `hide:` `visible == NO`», на которой держится мой
   вывод по вопросу 3.
4. **Регрессия легитимного пути** (её и так закрывает приёмка): окно, показанное хоткеем, после `printf '\e[5t'`
   остаётся на экране.
