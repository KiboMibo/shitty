# `T5.1` — решение: origin и четырёхсторонние инсеты в `VtGeometry`

**Дата:** 2026-09-04 · **Задача:** `T5.1`, волна 6 плана
`docs/plans/2026-08-29-upstream-merge.md` · **Ветка:** `arch/T5.1-vtgeometry`
(от `master`, `eb016aec` — дерево после `M6b`) · **Роль:** архитектурное
решение, кода нет · **Статус:** ждёт утверждения владельца форка.

Вход: `docs/plans/reviews/upstream-merge-invariants.md` §4 (варианты «А» и «Б»),
чек-лист `T0.3` §4.2, инварианты `A1`/`A8`/`A9`/`A10`, отчёты `M6` и `M6b`.
Всё, что ниже помечено ссылкой `файл:строка` или выводом команды, проверено на
этом дереве; всё, что не проверено, вынесено в раздел 10.

## 1. Решение в одном абзаце

**Рекомендую вариант «А»: заменить апстримный скаляр `borderPixels`
четырёхсторонними инсетами и добавить `originX`/`originY` прямо в `VtGeometry`,
а нашу собственную структуру `PaneGeometry` при этом закрыть — не оставлять
рядом.** Главный довод §4.3 против «А» — «`VtGeometry` это публичное поле,
на которое смотрит C-фасад `lib/embed`» — **на дереве не подтвердился**: фасад
`shitty_vt.h` не показывает наружу ни одного поля `VtGeometry`, а его
реализация держит структуру приватным полем и `borderPixels` не читает вовсе
(`git show 60562f22:lib/embed/shitty_vt.cpp`, строки 50, 474–475, 510 — только
`setCellPixelSize(1,1)` и `resize()`). Цена «А» — два файла ядра, 86 строк
(`vt_geometry.h` 38 + `vt_geometry.cpp` 48), которые апстрим за 82 коммита
после их появления **тронул один раз и только комментарием** (`9bf5e497`).
Вариант «Б» (наши поля рядом с апстримным скаляром) заводит два представления
одной величины ровно там, где план заранее назвал опасность. Вариант «В»
(прятать асимметрию в эмбеддер) не работает: пиксельная мышь, хит-тест ссылок и
XTWINOPS отвечают приложению изнутри ядра, и семь именованных тестов, которые
это уже проверяют, покраснеют (список в §6). Наше ядро **сегодня не содержит
`borderPixels` ни разу** — расхождение уже существует, «А» не создаёт его, а
оформляет.

## 2. Что именно добавляется в `VtGeometry`

Апстримный `VtGeometry` на `bd86ed38` и на `origin/master` — одна и та же
структура из семи полей (`git show origin/master:lib/vterm/vt_geometry.h`):

```
u16 columns, rows;
u16 cellPixelWidth, cellPixelHeight;
u16 pixelWidth, pixelHeight;
u16 borderPixels;
```

### 2.1. Предлагаемая форма

```c++
// Четыре стороны, а не «граница». Отдельный тип, а не четыре голых u16:
// пара «сторона -> ось» это то, что перепутывается молча.
struct VtInsets {
    u16 top = 0;
    u16 right = 0;
    u16 bottom = 0;
    u16 left = 0;
};

struct VtGeometry {
    void setCellPixelSize(u16 width, u16 height);
    void resize(u16 pixelWidth, u16 pixelHeight, VtHost* host);

    u16 columns = 0;                 // сетка ЭТОЙ панели
    u16 rows = 0;
    u16 cellPixelWidth = 0;          // без изменений
    u16 cellPixelHeight = 0;
    u16 pixelWidth = 0;              // поверхность окна, общая на все панели
    u16 pixelHeight = 0;

    // НОВОЕ, взамен borderPixels: воздух вокруг текста ЭТОЙ панели,
    // на четыре стороны, в физических пикселях. Резервы хрома сюда
    // не попадают никогда (A10).
    VtInsets insets;

    // НОВОЕ: левый верхний угол прямоугольника панели на поверхности,
    // в физических пикселях, отсчёт от (0,0) поверхности.
    i32 originX = 0;
    i32 originY = 0;

    // НОВОЕ: протяжённость прямоугольника панели в пикселях.
    i32 width = 0;
    i32 height = 0;
};
```

Порядок полей `VtInsets` — `top`/`right`/`bottom`/`left` — намеренно совпадает
с нашим `Insets` (`lib/shitty/composer.h:67-72`) и с `ChromeSide`
(`composer.h:81-87`), чтобы перенос между слоями был копированием поля в поле,
а не пересборкой по памяти.

### 2.2. Судьба `borderPixels`

**Поле удаляется, имя в ядре не остаётся.** Ни как поле, ни как метод, ни как
производное.

Три причины, каждая проверяемая:

1. **В нашем ядре его сегодня нет вовсе.** `grep -rc borderPixels lib/vterm`
   даёт пусто; все упоминания живут в `lib/shitty` (`composer.h` 4,
   `composer.cpp` 2, `composer_ut.cpp` 18, `mouse_frontend_ut.cpp` 16,
   `grid_geometry.h` 1, `test_mode.cpp` 1) и в `build.py` (7 — это сам гвард).
   Это результат решения `M6` §3.2: «взята наша сторона, ни `borderPixels()`,
   ни `scaledPixels()` в ядре нет». Оставить поле — значит вернуть в ядро то,
   что предыдущий шаг мержа оттуда сознательно убрал.
2. **Держать его производным — это и есть дефект варианта «Б».** Производное
   поле требует ответа на вопрос «кто прав при расхождении», и этот ответ
   придётся помнить в девяти местах `vterm.cpp` апстрима, где `borderPixels`
   читается (`git grep -n borderPixels origin/master -- lib/vterm/vterm.cpp`:
   строки 1604, 1605, 2017, 2426, 6516, 6524, 6596, 6597, 9727).
3. **Гварду это безразлично — проверено.** `border_pixels_guard` сопоставляет
   `\b(borderPixels|scaledPixels)\s*\(`, то есть **форму вызова**
   (`build.py:1384`). Апстримное поле `geometry.borderPixels` в счётчик не
   попадает; наш метод `Composer::borderPixels()` попадает.

   Проба, поставленная и откаченная в этом дереве:

   ```
   $ printf '... geometry.borderPixels + geometry.borderPixels ...' > lib/vterm/guard_probe.h
   GREEN                                    # поле не считается
   $ printf '... c.borderPixels() ...'      > lib/vterm/guard_probe.h
   borderPixels()/scaledPixels() are the border option and its scale, not the layout (A1)
   Unallowed uses:
     lib/vterm/guard_probe.h:2              # вызов считается
   $ rm lib/vterm/guard_probe.h && git status --short   # пусто
   ```

   То есть «побочная ловушка», названная в плане, **реальна ровно в одну
   сторону**: замена скаляра полями гвард не заденет (это план и говорил), а
   добавление *метода* `borderPixels()` в `VtGeometry` покраснеет. Решение
   метода не добавляет — соблазн расширить разрешение не возникает, и запрет
   `T2.1` не проверяется на прочность.

### 2.3. Отсчёт `origin` — это то место, где заводится «текст съезжает»

**`originX`/`originY` отсчитываются от (0,0) поверхности, а не от контентной
коробки.** Резерв хрома в них **уже вычтен эмбеддером**, потому что эмбеддер
вычел его, когда нарезал окно на панели.

Сегодня контракт другой, и это надо переключить одновременно в двух местах.
`MouseGeometry::contentLeft()` считает так
(`lib/vterm/mouse_frontend.h:72-74`):

```c++
int contentLeft() const { return insets.left + paneOriginX; }
```

где `insets` — это `composer.contentInsets()` (`mouse_frontend.cpp:43`), то есть
**граница плюс хром**, а `paneOriginX` отсчитывается от контентной коробки
(`windowPane()` возвращает origin по умолчанию, то есть ноль —
`lib/shitty/pane_layout.cpp:35-55`).

После перехода:

```
contentLeft = originX + insets.left        // insets = paneInsets, только border
```

и чтобы результат не изменился при одной панели, эмбеддер обязан подавать

```
originX_new = chromeInsets().left + originX_old
```

Если это преобразование забыть — а забыть его легко, потому что при нулевом
хроме обе формулы дают одно и то же — левая граница панели уедет на ширину
сайдбара. Если, наоборот, положить в `insets` не `paneInsets()`, а
`contentInsets()`, ширина сайдбара будет учтена дважды в правой панели
вертикального сплита: это ровно тот отказ, который план описывает словами «не
падает, текст просто съезжает». **Оба конца этого преобразования — приёмочный
критерий `T5.1`, а не деталь реализации.**

### 2.4. `PaneGeometry` закрывается, а не живёт рядом

Этого пункта в §4.3 нет, и он важнее, чем выбор между «А» и «Б».

У нас **уже есть** структура нужной формы, и она **уже в ядре**:
`PaneGeometry` в `lib/vterm/vterm.h:52-65` — `columns`, `rows`, `originX`,
`originY`, `width`, `height`. Она приходит в `Vterm::create` и в
`Vterm::paneResized`, и `VtermImpl` копирует её в шесть полей экземпляра
(`vterm.cpp:1010-1021`, установка — `vterm.cpp:8829-8836` и `8862-8867`).

Если `VtGeometry` получит origin и инсеты, а `PaneGeometry` останется, у нас
будут **две структуры, обе описывающие геометрию одной панели**, обе внутри
`lib/vterm`, и обе с полями `columns`/`rows`/`originX`. Это в точности дефект,
который §4.3 записывает в минусы варианта «Б», только заведённый с другой
стороны. Поэтому:

- `VtGeometry` становится **геометрией панели** (одна на `Vterm`), а не окна.
  План это уже предполагает: `T5.4` описан как «`VtGeometry` **на панель**».
- `PaneGeometry` удаляется; `Vterm::create` и `paneResized` принимают
  `VtGeometry&` / `const VtGeometry&`.
- `windowPane(const Composer&)` (`lib/shitty/pane_layout.h:26`) остаётся, но
  возвращает `VtGeometry` и заполняет `originX = chromeInsets().left`,
  `originY = chromeInsets().top`, `insets = paneInsets()`.

**Оговорка о владении.** `PaneGeometry` объявлена в `lib/vterm/vterm.h`, а
`T5.1` по плану владеет `vt_geometry.{h,cpp}` и `mouse_frontend.{h,cpp}`.
`vterm.h` не в её списке, `pane_layout.h` принадлежит `T5.4`. Удаление
`PaneGeometry` — правка в трёх строках `vterm.h` (объявление) плюс сигнатуры;
её надо либо явно добавить `T5.1` во владение, либо записать `T5.4` как первый
пункт. Разложить это по двум задачам «как получится» нельзя: между ними дерево
не соберётся.

### 2.5. Кто оповещает панели о смене геометрии

**Наш `paneResized()`, адресно, а не апстримный `VtGeometry::resize()`.**

Апстримный `resize()` сам вызывает `host->resized()` и комментирует это прямо:
«каждый терминал за окном должен услышать изменение геометрии, и только
эмбеддер знает их всех». Это верно для окна с одной панелью и неверно для
дерева панелей: при сплите каждая панель получает **свой** прямоугольник, и
широковещательное «геометрия поменялась» не несёт информации о том, какой.

Предлагается:

- `VtGeometry::resize(pixelWidth, pixelHeight, host)` **остаётся как есть**, с
  апстримной сигнатурой и апстримным телом, но пересчитывает сетку через четыре
  стороны вместо `2u * borderPixels`. Его пользователь — `lib/embed`
  (`shitty_vt.cpp:475,510`) и внутриполосный resize; для них панель и есть окно,
  и апстримная семантика верна.
- Раскладка панелей ходит через `Vterm::paneResized(const VtGeometry&)` —
  адресно, как сегодня (`vterm.cpp:8829`). `Composer::resize()` остаётся у
  эмбеддера, как решил `M6` (отчёт `M6`, §3.1).

Это сохраняет апстримный путь целым для апстримного потребителя и не заводит
второй источник правды: `resize()` и `paneResized()` пишут в **разные**
экземпляры `VtGeometry`, а не в один и тот же.

### 2.6. `grid_geometry.h` — не расщеплять

`T5.2` по плану должна расщепить `grid_geometry.h`: арифметику в `lib/vterm`,
обёртки в `lib/shitty`. Проверено, что расщеплять нечего.

Функции `grid_geometry.h` вызываются из ядра ровно в **четырёх** местах, все в
`vterm.cpp`: `gridColumns` (6537), `gridRows` (6544), `gridPixelWidth` (6616),
`gridPixelHeight` (6617). Все четыре — **вопросы про окно**, а не про панель:
`columnsForPixelWidth`/`rowsForPixelHeight` обслуживают `windowColumns()`,
`windowRows()`, `screenColumns()`, `screenRows()`, то есть отчёты XTWINOPS и
maximize (`vterm.cpp:3686`, `7368`, `7417`, `7476`). Остальные одиннадцать
потребителей `grid_geometry.h` — все в `lib/shitty`.

Поэтому: **арифметика четырёх сторон переезжает методами на `VtGeometry`**
(`columnsFor(pixelWidth)`, `rowsFor(pixelHeight)` и обратные), `grid_geometry.h`
целиком остаётся в `lib/shitty`, и `T5.2` сокращается до «ничего не делать с
этим файлом». Побочный выигрыш: ключ `lib/shitty/grid_geometry.h` в
`border_pixels_allowance` (`build.py:1262-1268`) не надо раздваивать — открытый
пункт §3.3 чек-листа закрывается сам.

### 2.7. Ловушка, которую надо назвать до `T5.5`

Четыре места из §2.6 — **окновые**, и после перехода их **нельзя** механически
перевести на инсеты панели. Апстримная строка выглядит механической:

```
lib/vterm/vterm.cpp:6516 (origin/master):  const u32 border = 2u * geometry.borderPixels;
```

и напрашивается замена на `geometry.insets.left + geometry.insets.right`. Но
`columnsForPixelWidth()` делит **ширину окна** (`windowInfo().width`), а инсеты
панели хрома не содержат. При ненулевом сайдбаре `CSI 18t` отчитается о большем
числе колонок, чем есть, приложение нарисует шире панели, и **ничего не
упадёт**. Сегодня эти четыре места читают `composer.contentInsets()`
(`vterm.cpp:6537`, `6544`, `6615`) — то есть уже правы.

**Решение: `T5.1` эти четыре места не трогает.** Они остаются на эмбеддере до
`M6d`, который убирает понятия эмбеддера из ядра и переводит `composer.resize()`
на `VtHost::requestResize()`. В приёмку `T5.5` (65 механических хунков) надо
внести явный запрет: строки `2u * geometry.borderPixels` в
`columnsForPixelWidth`/`rowsForPixelHeight`/`windowOperation` — **не
механические**.

## 3. Как это соотносится с `lib/embed`

§4.3 называет это главным доводом против «А». **Проверено на `60562f22` (шаг
`M7`) и на `origin/master`; довод не подтверждается.**

**Что торчит наружу из C-фасада.** `shitty_vt.h` объявляет ровно четыре
публичных типа: непрозрачный `shitty_vt`, `shitty_vt_cell`,
`shitty_vt_cursor`, `shitty_vt_callbacks` плюс указатель на функцию
`shitty_vt_cell_fn` (`git show 60562f22:lib/embed/shitty_vt.h`, строки 21, 55,
68, 76, 81). **`VtGeometry` среди них нет.** Геометрия пересекает границу ABI
только числами `uint16_t columns, rows`:

```
100:  shitty_vt* shitty_vt_new(uint16_t columns, uint16_t rows, uint16_t save_lines, const shitty_vt_callbacks*);
103:  void shitty_vt_resize(shitty_vt*, uint16_t columns, uint16_t rows);
 96:  void (*resize_request)(void* user, uint16_t columns, uint16_t rows);
```

`shitty_vt.map` экспортирует `shitty_vt_*` и прячет всё остальное.

**Что делает реализация.** `shitty_vt.cpp` держит `VtGeometry geometry;`
приватным полем структуры (строка 50) и обращается к нему пять раз: строит
1×1-пиксельную ячейку и ресайзит в «пикселях» = ячейках (`474-475`, `510`),
читает `pixelWidth`/`pixelHeight` для ответа на запрос размера окна
(`244-247`), обходит `rows`/`columns` при выдаче сетки (`528`, `533`).
**`borderPixels` не упоминается ни разу** — `git grep borderPixels
origin/master` даёт 13 файлов, и `lib/embed` среди них нет.

**Что сломается у потребителя фасада при варианте «А»:** ничего. Новые поля
имеют значения по умолчанию (`insets` нулевой, `originX/originY` нулевые,
`width/height` заполняются `resize()`), удаляемое поле фасад не называет,
сигнатура `resize()` не меняется, ABI не меняется. Единственная правка в
`lib/embed` — если `width`/`height` не заполнять внутри `resize()`, их надо
выставить рядом со строкой 510; это одна строка в файле, который мы всё равно
принимаем целиком на `M7`.

**Круг потребителей `vt_geometry.h` во всём апстримном дереве — пять файлов:**

```
$ git grep -ln vt_geometry.h origin/master
lib/embed/shitty_vt.cpp
lib/shitty/composer.h
lib/vterm/vt_geometry.cpp
lib/vterm/vt_headless.cpp
lib/vterm/vterm.cpp
```

Из них `composer.h`, `vterm.cpp` и `vt_headless.cpp` у нас в любом случае свои
(см. §4).

## 4. Насколько углубляется расхождение с апстримом

Мера — «сколько файлов ядра станут нашими навсегда» и «сколько раз апстрим их
трогает».

**Предельная цена варианта «А» — два файла, 86 строк:** `vt_geometry.h` (38
строк) и `vt_geometry.cpp` (48). Всё остальное, чего касается `T5.1`, уже наше
и станет нашим независимо от выбора:

| Файл `lib/vterm` | Строк расхождения с `origin/master` сегодня | Чей по существу |
|---|---:|---|
| `vterm.cpp` | 893 | наш (`A8`, `A9`; +65 хунков `T5.5`) |
| `vterm.h` | 170 | наш (`PaneGeometry`, `paneResized`) |
| `mouse_frontend.h` | 106 | наш (211 строк против апстримных 109) |
| `mouse_frontend.cpp` | 85 | наш (241 против 170) |
| `cell_extra_store.{h,cpp}` | 165 | наш (`R7`, `T5.3`) |
| **`vt_geometry.{h,cpp}`** | **н/д (файлов ещё нет)** | **предмет решения** |

(Числа сняты как `git diff origin/master -- <файл> \| grep -c '^[+-]'` на дереве
`eb016aec`; часть из них — «ещё не смержено», а не «сознательно наше», и это
надо читать как порядок величины, а не как ведомость.)

**Сколько это стоит на каждом следующем мерже — измерено, а не оценено.** С
момента появления `vt_geometry.{h,cpp}` в `bd86ed38` до `origin/master` прошло
**82 коммита**, и `vt_geometry` из них тронул **один**:

```
$ git log --oneline bd86ed38..origin/master -- lib/vterm/vt_geometry.h lib/vterm/vt_geometry.cpp
9bf5e497 Scrub the last embedder concepts out of the VT core
```

а его правка — **замена одного слова в комментарии** («from its font» →
«from whatever it draws with»). Файл функционально заморожен. Утверждение §4.3
«каждый следующий мерж будет трогать `vt_geometry.h`» на измеренной истории не
подтверждается: частота примерно один конфликт на восемьдесят коммитов, и тот
в комментарии.

**Существенное уточнение к цели `Р2`.** Расхождение, которое `T5.1` якобы

## 5. Проверка на текущем дереве: что изменили `M6` и `M6b`

§4.3 писалась до волны 6. Два мерж-шага прошли, и оба **оставили за
`Composer`** то, что могло уехать в ядро. Цена вариантов от этого изменилась —
в пользу «А».

1. **`borderPixels()`/`scaledPixels()` остались на `Composer`** (отчёт `M6`
   §3.2). Следствие: у ядра сегодня **нет** имени для границы вовсе. Вариант
   «Б» («оставить апстримный `borderPixels`, наши поля рядом») теперь означает
   не «сохранить апстримное», а **«внести в ядро поле, которого там нет»** —
   и тем самым отменить решение `M6`. Это уже не консервативный вариант.
2. **`Composer::resize()` остался на `Composer`** (отчёт `M6` §3.1). Значит
   пересчёт сетки окна из четырёх сторон уже живёт у эмбеддера и уже работает;
   `VtGeometry::resize()` дублировать его не должен и не будет — он считает
   сетку **панели** из её собственного прямоугольника.
3. **`VtState` уже несёт `baseBorder` и `contentScale` полями**
   (`lib/vterm/vt_state.h:57-63`) с комментарием, дословно ссылающимся на
   `T5.1`: «ядро, которое тоже владело бы границей, было бы вторым источником
   правды, ради решения о котором `T5.1` и существует». `M6c` растворяет
   `VtState`; этим полям нужен дом, и правильный дом — `Composer` (они и есть
   опция плюс её масштаб, то есть `A1`).
4. **`T2.1` уже сделана.** `guard_scan_roots` содержит `lib/vterm`
   (`build.py:1285`), `mouse_geometry_allowance` перекеен на
   `lib/vterm/mouse_frontend.{h,cpp}` (`build.py:1448-1451`),
   `border_pixels_guard` читает через `blanked()` и сопоставляет по границе
   слова с формой вызова (`build.py:1384`). Все три опасения §3.2/§3.3 чек-листа
   уже закрыты; гвард на этом дереве зелёный (проверено прямым исполнением
   программы гварда через `ast`, не по штампу `.build`).

**Что от этого меняется в оценке:** довод «`Б` дешевле, потому что не трогает
апстримное» перестал быть верным — трогать апстримное придётся в любом случае,
потому что предыдущий шаг мержа уже выбрал нашу сторону. Остаётся выбор между
одной честной структурой и двумя.

## 8. Третий вариант — есть, и его стоит назвать, чтобы отвергнуть явно

**Вариант «Г»: оставить `vt_geometry.{h,cpp}` побайтово апстримными, а всю нашу
геометрию держать в `PaneGeometry` — структуре, которой у апстрима нет вообще.**

Из сегодняшнего дерева он виден лучше, чем из §4.3, потому что `PaneGeometry`
уже существует, уже в `lib/vterm/vterm.h:52`, и уже несёт origin. `Vterm::create`
принимал бы оба: `VtGeometry&` (окно — для `resize()`, XTWINOPS, фасада) и
`const PaneGeometry&` (панель — для сетки, мыши, хит-теста).

*За:* два файла ядра остаются нулевыми в дифе навсегда; конфликтов в них не
будет никогда, а не «один на 82 коммита»; `lib/embed` нетронут; расхождение
уезжает целиком в структуру, которой апстрим не касается, — а новая структура
в мерже дешевле изменённой.

*Против, и это решающее:* обе структуры имеют поля `columns` и `rows`, и они
означают разное (окно против панели). При одной панели значения совпадают, при
сплите — расходятся. Ровно тот второй источник правды, о котором предупреждает
уточнение плана, только не между `Composer` и `VtGeometry`, а внутри ядра.
Плюс `Vterm::create` получает два геометрических аргумента, и порядок их
перепутывания компилируется. Плюс расходится с планом, который писал
«`VtGeometry` **на панель**» (`T5.4`), — а значит `T5.4`, `T5.5`, `T5.10` надо
переписывать.

**Отвергаю.** Экономия — один конфликт в комментарии на 82 коммита; цена —
именно тот дефект, ради предотвращения которого `T5.1` объявлена точкой
остановки.

Четвёртый вариант («поднять вопрос в апстрим, чтобы он сам взял четыре
стороны») я рассматривал и не оцениваю: он вне контроля владельца форка и не
имеет срока. Упоминаю, потому что он единственный, который сокращает
расхождение, а не оформляет его; если контакт с апстримом есть, это дешевле
всего остального в этом документе.

## 9. Что решение делает необратимым

придётся не идею, а количество переписанных вызовов. Поэтому дешевле всего
решать сейчас, до того как `T5.4` и `T5.10` эти вызовы напишут.
