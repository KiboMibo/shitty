## Резюме

Волна не добавила ни сетевых входов, ни разбора недоверенных данных, ни работы с секретами, и результат ей соответствует. `T5` — перестановка одного `ioctl` через границу `fork`; `T3` — вынос двух циклов в функции плюс один диагностический вывод. Обе правки закрыты по своим главным рискам: `resizePty()` на пути ошибки только предупреждает и не роняет открытие сессии, дескрипторы вокруг `fork` закрываются на всех путях, диагностика печатает метаданные и ничего больше.

Четыре замечания — про то, что и до волны было так же (три из четырёх — прямо унаследованное), но что задача просила посмотреть и что стоит одной-двух строк правки: у новой диагностики нет верхней границы по общему числу отчётов; в `spawn()` отказ открыть pty убивает весь процесс, а не сессию; `execvp` после `fork` в многопоточном процессе формально небезопасен; в `tst/harness.py` буфер чтения растёт без предела длины.

## 1. Главный вопрос: утечка содержимого экрана в stderr

**Не утекает.** Проверено по коду, не по комментарию.

Вся диагностика — два `fprintf` в `reportRefusedFrame()` (`lib/shitty/application.cpp:584-615`):

```c
fprintf(stderr, "%s: renderer refused %u frames in a row, a full expose included; %zu pane(s) offered:\n", brand, refusedFrames, frameUpdates.length());
```

```c
fprintf(stderr, "%s:   pane %zu: grid %ux%u, %zu row(s) given: %s\n", brand, at, update.gridColumns, update.gridRows, update.rowCount, reason);
```

Разбор аргументов по одному:

| аргумент | что это | откуда |
|---|---|---|
| `brand` | `"shitty"` / `"pretty"` / `"terminal"` | `Brand::identifierCString()` (`brand.cpp:55`) над `identifier()`, который у всех трёх реализаций — строковый литерал (`bin/st/main.cpp:34`, `bin/pt/main.cpp:34`, `brand.cpp:39`). Компилтайм-константа, к вводу отношения не имеет. |
| `refusedFrames` | счётчик отказов, `u32` | `application.cpp:171` |
| `frameUpdates.length()` | число панелей в кадре, `size_t` | — |
| `at` | индекс панели, `size_t` | — |
| `update.gridColumns`, `update.gridRows` | размер сетки, `u16` каждый | `vterm.h:145-146` |
| `update.rowCount` | число переданных строк, `size_t` | `vterm.h:138` |
| `reason` | один из четырёх строковых литералов, выбираемых по `nullptr`/нулю | `application.cpp:605-612` |

Ключевое: из `TerminalUpdate` берутся **только скалярные поля**. Указатели `update.rows` (`const TerminalRow*`), `update.overlayCells` (`const TerminalCell*`), `update.shapes` (`Screen*`) — то есть всё, где лежат символы, которые читает пользователь, — не разыменовываются нигде в функции. Единственное обращение к указателю — сравнение `update.colors == nullptr` (`application.cpp:606`), проверка на null без чтения по адресу. Форматная строка в обоих вызовах — литерал, так что форматной инъекции тоже нет.

Что в лог всё-таки попадает: количество открытых панелей и размер сетки каждой из них. Это метаданные сеанса, а не его содержимое, и они там и раньше были — `composer.cpp:252` печатает грид тем же способом. Заголовки окна, вывод команд, буфер ввода, выделение, preedit — ничего из этого в отчёте нет.

Заявление автора («grids and counts only») подтверждается.

Отдельно: `reportRefusedFrame()` читает `frameUpdates[at].update`, а `PaneUpdate::update` — это **ссылка** (`composer.h:112`). Проверил, не висячая ли она: `Vterm::retainedOutput()` объявлен возвращающим `const TerminalUpdate&` (`vterm.h:268`), а не значение, так что ссылка указывает на объект, которым владеет терминал, а не на временный. Панель жива — обход `framePanes` только что её отдал. Чтения за пределами времени жизни нет.

## Находки

### Z1. У диагностики отказов нет верхней границы, и она не зависит от времени

- **Уровень:** замечание
- **Где:** `lib/shitty/application.cpp:592-596`
- **Класс:** неограниченный рост лога (CWE-779, «excessive logging»)
- **Кто может:** никто извне; состояние достигается отказом бэкенда (потерянная поверхность, нулевая сетка)

Ограничитель считает **кадры**, а не время:

```c
static constexpr u32 stalledFrames = 3;
static constexpr u32 repeatEvery = 600;
if (refusedFrames < stalledFrames || (refusedFrames - stalledFrames) % repeatEvery != 0) {
    return;
}
```

Комментарий переводит 600 кадров в «примерно десять секунд», и для этого нужна частота 60 Гц. Я проверил, чем на самом деле задаётся частота: `presentTerminal()` вызывается **только** из `ApplicationImpl::frame()` (`application.cpp:777`), то есть исключительно с кадрового колбэка платформы. На cocoa это CVDisplayLink (`ext/plt/platform_cocoa.mm:1604-1609`, `draw()` в 1619) — вертикальная синхронизация, ~60 Гц. На wayland `WindowImpl::ready()` при `frame()`, вернувшем false, повторяет один раз немедленно, а дальше уходит на `timeout(10'000, ...)` (`ext/plt/platform_wayland.cpp:2744-2753`), то есть 10 мс, ≤100 Гц. Значит частота отчётов действительно ограничена: не чаще одного примерно раз в 6 секунд.

**Чем грозит.** Диск это не заполнит: один отчёт — 1 строка плюс по строке на панель, ~80–110 байт каждая; при четырёх панелях это порядка 7 МБ в сутки в худшем случае. Но у отчётов нет ни потолка по общему числу, ни затухания: окно, зависшее из-за неустранимой причины, будет писать эту строку бесконечно, пока живо, и, в отличие от соседней диагностики окна (`application.cpp:746`), не смотрит на `composer.opts->verbose`. В journald или в логе CI это шум, который никогда не кончается.

Отмечу как проверенное и безопасное: переполнение `refusedFrames` (u32) ничего не ломает — после обёртывания значения 0, 1, 2 отсекаются первым условием, вычитания без знака под нулём не происходит; меняется только фаза повторов.

- **Как чинить:** либо ограничить общее число отчётов (например, замолчать после N-го, напечатав, что дальше молчим), либо перевести повтор на монотонные часы вместо счётчика кадров — тогда сообщение об одном и том же не зависит от того, как платформа перезапрашивает кадр.
- **Как проверить:** отдельного теста на это сейчас нет; добавить юнит-тест, который заставляет фальшивый рендерер отказывать N раз подряд и считает строки в перехваченном stderr (обвязка уже умеет перехват — `Shitty(capture_stderr=True)`, `tst/harness.py:217`, `stderr_text()` в 262).

### Z2. Отказ открыть pty убивает весь процесс, а не сессию

- **Уровень:** замечание
- **Где:** `lib/shitty/pty.cpp:106-137` (`openPtyMaster`, `openPtySlave`), через `sysError()` в `pty.cpp:72-78`; вызовы — `pty.cpp:883-884`
- **Класс:** отказ в обслуживании, локальный (CWE-703)
- **Кто может:** локальный пользователь этой же сессии — в том числе непреднамеренно, исчерпав лимит pty
- **Унаследовано:** да, `T5` этого кода не касалась; попадает в отчёт потому, что задача просила разобрать пути ошибок `spawn()`

`sysError()` — `[[noreturn]]` и заканчивается `exit(1)`. Значит любой отказ `posix_openpt()`, `grantpt()`, `unlockpt()`, `ptsname()` или `open()` слейва при открытии **одной новой панели** гасит весь терминал вместе со всеми остальными панелями и вкладками. Исключения при этом не возникает, так что `try`/`catch (...)` вокруг вызова (`session.cpp:452-461`), который освобождает арену, для этого пути мёртв — раскрутки стека не будет.

- **Чем грозит.** Пользователь, упёршийся в системный лимит на pty (или в `RLIMIT_NOFILE`), теряет не создание панели, а всю сессию со всей несохранённой работой в каждой панели. Достижимо из-под обычного пользователя без всякой злонамеренности.
- **Как чинить:** на этих путях бросать исключение вместо `exit(1)` (`Errno().raise(...)` — принятый в проекте способ, ср. `brand.cpp:64`), чтобы уже существующий `catch` в `openSession()` освободил арену и отказ остался отказом одной панели. `sysError()` при этом стоит оставить как есть для путей, где восстановление действительно невозможно, — менять его целиком не нужно, достаточно двух функций открытия pty.
- **Как проверить:** тест, в котором открытие слейва отказано (например, через исчерпание дескрипторов в дочернем процессе теста), должен получить исключение и живой процесс, а не код возврата 1.

### Z3. `execvp` между `fork` и `exec` в многопоточном процессе

- **Уровень:** замечание
- **Где:** `lib/shitty/pty.cpp:924`
- **Класс:** зависание при `fork` в многопоточной программе (CWE-833, deadlock)
- **Кто может:** никто намеренно; окно гонки — микросекунды
- **Унаследовано:** да, `T5` этот участок не трогала; в отчёте потому, что задача просила посмотреть на окно между `fork` и `exec`

После `fork()` в процессе с несколькими потоками ребёнку разрешено звать только async-signal-safe функции. Всё, что зовётся в ветке `pid == 0` (`pty.cpp:905-926`), этому удовлетворяет — `sigprocmask`, `setsid`, `ioctl`, `close`, `dup2`, `fcntl`, `tcgetattr`, `tcsetattr`, `write` — **кроме `execvp`**: POSIX относит к безопасным `execv`/`execve`, но не `execvp`/`execlp`, потому что поиск по `PATH` в реализации может брать память. Потоки у процесса к этому моменту есть: дренажный поток `PtyImpl` поднимается лениво на первом `engage()` (`pty.cpp:586` рядом), поэтому второй и последующие `spawn()` форкают многопоточный процесс.

- **Чем грозит.** Если чужой поток держал аллокаторную блокировку в момент `fork`, ребёнок может заклиниться в `execvp` навсегда, оставив открытым слейв и панель без процесса. Это зависание, не компрометация; вероятность крайне мала, и за всё время это ни разу не всплыло.
- **Как чинить.** Дёшево — только если правка окажется меньше риска: заранее, до `fork`, разрешить путь до исполняемого файла и звать `execv`. Осмысленная альтернатива — ничего не делать и записать это как принятый риск; тогда место стоит пометить комментарием, чтобы следующий читатель не тратил на него тот же час.
- **Как проверить:** воспроизводимого теста на это не построить; критерий приёмки — сам вызов, а не поведение.

### Z4. Буфер чтения обвязки растёт без предела длины

- **Уровень:** замечание
- **Где:** `tst/harness.py:278-292`
- **Класс:** неограниченное потребление памяти (CWE-770)
- **Кто может:** только тестируемый бинарь, то есть свой же код; продукта не касается

`REPLY_TIMEOUT` и `select()` (`harness.py:287-288`) поставили границу **по времени на одно чтение**, и поставили её правильно — на чтение, а не на сокет, с объяснением, почему `settimeout()` там ломает записи. Но границы **по длине** у накопления нет: `self._receive_buffer.extend(chunk)` (`harness.py:292`) растёт, пока в буфере не найдётся `\n`, а `select()` не срабатывает, пока данные продолжают приходить. Терминал, который непрерывно пишет в сокет без перевода строки — заклинившая генерация ответа, мусор от повреждённого протокола, — раздувает буфер прогонщика тестов до OOM, и тайм-аут при этом не наступит ни разу.

Это обвязка, а не продукт, и пишет в неё собственный бинарь, поэтому уровень — замечание. Побочно: `bytearray.find(b"\n")` перезапускается с нуля на каждой итерации, то есть на большом буфере это ещё и квадратично.

- **Чем грозит:** прогон тестов падает по памяти вместо того, чтобы упасть красным тестом, — ровно тот класс отказа, который `REPLY_TIMEOUT` и вводили, чтобы устранить.
- **Как чинить:** добавить потолок на `len(self._receive_buffer)` (мегабайта хватает с большим запасом — самый длинный штатный ответ протокола на порядки меньше) и поднимать `RuntimeError` с тем же тоном, что и рядом. Заодно искать `\n` со смещения предыдущего поиска.
- **Как проверить:** `tst/test_harness_reply_timeout.py` уже держит границу по времени; дописать туда случай, где поддельный писатель шлёт данные без `\n`, и ожидать `RuntimeError`, а не рост памяти.

## Проверенное и чистое

Всё ниже прочитано и признано корректным; находок здесь нет.

**`T5`, дескрипторы вокруг `fork` (`pty.cpp:875-930`).**

- Мастер получает `FD_CLOEXEC` сразу после `posix_openpt()` (`pty.cpp:111`), так что в `exec`-нутого потомка он не попадает; сверх того ребёнок закрывает его руками (`pty.cpp:913`).
- Слейв закрывается на обоих путях: в родителе после `fork` (`pty.cpp:928`) и в ребёнке — внутри `redirectFds()` (`pty.cpp:101-103`), после `dup2` на 0/1/2.
- Путь отказа `fork()` закрывает **оба** дескриптора и восстанавливает маску до `sysError()` (`pty.cpp:897-904`).
- `resizePty()` **не открывает и не закрывает ничего** — работает по уже открытому слейву, — поэтому новых путей утечки правка `T5` не добавила.
- Гонки «слейв одного `spawn()` протёк в потомка другого» нет: между `openPtySlave()` и `fork()` нет ни одной точки, где фибра уступает управление, а из дренажного потока `spawn()` не зовётся.
- Прошёл по остальным дескрипторам, которые открыты в момент `spawn()` в живом окне, и все они закрываются на `exec`: будильниковая труба `PtyImpl` (`pty.cpp:586-591`, `FD_CLOEXEC`), `loop_wake` (`ext/plt/loop_wake.cpp:24-29`), файлы шрифтов (`font_face.cpp:132`, `O_CLOEXEC`), трубы wayland (`platform_wayland.cpp:1341`, `2902` — `pipe2(O_CLOEXEC)`), управляющий и IO-дескрипторы тестового режима (`test_mode.cpp:2076`). Постоянного дескриптора у поллера нет — цикл построен на `poll(2)`. Два места в проекте открывают файл без `O_CLOEXEC` (`main.cpp:110`, `heap_profile.cpp:63`), но оба — в подкоманде `perf` и в дампе профиля, которые pty не порождают, и оба сразу оборачивают дескриптор в `ScopedFD`.

**`T5`, поведение `resizePty()` при отказе `ioctl` (`pty.cpp:139-148`).** При неудаче `TIOCSWINSZ` функция зовёт `sysWarn()` — печать в stderr и возврат, — а не `sysError()`. То есть **в отказ открытия сессии это не превращается**: потомок родится с сеткой 0×0, ровно как до `T5`, и первый же `applyLayout()` (`session.cpp:863`) выставит размер заново. Деградация мягкая и в правильную сторону.

**`T5`, окно между `fork` и `exec` (`pty.cpp:905-926`).** Порядок верный: маска восстанавливается первой операцией (`906`), затем `setsid()` (`907`), затем `TIOCSCTTY` на слейве (`910`) — то есть управляющий терминал берётся уже в новой сессии, как и требуется. Между `setsid()` и `TIOCSCTTY` ребёнок ненадолго без управляющего терминала, но это неизбежно и ничем не грозит: он ещё ничего не исполняет. `SIGCHLD` в этом окне сработать не может — ожидающие сигналы после `fork` у ребёнка очищены, а собственных детей у него нет; сам блок `SIGCHLD` вокруг `fork` (`pty.cpp:891-895`) как раз и не даёт потомку, умершему мгновенно, обогнать учёт в родителе. Единственное, что здесь стоит внимания, — `execvp`, см. `Z3`.

**`T5`, усечение размеров.** `resizePty()` кладёт `u32` в `unsigned short` полей `struct winsize` (`pty.cpp:141-144`). Проверил достижимость: `PtySize` собирается в `SessionSetImpl::ptySize()` (`session.cpp:1022-1029`) из `pane.columns`/`pane.rows` разметки, умноженных на размер глифа, и `resize()` зовут только из `applyLayout()` (`session.cpp:863`) — то есть из геометрии окна, а не из потока pty. Управляющей последовательности, которой потомок мог бы попросить свой размер (XTWINOPS `CSI 8 t`), в дереве нет: других вызывающих `->resize(` не нашлось. Чтобы переполнить 65535 по пикселям, нужно окно шириной в десятки тысяч пикселей. Недостижимо и потомком не управляемо.

**`T3`, поведение счётчика и повторная сборка кадра.** Обход, решающий, кто должен `consume()`, и обход, собирающий `frameUpdates`, после отказа выполняются заново оба (`application.cpp:692-694`), а финальный цикл `consume()` (`application.cpp:713-718`) читает `paneOutputs` из **последнего** обхода — то есть согласован с тем кадром, который в итоге приняли. Двойного `consume()` или `consume()` на панели, отдавшей удержанную форму, отсюда не получается. Ссылок, переживших `frameUpdates.clear()`, тоже нет.

**Секреты.** `gitleaks` по обоим коммитам — чисто. Ни один из тронутых файлов не работает с ключами, паролями, строками подключения или переменными окружения с секретами.

**Внешние входы.** Волна не добавила ни одного нового входа: ни сетевого сокета, ни разбора недоверенного формата, ни новой команды тестового протокола, ни нового аргумента командной строки. Разбор escape-последовательностей — единственный настоящий недоверенный вход этого продукта — обеими задачами не тронут.
