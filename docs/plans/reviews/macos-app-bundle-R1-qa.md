# QA-отчёт: приёмка T1 (macos-app-bundle, волна W1)

**Дата:** 2026-08-15
**Область:** коммиты `fb200a18` (`dev/make_app.sh`, `README.md`) и `c0be72ab` (отчёт исполнителя) поверх `master`, ветка `feat/macos-app-bundle`
**Вердикт:** готово с замечаниями

## Резюме

Скрипт делает то, что заявлено: собирает валидные `Shitty.app`/`Pretty.app` из
уже готовых бинарей, `plutil -lint` проходит, `CFBundleIdentifier` верный,
иконка рендерится и корректно опускается без `rsvg-convert`. Главный пункт —
видимое пользователю имя — перепроверен независимо и подтверждён: не только
`displayed name` в System Events, но и реальный текст пункта меню (`menu bar
item 2`) после запуска бандла равен `Shitty`, а не `st`. Все пять критериев
приёмки закрыты. Блокирующих находок нет.

Главное замечание — временные файлы и наполовину собранный `.app` не
чистятся, если `make_icns` падает после того, как уже создала рабочую
директорию (например, если `iconutil` завершится с ошибкой): я это
воспроизвёл. Второе — README рекомендует `./dev/make_app.sh` сразу после
`brew install`, полагаясь на резолвинг `pt` через `PATH`, а исполнитель сам же
обнаружил, что `pt` коллизирует с формулой `tcl-tk`; сообщение об этой
ловушке в README нет.

## Что проверено

- Реальный прогон `./dev/make_app.sh /opt/homebrew/bin <out>` на живых
  бинарях из `pg83/tap` (`brew link --overwrite pretty` для снятия коллизии
  с `tcl-tk`, как и советует отчёт исполнителя) — `exit=0`, обе структуры
  `Contents/{Info.plist,MacOS/<exe>,Resources/<icns>}` на месте.
- `plutil -lint` на обоих `Info.plist` — `OK`.
- `plutil -extract CFBundleIdentifier raw` — `org.pg83.shitty` / `org.pg83.pretty`.
- Полный дамп `Info.plist` (`plutil -p`) с иконкой (9 ключей) и без (8 ключей,
  без `CFBundleIconFile`) — совпадает с числами из отчёта исполнителя.
- `file *.icns` — оба валидные `Mac OS X icon`, тип `ic12`.
- `open Shitty.app` + независимая проверка видимого имени (см. «Критерий 4»
  ниже) — двумя разными способами, не полагаясь на утверждение отчёта.
- Повторный прогон поверх уже собранного бандла (идемпотентность) — `exit=0`,
  `plutil -lint` снова `OK`.
- Прогон с `PATH` без `rsvg-convert` — предупреждение в stderr, `exit=0`,
  ключ `CFBundleIconFile` корректно отсутствует.
- Прогон с путём вывода, содержащим пробел — отработал верно (кавычки в
  скрипте расставлены аккуратно).
- Прогон с несуществующим `BIN_DIR` и без резолвящегося бинаря в `PATH` —
  скрипт падает (`exit=1`), просто сообщение от `cp` малоинформативно.
- Прогон из `dev/` вместо корня репозитория — иконка молча пропускается
  (SVG ищется относительно `cwd`, а не относительно скрипта).
- **Внесена намеренная поломка** — подменил `iconutil` в `PATH` на версию,
  всегда завершающуюся ошибкой, чтобы проверить очистку временных файлов на
  падении (см. находку В1) — воспроизвёл, откатил.
- `grep -n "sudo\|chown\|chmod 777"` по скрипту — ничего не найдено,
  root-операций нет.
- Сверка стиля с соседним `dev/build_brew_macos.sh`: тот же заголовок
  лицензии, `#!/bin/sh`, `set -e`, комментарии объясняют «почему», а не
  «что» — стиль выдержан.
- `shellcheck` недоступен в окружении — не прогонялся; квотирование
  переменных проверено вручную (тест с пробелом в пути) и построчным чтением
  скрипта.

## Критерии приёмки (борд W1)

1. **Собирает `Shitty.app` и `Pretty.app` из указанных бинарей.** Закрыт.
   Воспроизведено на `/opt/homebrew/bin/{st,pt}`, `exit=0`, обе структуры на
   месте.

2. **`plutil -lint` проходит; `CFBundleIdentifier` верный.** Закрыт.
   Проверено напрямую, значения совпадают с планом: `org.pg83.shitty`,
   `org.pg83.pretty`.

3. **`.icns` из SVG, при отсутствии растеризатора бандл всё равно
   собирается.** Закрыт. Оба пути прогнаны: с `rsvg-convert` иконка
   генерируется (валидный `ic12`), без него — предупреждение в stderr,
   `exit=0`, `CFBundleIconFile` корректно отсутствует, а не пуст.

4. **`open Shitty.app` поднимает окно, в Dock/меню видно `Shitty`, не `st`.**
   Закрыт — перепроверено независимо, не на слово исполнителя. Помимо
   `osascript ... name of p, displayed name of p` (дало `st` / `Shitty`, как и
   в отчёте), я отдельно поднял бандл и запросил у System Events реальный
   список пунктов меню процесса:
   ```
   $ osascript -e 'tell application "System Events"
       tell process "Shitty"
         repeat with i from 1 to (count of menu bar items of menu bar 1)
           ...
         end repeat
       end tell
     end tell'
   Apple, Shitty
   ```
   Второй пункт меню (тот самый жирный текст в строке меню сразу после
   яблока — то, что реально видит пользователь, а не свойство `name`
   доступности) равен `Shitty`. `bundle identifier of p` при этом —
   `org.pg83.shitty`, то есть проверялся именно наш процесс. Аргумент
   исполнителя про `name` vs `displayed name` в System Events подтверждается,
   и я усилил его прямой проверкой отрисованного текста меню, а не только
   ещё одного свойства объекта доступности.

5. **Не требует root, не пишет вне выходной директории.** Закрыт в
   happy path, но с оговоркой — см. находку В1: при падении внутри
   `make_icns` скрипт пишет (и оставляет) файлы в `$TMPDIR` вне указанной
   `$OUT_DIR`. `sudo`/root-операций в скрипте нет.

## Находки

### Блокирующих нет

### Важные

1. **Временные файлы и недостроенный `.app` не чистятся при падении в
   `make_icns`** — `dev/make_app.sh:44-52` (создание `$WORK`/`iconutil`) и
   `dev/make_app.sh:68-70` (вызов `make_icns` в `make_bundle` без обработки
   ошибки).
   Что не так: `rm -rf "$WORK"` стоит **после** вызова `iconutil` одной
   строкой ниже без `trap`/`||`. Скрипт работает под `set -e` верхнего
   уровня; если любая команда внутри `make_icns` (любой `rsvg-convert` из
   цикла или сам `iconutil`) завершится с ошибкой, весь скрипт немедленно
   выходит, `rm -rf "$WORK"` не выполняется.
   Воспроизвёл: подменил `iconutil` в `PATH` на версию, которая всегда падает
   с `exit 1`, прогнал `./dev/make_app.sh /opt/homebrew/bin <out>`. Итог:
   `exit=1`, и в `$TMPDIR` остался каталог `tmp.XXXXXXXX/icon.iconset/` с 10
   PNG-файлами, который скрипт никогда не удалит сам. Побочный эффект того же
   падения: `<out>/Shitty.app` тоже остаётся на диске в недостроенном виде —
   есть `Contents/MacOS/st`, но нет `Info.plist` и `Resources/*.icns` —
   формально это не бандл (нет `Info.plist`), но каталог с расширением
   `.app` лежит и может ввести в заблуждение при следующем ручном осмотре
   `$OUT_DIR`.
   Чем грозит: на CI-машине с частыми падениями сборки (например, временная
   недоступность `rsvg-convert`/повреждённый SVG/нехватка места на диске
   для `iconutil`) в `$TMPDIR` будет копиться мусор; при однократном ручном
   запуске риск минимальный — несколько мелких PNG на diskе.
   Предлагается: `trap 'rm -rf "$WORK"' EXIT` сразу после `WORK="$(mktemp -d)"`
   внутри `make_icns`, либо явный `rm -rf "$WORK"` в обеих ветках
   (успех/провал) через `if ! iconutil ...; then rm -rf "$WORK"; return 1; fi`.

2. **README рекомендует команду, которая зависит от известной коллизии в
   `PATH`** — `README.md:341-347` (новый абзац), в связке с
   `dev/make_app.sh:19-25` (`find_binary`, ветка `command -v "$1"`).
   Что не так: раздел `## Install` → `### Homebrew` показывает ровно
   `brew install pg83/tap/shitty && brew install pg83/tap/pretty`, затем сразу
   `./dev/make_app.sh` без аргументов. При дефолтных путях (`.build` не
   существует, если пользователь не собирал руками) скрипт уходит в
   `command -v pt`, которая резолвится через `PATH`. Отчёт исполнителя сам
   фиксирует, что `/opt/homebrew/bin/pt` может указывать на `tcl-tk`, а не на
   `pg83/tap/pretty` (коллизия имени `pt` между формулами), и что в таком
   окружении `codesign` падает на чужом файле с `Permission denied`. Это
   ровно тот путь, которым README ведёт свежего читателя, а само README про
   ловушку молчит.
   Чем грозит: пользователь с установленным `tcl-tk` (частый пакет для
   scripting/GUI-инструментов) следует README дословно и получает
   непонятную ошибку `codesign`, без подсказки, что дело в коллизии имён
   Homebrew-формул, а не в самом скрипте.
   Предлагается: одна строка в README рядом с примером команды — например,
   «если `pt` уже занят другой формулой (`tcl-tk` ставит одноимённый бинарь),
   выполните `brew link --overwrite pretty` перед упаковкой» — или сноска в
   самом скрипте/README на `command -v`. Правку не делаю — это чужой файл
   (`README.md` в зоне T1).

### Замечания

- `dev/make_app.sh:19-25` (`find_binary`) — если бинарь не найден ни в
  `$BIN_DIR`, ни в `$PATH`, `command -v` возвращает пусто, и падение
  происходит на `cp` с малопонятным `cp: : No such file or directory`
  вместо внятного «binary 'pt' not found in $BIN_DIR or PATH».
- `dev/make_app.sh:75-80` (`make_bundle`, поиск SVG) — путь к SVG задан как
  голое имя файла (`shitty.svg`) относительно `cwd`, а не относительно
  расположения скрипта. Запуск не из корня репозитория (например,
  `cd dev && ./make_app.sh`) молча собирает бандл без иконки — в отличие от
  ветки «нет `rsvg-convert`», здесь никакого предупреждения не печатается,
  хотя итог для пользователя тот же (иконки нет). README показывает вызов
  только как `./dev/make_app.sh` из корня, так что на заявленном пути
  использования это не проявляется.
- `dev/make_app.sh:34` — `CFBundleShortVersionString`/`CFBundleVersion`
  заполняются как `git describe --tags --always` (например,
  `11-3-gfbd38953`), что не является строго dotted-numeric форматом, который
  Apple рекомендует для этих ключей. Для локальной ad-hoc упаковки без
  дистрибуции через нотариус/App Store это не создаёт проблем — `plutil
  -lint` не возражает, бандл запускается — отмечаю на будущее, если появится
  нотаризация.

## Документация

**Состояние.** Новый абзац в `README.md` (раздел `## Install` → `### Homebrew`)
правдиво описывает, что делает скрипт (Dock/Finder launch, имя в меню, иконка
из `Info.plist` вместо runtime-фолбэка) — я проверил каждое из этих
утверждений отдельно, все подтвердились. Тон и формат (короткий абзац +
блок команды сразу после Homebrew-инструкций) соответствуют соседним
разделам. Единственный минус — уже описан как важная находка №2
(README не предупреждает про коллизию `pt`↔`tcl-tk`, хотя её нашёл сам
исполнитель).

**Создано/обновлено.** Ничего — правки документации не делал, файл в зоне
ответственности T1 (правила скилла запрещают одновременно проверять и
править чужие файлы в этой роли).

## Рекомендации

1. Добавить `trap`/явную очистку `$WORK` в `make_icns` на случай ошибки —
   закрывает важную находку 1.
2. Одна строка в README про коллизию `pt`↔`tcl-tk` (или ссылку на неё) —
   закрывает важную находку 2.
3. Внятное сообщение об ошибке в `find_binary`, если бинарь не найден нигде —
   мелочь, но экономит время при первом запуске на чужой машине.
4. Резолвить путь к SVG относительно расположения скрипта (`$(dirname "$0")/..`),
   либо хотя бы предупреждать в stderr, если файла нет — на случай запуска не
   из корня репозитория.

Пункты 3–4 не блокируют мердж при заявленном способе использования
(`./dev/make_app.sh` из корня репозитория, как показано в README).
