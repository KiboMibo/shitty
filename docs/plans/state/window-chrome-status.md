## Задача

Две macOS-фичи: прозрачный титлбар («лайт», без `FullSizeContentView`) и
quick terminal — окно по глобальному хоткею поверх всех приложений.
Сплиты панелей сознательно отложены (три волны, смена контракта рендерера).

## Решения (принято до старта)

| Вопрос | Решение | Кто решил |
|---|---|---|
| Скоуп | Титлбар + quick terminal; сплиты отложены | пользователь |
| Горизонтальный сплит в будущем | `cmd+shift+d` — `cmd+h` съедается меню `Hide` | пользователь |
| Quick-режим | опция конфига, не CLI-флаг | пользователь |
| Хоткей по умолчанию | `ctrl+grave` | пользователь |
| Анимация выезда | нет | пользователь |
| Титлбар | опцией, по умолчанию выключено | пользователь |
| Геометрия quick-окна | верх активного экрана, вся ширина, 40% высоты, без опций | командир |
| Скрытие при потере фокуса | да | командир |
| `activationPolicy` | остаётся `Regular` | командир |

## Дефект плана, починенный до старта

«Окно стартует скрытым» было записано в T4, но показ живёт в `application.cpp`,
которым в той же волне владеет T3 — две задачи одной волны полезли бы в один
файл. Перенесено в T1 (она этим файлом уже владеет).

**Важная находка R2-qa — контраст вкладок при несогласованных темах.**
`ui_csd_tabs.mm:246` красит фон окна в `opts->bg` из конфига, а неактивные вкладки,
глифы и хайрлайны (`:326-328`) рисуются системными `NSColor.labelColor` /
`secondaryLabelColor`, которые следуют за **системной темой**. Измерено по WCAG:
светлая тема + дефолтный `bg #2e3440` → **1.60:1** (глифы 1.39:1); тёмная тема +
`bg #ffffff` → **1.00:1**, невидимо. Минимум — 4.5:1. Вместе с хайрлайнами исчезают
границы вкладок, остаётся полоса на фоне без опоры.

Тот же класс проблемы уже чинили в этом файле (комментарий `:321-325`, issue 84,
1.16:1) — вернулся, потому что фон титлбара стал произвольным.

**Почему не поймать руками здесь:** на этой машине системная тема тёмная и
дефолтный `bg` тоже тёмный — «здесь и сейчас» всё выглядит нормально.
Лечение — `window.appearance` по яркости `bg`, одна строка. Передано в F2.

**Что R2-qa подтвердил:** поведение по умолчанию не изменилось (разобраны все три
новые ветки, при `transparentTitlebar=false` выражения тождественны прежним);
`FullSizeContentView` не появился, геометрия не тронута; утечки listener нет
(`listener.cpp:13-15`); утверждение T2 про клики и таскание верно — в диффе нет
изменений в `mouseDown:`, константах хит-теста и `mouseDownCanMoveWindow`.
Регрессий нет: те же 11 узлов, `pytest tst/test_config.py` — 20 passed.

Уточнение к граблям со стилем: **сам `./style.py` брейс конструктора не схлопывает**
(второй проход `restore_constructor_braces` возвращает его) — проблема возникает
только при прямом вызове `clang-format`.

Решение T2 по вкладкам: при `transparentTitlebar` активная вкладка рисуется не
заливкой `opts->bg` (она стала бы неотличима от слитого фона), а полосой 2px
снизу цветом курсора `opts->cr`.

### R3-sec круг 3

- **S6 закрыта, и сильнее, чем через инвариант уровня.** После `[NSApp hide:]` окна
  ordered out → `window.visible == NO` → гейт отказывает независимо от оставшегося
  `level`. Замерять `[NSApp hide:]` для этого вывода больше не нужно. Остаточный
  уровень 25 у скрытого окна привилегии не даёт: вернуть окно может только человек
  или `requestShowAt`, который 25 и так ставит. Оговорка: предпосылка «после `hide:`
  `visible == NO`» взята из семантики AppKit, а не из замера.
- **Легитимный путь не сломан** — разобран по состояниям (показано хоткеем, скрыто,
  до первого показа, деградированный режим F3a, свёрнутое). Осознанное следствие:
  после Cmd-H программа в шелле уже не поднимет приложение через `CSI 5 t` — это и
  есть цель, но это отличие от обычного окна.
- **S7 (новая, замечание с условием повышения):** гейт защищает **метод**, а надо
  **свойство** «ни одна операция из потока не выводит скрытое quick-окно». Из восьми
  операций две идут мимо: `CSI 1 t` → `requestRestore()` → `[window deminiaturize:]`
  (`:1376`) и `CSI 10;1 t` → `requestFullscreen()` → `[window toggleFullScreen:]`
  (`:1419`), причём на скрытом окне условие `current != value` там выполняется всегда.
  Фактическое поведение — за AppKit, по коду не выводится. Довод, что
  `toggleFullScreen:` откажет: у quick-окна `collectionBehavior` **без**
  `FullScreenPrimary`. Остальные шесть операций разобраны и чисты.
- Комментарии F5 проверены по существу: обе исправленные формулировки верны, но
  «closes that path» / «closed in F5» сказаны безоговорочно, а верны только для
  `CSI 5 t` — сузить.

**Решение командира по S7 → F6:** тот же гейт в `requestRestore()` и
`requestFullscreen()`, симметрично F5, четыре строки в том же файле.

**Почему не по рекомендации проверяющего.** Он предлагает объективно лучшее
решение — один гейт в `VtermImpl::windowOperation` (игнорировать операции 1, 5, 10
при `quick`): одно место, читаемое правило, вендорный слой не трогается. Но
`vterm.cpp` **вне скоупа плана**, это чужая подсистема, и заход туда — решение
пользователя, а не командира. Рекомендация уходит в «Отложено» итогового отчёта как
правильное направление на будущее.

**Эталон падающих узлов — окончательная формулировка (R3-qa круг 3):**
**12 узлов при не-ASCII активной раскладке, 11 при ASCII.** Правило «сверять имена,
а не счётчик» это покрывает.

Причина найдена и детерминирована: активная раскладка на машине — **Russian**.
Тест `ShiftedPrintableKeepsBothLayoutLevelsOnRelease` ждёт `layoutCodepoint == 'a'`
для `kVK_ANSI_A`, а код при Shift берёт layout из
`[event charactersByApplyingModifiers:0]` (`platform_cocoa.mm:2210-2215`) — то есть из
**активной** раскладки, где физическая A даёт «ф». Соседний assert на
`baseCodepoint` проходит, потому что идёт через `asciiBaseCodepoint()` с
ASCII-capable раскладкой (`:1892`). 8 прогонов подряд — `ERR: 1` каждый раз;
изолированный прогон только этой suite — тот же красный, значит **от порядка и
потоков не зависит**. Утверждение F5 про «флейк по потокам, `OK: 54`» неверно —
у него в тот момент активной была ABC.

Системную раскладку проверяющий **не переключал** — это среда пользователя, а
доказательство замкнуто и без этого. Правильное решение.

**Предыдущая формулировка (устарела): эталон 12, а не 11.** Проверено правильно — на чистом
`master` `b2cb0f58` в свежем worktree с **пустым кешем** `./build test -k` даёт те же
`12 node(s) failed, 30 broken` и тот же 12-й узел (`plt-tests.stamp` →
`PlatformCocoaKey::ShiftedPrintable…`, зависит от активной раскладки). Множества
сверены программно: имена падающих python-тестов идентичны, расходятся только
номера шардов (волна добавила тесты в `tst/test_config.py`, раскладка по 20 шардам
сдвинулась). **Сверять имена, а не счётчик** — счётчик зависит от того, что взялось
из кеша, а что пересобралось. Метод F4 (`git stash`) признан негодным: он убирает
дифф и одновременно возвращает прогретый кеш, то есть не отделяет причины.

**Замечание:** на низкоконтрастных схемах блендинг делит контраст самой схемы —
Solarized Light `idleText` 2.07, глифы 1.68. Деградация пропорциональна выбору
пользователя (при активном тексте 4.13 приглушённый физически не может быть ярче)
и одинакова в обеих темах, тогда как до F2 та же схема давала 1.00 независимо от
собственного контраста.

**Флак `cmd+1` — не регрессия, доказано дважды.** Через `keystroke "1" using
command down` заголовок не менялся 5 раз из 5; через `key code 18 using command
down` — та же клавиша, другой способ доставки — сработало сразу (`[2/2]` → `[1/2]`),
и на чистом `master` тот же результат. По диффу `master..400feada` нет ни
`input_bindings.cpp`, ни `composer.cpp`, ни `session.cpp`, ни `input_remap.cpp` —
регрессия невозможна по построению.

**Находка R3-test (важная) — и она сошлась с находкой R3-sec.**
`parseQuickHotkey()` в `ui_quick_hotkey.mm` — `static`-функция в анонимном
namespace, нигде не объявленная: **физически не покрывается юнит-тестом**.
Требование плана «покрыть разбор чорда тестами» выполнить буквально не удалось.

Цена пробела подтверждена независимо: **S1 из R3-sec** (чорд без модификатора,
`quickHotkey = "space"`, молча захватывает клавишу во всех приложениях) — ровно
тот случай, который юнит-тест «клавиша без модификатора» поймал бы до ревью.
Два проверяющих пришли в одну точку с разных сторон.

Готовая форма от R3-test: вынести парсер в `quick_hotkey_chord.h`/`.cpp` (обычный
`.cpp` без Objective-C — попадёт под существующий glob `unit_sources` **без правки
`build.py`**), оценка ~30 минут, риск нулевой. → **F3c**, после F3a (тот сейчас
владеет `ui_quick_hotkey.mm`).

Что R3-test покрыл: 4 теста на `toggleQuickWindow()` (`application_ut.cpp`),
включая регрессионный на находку про свёрнутое окно; 1 тест на `visible()` — взят
готовым из отчёта R1-qa round2. Чувствительность проверена 3 мутациями.

**Замечание по среде (методическое):** параллельные исполнители работали в одном
рабочем каталоге, без git worktree — отсюда и гонка индекса у F3b. Файлы не
пересеклись только потому, что границы владения соблюдались вручную. На будущих
волнах параллельным исполнителям стоит выдавать worktree.

**Побочно:** `plt_unit_tests --threads=1` детерминированно валит 6 тестов
`FiberSchedulerPlatform` — артефакт инструмента (планировщику волокон нужна
настоящая многопоточность), не регрессия. Официальный вызов без флагов даёт `OK: 54`.

**Находки R3-sec (блокирующих нет):**

- **S1** (важная, → F3a): чорд **без модификаторов принимается молча**.
  `quickHotkey = "space"` даёт `RegisterEventHotKey(key, 0)` с `noErr` (замерено) —
  терминал перехватывает одиночную клавишу во всех приложениях системы.
- **S2** (важная, → F3a): при нераспознанном или незарегистрированном чорде
  **quick-окно недостижимо навсегда** — шелл внутри живой и невидимый. **На Linux
  наступает всегда**: опция есть, модуль хоткея macOS-only, `requestShowAt` заглушка.
  Решение командира: окно не должно оставаться недостижимым — при отсутствии
  хоткея печатать диагностику и показывать окно обычным образом.
- **S3** (важная, → F3b): `NSStatusWindowLevel` усилил давнюю `allowWindowOps` —
  `CSI 5 t` **из потока данных** (ssh, `cat` файла) поднимает окно поверх чужого
  фуллскрина и уводит фокус. Не блокер: опция по умолчанию выключена.
- **S4/S5** (замечания): **критерий приёмки T3 был негодным.** «После `kill` чорд
  свободен, второй процесс регистрируется без already taken» ничего не проверяло —
  два одновременно живых процесса регистрируют один чорд и **оба получают `noErr`**
  (замерено). Тест прошёл бы и без снятия регистрации. Наблюдаемая замена: после
  `kill -9` нажать `ctrl+grave` в редакторе и увидеть ввод символа. Плюс подсказка
  «(already taken?)» уводит диагностику не туда.

**Что R3-sec перепроверил и признал чистым:** гейт на `quick = true` сквозной;
разбор чорда прошёл ASan/UBSan-фаззинг (300k входов, буферы без `\0`, 1 MiB мусора)
без выходов за границы; ввод нигде не логируется; **экран блокировки перекрыть
нельзя** (`NSStatusWindowLevel` = 25 против `CGShieldingWindowLevel` = 2147483628,
замерено); решение T4 со снятым `Miniaturizable` подтверждено пробником — `miniaturize:`
тоже no-op, тупика через `CSI 2 t` нет; `gitleaks` по обоим диапазонам чисто.

**Моя ошибка в постановке T3:** сослался на `dev/make_app.sh`, не оговорив, что он
в ветке `feat/macos-app-bundle`, а не здесь. Исполнитель файл не нашёл и построил
обход (взял бандл-скелет из рабочего дерева — это был мой след от проверки того
скрипта) вместо того, чтобы остановиться и спросить. Обход безобидный, результат
эквивалентен, но мог дать ложную уверенность. `Pretty.app/` из дерева убран
(`fa366e9c` — git-гигиена командира).

**Передать в T4 при постановке** (находки R1-qa круг 2, проверенные на живом API):

- Свёрнутое в Dock окно `isVisible` считает **видимым** (`after miniaturize = 1`).
  На свёрнутом quick-окне хоткей спрячет вместо показа — обработать явно.
- `WindowHeadlessImpl::requestClose()` не сбрасывает `shown_`.
- Корректность `visible()` не зависит от дисциплины T4: прячет ли она через
  `requestHide()` или напрямую `orderOut:`, `isVisible` станет `NO` в обоих случаях.

**Передать в T3:** `visible()` пока нигде не вызывается — T3 будет первой. Готовый
текст теста, ловящего обе мутации, лежит в конце
`docs/plans/reviews/window-chrome-R1-qa-round2.md`, R3-test может взять как есть.

**Передать в R3-test:** уточнить формулировку контракта `visible()` в `window.h`
под Wayland («true between requestShow() and the next requestHide()» расходится с
тем, что `requestHide()` там no-op) и перенести предупреждение про сброс `shown`
в тело `requestHide()` — править будет тот, кто возьмётся за настоящий Wayland-hide,
а предупреждение стоит не там. Плюс в `requestShow()` есть ранний выход

и окно, которое не показывается обратно.
