## Задача

Семь фич: скруглённые углы, запоминание фрейма и фуллскрин quick-окна; боковая
панель вкладок справа с `cmd+b`; автоскрытие оформления по ховеру; сплиты
панелей внутри вкладок. Три фундамента под ними: асимметричные отступы,
геометрия в `Vterm`, контракт рендерера.

## Решения пользователя

| Вопрос | Решение |
|---|---|
| Скоуп | Всё, включая сплиты |
| Вкладки и сплиты | Панели **внутри** вкладок (как iTerm2/Ghostty/Warp) |
| Боковая панель | Плоский список **только вкладок** |
| Геометрия quick после ручного сдвига | **Сохранённое побеждает** `quickGeometry` |
| Фуллскрин для TUI | Отдельным хоткеем, не автоматически |

## Исправленное недоразумение

Пользователь сообщил, что «не работают сплиты по `cmd+d`/`cmd+shift+d`».
Проверено: в коде **ноль** действий `Split`/`Pane`, `cmd+d` не привязан ни к
чему. Сплиты были явно вынесены за скоуп в первой работе (пользователь выбрал
«дешёвое сначала»), а `cmd+shift+d` обсуждался как **выбор клавиши на будущее**,
потому что `cmd+h` съедается системным меню `Hide`. Это не регрессия.

## Бесплатное, что пользователь уже может

`border = 4` в конфиге — паддинг вокруг текста, опция существует с дефолтом 2.
Симметричная: добавит отступ и сверху/снизу.

**Модуль T2** (`lib/shitty/quick_frame_store.h`) — контракт для T3:

```cpp
struct QuickFrame { i32 x = 0; i32 y = 0; u32 width = 0; u32 height = 0; };
bool defaultQuickFramePath(stl::StringView configPath, stl::StringBuilder& out);
bool loadQuickFrame(stl::StringView path, QuickFrame& out);
bool saveQuickFrame(stl::StringView path, const QuickFrame& frame);
```

Путь берётся от `composer.opts->configPath` (учитывает `-config`, XDG, HOME), расширение
меняется на `-quick-frame` в той же директории — бренд не нужен. Формат — `key=value`
построчно, не TOML. Повреждённый или неполный файл трактуется как **отсутствующий целиком**,
частичного применения нет. Клэмп против живого экрана и приоритет «сохранённое побеждает
`quickGeometry`» — на стороне T3, модуль про экран не знает.

Атомарность: временный файл `path + ".tmp." + getpid()` в той же директории → `rename()`.
Pid в имени намеренно — два процесса `quickCompanion` не столкнутся. **Доказано
экспериментом:** `chmod 0500` на каталог между сохранениями → save падает, старый фрейм цел,
временного файла не осталось (проверено `access()`). Чувствительность — две мутации.

**Точка остановки, помеченная T1 и переданная T3:** если для уведомления о перемещении и
ресайзе понадобится новый виртуальный метод в `Window`/`WindowEvents` — это расширение
контракта за пределы волны; T3 обязана остановиться и спросить, потому что на `window.h`
заложились пять следующих волн.

**Наблюдение по тестам:** у T2 базис дал 13 узлов вместо 14 — `plt-tests.stamp` прошёл сам.
Это флакующий 120-секундный таймаут враппера, а не тесты: прямой прогон `plt_unit_tests`
даёт `OK: 54`. Ещё одно подтверждение правила «сверять имена, а не счётчик».

**Контракт, зафиксированный T1** (девять следующих задач используют как есть):

- Опции: `quickCornerRadius` (u16, 0..1000, деф. 0), `sidebarWidth` (u16, 1..3000, деф. 220),
  `quickFullscreenHotkey` (строка, пусто = выключено), `quickRememberFrame` / `sidebarTabs` /
  `autoHideChrome` / `panes` (bool, все `false`).
- `struct Insets{top,right,bottom,left}` и `Composer::contentInsets()` в `composer.h`;
  сейчас возвращает симметричный `border` — поведение не меняется.
- `struct PixelRect`, `struct PaneUpdate{PixelRect area; const TerminalUpdate& update;}` в `composer.h`.
- `plt::WindowOptions.quickCornerRadius` — единственное поле, реально нужное слою `ext/plt`.

**Отклонение от буквы плана, принято:** план писал `stl::Span<const PaneUpdate>`, но
`stl::Span` в кодовой базе **не существует** (проверено командиром — `grep` по `ext/libstd/`
пуст). Контракт для T8 задокументирован как `update(const PaneUpdate* panes, size_t count)` —
идиома указатель+счётчик, как у `Darts::create` и `ConfigSink`. Развилка `A2` (список вместо
машины состояний `beginFrame`/`endFrame`) не менялась.

**Решение T1, оставленное T3:** шесть опций из семи не идут через `WindowOptions` —
`platform_cocoa.mm` не инклюдит `lib/shitty` вообще. Если T3 понадобится новый виртуальный
метод в `Window`/`WindowEvents` ради `quickRememberFrame` — это расширение контракта за
пределы волны, то есть **точка остановки**, а не тихая правка.

**Ловушка, найденная T1:** `./build -j 8 st pt` **не пересобирает `st_test`** — его надо
собирать отдельно, иначе `pytest` гоняется по старому бинарю.

`R1-test` и `R1-sec` не заводятся: волна не добавляет исполняемой логики, только
разбор опций — его покроет `R2-test` вместе с первой реальной фичей.

### R1-qa — вердикт: готово с замечаниями, блокеров нет

Замеры делались в двух отдельных `git worktree` (проверяемый `a4331e69` и эталонный
`60d4808e`), рабочее дерево не трогалось — работа T2 в них не попала. Сверка по именам:
регрессий ноль.

**Две находки ударили по T3, которая работала в этот момент — решения приняты на ходу:**

1. **`quickCornerRadius` применяется при создании окна** (`window.h:149-153`), а T3 делает
   фуллскрин, где углы надо убрать и вернуть. `setCornerRadius()` в `plt::Window` нет, а
   `window.h` был у T3 только на чтение — то есть точка остановки посреди волны.
   → **Решение: `ext/plt/window.h` передан T3 во владение на волну 2**, разрешено добавить
   `setCornerRadius()` и **только его**, с реализацией во всех трёх бэкендах. Параллельных
   задач в файле нет.
2. **`WindowEvents` содержит только `close()`**, колбэков на move/resize нет, а `A6` требует
   «подписаться на перемещение и ресайз».
   → **Решение: новый колбэк не заводить.** `plt::FrameCallback::frame(const WindowInfo&)`
   (`window.h:122-125`) зовётся каждый кадр и приносит `x`, `y`, `width`, `height`,
   `fullscreen`, `contentScale`; плюс `Window::info()`. Сравнения прошлого и текущего фрейма
   достаточно.

**Важная находка, предотвратившая двукратный промах на волне 4 → F1 (запущена):**
единицы `Insets` не были зафиксированы. `borderPixels()` = `opts->border * contentScale`, то
есть **backing pixels**, а `sidebarWidth` документирован «in points» без слова о пересчёте.
На Retina T5 зарезервировала бы 220 пикселей под панель шириной 440 — дословный провал её
критерия «текст не заезжает под панель» плюс двукратный промах хит-теста. Зафиксировано в
плане и чинится в комментариях `composer.h`.

**Что приёмка проверила не рассуждением:**

- Идиома `update(const PaneUpdate* panes, size_t count)` — **probe-компиляцией отдельного TU**:
  агрегат на стеке собирается, `stl::Vector<PaneUpdate>` с `pushBack` компилируется,
  `data()` даёт ровно `const PaneUpdate*`. Ограничение зафиксировано негативным probe:
  `panes.mut(i) = ...` не компилируется (ссылочное поле). Для T8 не помеха — список
  собирается `pushBack`-ом. **Решение командира: ссылку сохраняем**, соответствует `A2`.
- Соответствие конвенциям — не догадка: pointer+count используется в чисто виртуальных
  методах `VtermHeadless::feed`, `FontPack::resolveFace`, `Pty::send`, `TomlSink::tomlKey`,
  `Darts::create`.
- `PixelRect` вместо `Rect` — **улучшение контракта**: `Rect` (`rect.h:11-19`) это пара
  `Point` в координатах **ячеек**, живёт в выделении текста. Пиксельный прямоугольник под тем
  же именем был бы миной для T4 и T10.
- Поведение по умолчанию — по наблюдаемому протоколу: `diff` ответов `OPTIONS` между
  эталоном и `a4331e69` нулевой по всем прежним полям.
- Валидация границ — 12 запусков, `rc=255` и тексты в формате существующей опции `border`.
  **Для будущих проверяющих:** `-version`/`-help` короткозамыкают разбор **до** валидации,
  поэтому `./st -sidebarWidth 0 -version` даёт `0` — проверять надо без них.
- Em dash `U+2014` подтверждён **побайтово** во всех 14 новых строках обоих конфигов.

**Следствие для T3, переданное ей:** разбор чорда `quickFullscreenHotkey` **нельзя проверить
через `OPTIONS`** — `harness.options()` (`tst/harness.py:259-268`) разбирает значения через
`int(value)`, строку туда не положить. Нужен hex-ответ по образцу `ARGV` либо ручной сценарий
для R2-qa.

**Замечания, исправленные в плане командиром:** `./style.py` → **`dev/style.py`**; перенос
тела `contentInsets()` в `composer.cpp` назначен **T5**, а не T4 (T4 не владеет `composer.h`);
единицы `Insets` зафиксированы в разделе «Контракты»; ограничение `PaneUpdate` записано там же.

### Блокеры R2-qa (все воспроизведены прогоном)

**B1. Единицы: точки против backing pixels** (`application.cpp:602-626`).
`WindowInfo` **смешивает единицы по конструкции**: `x`/`y` — точки, `width`/`height` —
backing pixels контента, `screenPixel*` — backing pixels; `requestMove` берёт точки,
`requestResize` — пиксели. `applySavedQuickFrame()` клэмпит точечной границей экрана **и**
пиксельный размер, **и** точечную позицию. При `contentScale = 2`: сохранённые `3840×2160`
восстанавливаются как `1920×1080`, позиция `1400,300` — как `0,0`.
**На любом Retina размер режется вдвое.** Живой прогон T3 не увидел, потому что основной
монитор машины — внешний 3840×1080 при scale 1. Ровно тот класс дефекта, ради которого F1
писала предупреждение в `composer.h`.

**B2. Позиция уезжает вниз на 80 pt за цикл показа.** Шесть циклов, файл состояния:
`y=330 → 250 → 170 → 90 → 10 → −70`. Причина **на стороне применения**: `requestMove`
синхронный, `requestResize` асинхронный, origin ставится при старой высоте, `setContentSize:`
держит верхний край; плюс origin **рамки** лежит рядом с размером **контента**.
Приёмка предупредила: менять способ сохранения бесполезно.

**B3. Фуллскрин разворачивает, но никогда не складывает.** Условие свёртки
`NSEqualRects(window.frame, screen.frame)` недостижимо: AppKit ужимает рамку титульного окна
под меню-бар — замерено `3840×1050` против `3840×1080`. Каждое нажатие затирает
`priorFullscreenFrame` уже развёрнутым кадром. Четыре прогона, до шести нажатий — ни разу.
Разворот при этом корректен: PTY 20 → 53 строки.
**Побочно:** восстановление радиуса углов из `05c3e9f7` стоит в этой недостижимой ветке —
окно теряет скругление **насовсем** после первого фуллскрина.

### Решение командира

**Фуллскрин-чорд не должен писаться в `quickRememberFrame`.** Живой прогон показал: ручной
кадр пользователя (`400,200,1000×400`) затирается фуллскрин-кадром `0,0,3840×388`. Опция про
**ручную** установку; развёрнутый на весь экран кадр ею не является.

### Тесты волны слепы к B1

Мутация «исправить единицы» **не роняет ни один** из четырёх тестов `ToggleQuickWindow::*` —
headless жёстко ставит `contentScale = 1.0f`. Фикс без нового теста не удержится; F2 обязана
завести регрессионный тест на `contentScale = 2` и проверить его чувствительность.

### Что приёмка подтвердила зелёным

Главный критерий волны выполнен: **26 показов** на бинаре волны и 26 на эталонном — все дали
`x=0 y=30 w=3840 h=420 layer=25`. `./build test -k` — одинаковые наборы падающих узлов,
регрессий ноль. `unit_tests` 686/682, разница ровно в четырёх новых тестах.

### Прорыв метода: живой прогон всё-таки возможен

Приёмка добралась до того, что не далось T3. **Ключ — не трогать `System Events`/AppleScript
вообще.** Геометрия — `CGWindowListCopyWindowInfo` из Swift-программы; чорды —
`CGEvent.post(tap: .cghidEventTap)` (26 из 26 доходят, глотается только первое нажатие после
старта); ручной сдвиг окна — `AXUIElementSetAttributeValue`; размер сетки TUI —
`stty -f /dev/<tty дочернего> size`. **F2 поручено оформить это скриптом в `dev/`** — следующим
волнам сэкономит дни.

### Отменённая директива командира

Я передал рекомендацию приёмки волны 1 («ловить перемещение через `FrameCallback::frame()`»)
как директиву, не проверив частоту вызова. Исполнитель возразил: `frame()` — **покадровый
колбэк рендера** (`window.h:122-125`, «returns true when a frame was submitted»), при живом
перетаскивании писал бы на диск десятки раз в секунду без дебаунса. Проверил — довод верный,
директиву отменил, решение через `NSWindowDidResignKeyNotification` осталось.
R2-qa независимо перепроверила и **сняла собственную первую формулировку**: `frame()`-путь
B2 бы **не предотвратил**, сдвиг целиком на стороне применения.

**Урок:** рекомендация проверяющего, превращённая в директиву без проверки, стоит исполнителю
переделки.

### I7 — четвёртая находка, донесена в F2 на ходу

`requestCornerRadius()` (`platform_cocoa.mm:1610-1611`) помимо радиуса пишет **`window.opaque`
и `window.backgroundColor`**. Ту же `window.backgroundColor` пишет
`CsdTabsUi::applyTitlebarColor()` (`ui_csd_tabs.mm:246`) при `transparentTitlebar`.
**Два слоя, одно свойство AppKit, арбитра нет.**

1. **`transparentTitlebar` + `quickCornerRadius` — скругление гасится.** `createWindow()`
   (`application.cpp:720`) ставит `clearColor`, `createCsdTabsUi()` (`:743`) **сразу после**
   заменяет её непрозрачным цветом фона. За скруглёнными углами — залитый прямоугольник,
   ровно тот артефакт, против которого написан комментарий метода. Дефект волны 2
   (`10e24459`), просто раньше некому было заметить.
2. **Фуллскрин-чорд сбрасывает цвет титлбара** — `requestCornerRadius(0)` затирает тинт,
   вернётся только по `SIGUSR1`. Срабатывает **даже при `quickCornerRadius = 0`**.

### Правило «контракт против эскейп-хэтча» — зафиксировано

Выведено приёмкой, принято командиром, F2 поручено записать в комментарий `renderContext()`:

- **через контракт** — то, у чего есть осмысленный ответ на не-Cocoa платформе (радиус на
  Wayland — честный no-op, решать должен бэкенд);
- **через эскейп-хэтч `renderContext().window`** — то, для чего контракт сознательно не даёт
  входа (`requestFullscreen()` на quick-окне не работает намеренно; атомарно поставить рамку
  синхронный `requestMove` + асинхронный `requestResize` не позволяют).

До сих пор правило нигде не было записано — ни в `window.h`, ни у `renderContext()`, где
вообще нет комментария. `I7` показала, что цена уже не теоретическая. **T5 и T6 упрутся в ту
же развилку на волне 4.**

### Ограничения проверки, зафиксированные честно

- Потерю скругления после фуллскрина **живьём подтвердить не удалось**: `kCGWindowIsOpaque` в
  этой macOS в словаре `CGWindowListCopyWindowInfo` отсутствует (проверено дампом всех десяти
  ключей), скриншот недоступен. Вывод держится на том, что вызов физически один и стоит в

проверяемого AppKit-вызова.

(22.1.8) отвергает несколько `-lines` разом.

### Два новых блокера, оба замерены

- **`B6` — `quickRememberFrame` умирает до перезапуска.** `quickFrameScreenGuessed`

### Вердикт приёмки по отклонению `F2c` — принимать нельзя как окончательное

Первая половина довода `F2c` **верна**: при нынешней реализации широкое условие даёт тупик на
уменьшившемся экране — флаг ставится на показе, ручной сдвиг его не снимает, новая расстановка
не запоминается никогда. Но вывод «значит широкое условие невозможно» — **ложная дизъюнкция**:
есть третий вариант, который `F2c` не рассматривала — широкое условие **плюс сброс флага по
`NSWindowDidMove`/`DidResize`**. Подрезали на показе — не пишем; пользователь подвинул — пишем.
Наблюдатель на этом окне уже есть, добавляется одна подписка, и она же закрывает `B6`.
Вторая половина довода **неверна**: сценарий потери данных при найденном экране остался, это
`B7`.

### `L1` — блокер, крупнее всего, что находила приёмка: волна сломала не-Apple сборку

`application.cpp:595` зовёт `applyQuickFrameToWindow()` **без** `#if defined(__APPLE__)`, а она
определена только в darwin-only `ui_quick_hotkey.mm`. `st`, `pt`, `st_test`, `unit_tests` не
линкуются ни на одной не-Apple платформе. Внесено `F2c` (`45eae88d`). Доказано экспериментом:
исключение файла из графа даёт `Undefined symbols: applyQuickFrameToWindow(…) referenced from

гвардом стоят, а этот вызов — нет.

**Почему это не поймали три круга приёмки и CI.** Кросс-компиляция из песочницы недоступна —
все три круга честно писали «Wayland-реализация не проверена компилятором»; ветка на 90
коммитов впереди `origin/master`, Linux-джобы по ней не гонялись. Проверка **аудитом
директив препроцессора** вместо компилятора никому не пришла в голову — а стоила одного
прохода. Правило волнам 3-8: на каждом стыке портируемого и Cocoa-кода проверять гвард
глазами, раз компилятором нельзя.

### Опора для `T6` — единственное, что ей нужно от `T5`

enum class ChromeSide : u8 { Top, Right, Bottom, Left, Count };

**Аргумент в логических точках**, не в пикселях: `contentInsets()` умножает на

### Долг `M14` — теперь достижим, вот как

Два способа получить ненулевой **верхний** резерв, оба названы исполнителем:

1. **Прямо:** `composer.setChromeReserve(ChromeSide::Top, 32);` из любого состояния `Composer`,

   масштабирует `contentInsets()` при чтении, поэтому `setContentScale(2.0f)` сразу даёт
   `contentInsets().top == 64` без повторного вызова.
2. **Через модуль:** `autoHideChrome = true` (и `noDecorations == false`), headless-окно,
   `setGlyphSize()`, затем `createCsdTabsUi()` → `chromeReserve(Top) > 0`. Величину брать не
   числом, а из `chromeReserve(Top)` — это высота титлбара по AppKit.

Оба дают `insets.top > insets.left`, то есть ту самую вертикальную асимметрию. **Владелец
закрытия — `R4-test`.**

### Самый важный критерий проверен, а не заявлен

«Ни одно ожидание существующего теста не подогнано» — исполнитель доказал это механически:
`git show <три коммита> -- <тестовые файлы> | grep '^-'` даёт **ровно две** удалённые строки —
вызов `Vterm::create`, получивший новый обязательный аргумент, и пустое тело
`SecondPtyStub::send`, ставшее записывать отправленное. **Ни один `STD_INSIST` не изменён и не
удалён.** Для ядра проекта это ровно та проверка, которой не хватало бы на слово.

`SIGWINCH`: сквозь настоящий pty (ребёнок ждёт 3 с после ресайза, чтобы запоздавший сигнал
был посчитан) один ресайз → `WINCH|1|80x5`; **контроль на два ресайза** → `WINCH|2|90x6`,
то есть инструмент не залип. На уровне `SessionSet` — один `TIOCSWINSZ` на хендл, оси не
перепутаны, повторный ресайз в тот же размер даёт ноль.

> **Поправка после `R5-test` (находка `T5-1`) — читать вместе с абзацем выше.** Замер сигналов
> к тому дефекту, от которого защищает критерий, **слеп**. Мутации `M1` (`session.cpp:438`,
> `handle->resize()` дважды — буквально «лишний холостой прогон», о котором предупреждает план)
> и `M1b` (фантомный `1x1` перед настоящим) **обе оставляют замер на `WINCH|1`**. Механизм
> POSIX: повтор `TIOCSWINSZ` с тем же размером не сигналит вовсе, а два сигнала до
> планирования процесса сливаются в один. Контроль на два ресайза показывает, что счётчик жив,
> но **не** что он различает дефект — `R5-test` подтвердил это отдельным опытом на голом
> `pty.fork()` с ребёнком на C: два ресайза подряд дают то `2`, то `1`.
>
> **Критерий выполнен, но доказывают его не сигналы**, а два юнит-счётчика:
> `SessionSet::EachResizeCostsEveryShellExactlyOneWinsize` и
> `VtermHeadless::ReportsOneInBandResizePerWindowResize` — обе мутации убиты ими.
> Волнам 6-8: «ровно один `SIGWINCH`» проверяется счётчиком `TIOCSWINSZ` и счётчиком отчётов
> `CSI 48`, а не счётчиком сигналов у ребёнка.

### Опора для `T9`/`T10` — начало панели отдельно от отступов окна

`lib/shitty/mouse_frontend.h`: `MouseGeometry` носит `int paneOriginX` / `int paneOriginY`
рядом с `Insets insets`; складываются они **только** в `contentLeft()` и `contentTop()`.

однопараметрическая форма сохранена и означает «панель во всё окно». Ровно то разделение,

## Отложенная задача по `Pty` — закрыта второй сессией. Вердикт: **тест, не продукт**

Ветка `fix/pty-resize-oracle` от `650da24f` (коммиты `ba7e77e3`, `f8de3c90`), отчёт
`docs/reports/Pty-resize-oracle-2026-08-19.md`. `lib/shitty/pty.cpp` **не менялся ни строкой**;
правка целиком в `tst/pty_test_helper.c`, +45 строк, из них кода около 18.

**Причина №1 — почему `SIGWINCH` не приходил вовсе.** У `SIGWINCH` действие по умолчанию —
«игнорировать», а XNU отбрасывает сигнал с диспозицией `SIG_IGN` **при генерации**, проверяя
это раньше маски блокировки. Процесс, ни разу не сменивший диспозицию, не может получить
`SIGWINCH` никак — ни обработчиком, ни `sigwait()`. Хелпер делал всё по учебнику (заблокировал,
напечатал `ready`, ушёл в `sigwait`) и **именно поэтому** не работал. На Linux заблокированный
сигнал не считается игнорируемым — тот же код работает; отсюда и то, что дефект вылез ровно
тогда, когда волна 2 впервые скомпилировала этот файл на macOS.

Доказано **вне продукта**: изолированная репродукция повторяет `PtyImpl::spawn` посимвольно и
воспроизводит падение, попутно закрыв версию «сигнал уходит не туда» — ребёнок **является**
передней группой процессов терминала. Различающий опыт: тот же код ожидания, единственная
разница в диспозиции — по умолчанию `ALARM`, с пустым обработчиком `47 123`.

**Причина №2 — `OwnerDeathReleasesBlockedIoAndHangsUpChild`.** На macOS канонический pty не
даёт обратного давления вообще: измерено — **64 MiB приняты без единого `EAGAIN`**, в сыром
режиме `EAGAIN` наступает на 1022 байтах. Первый зонд был на продукт (инструментирована ветка
`EAGAIN` в `send()`) — не срабатывала ни разу, то есть продукт паркуется правильно, просто
переполнения не наступает. Хелпер теперь переводит свой tty в сырой режим до `ready`, как это
делает любая настоящая оболочка.

**`alarm(10)` не тронут** — исполнитель сперва выяснил, зачем он: превращает «сигнал не пришёл»
из зависания `unit_tests` в падение теста. Остаётся предохранителем; с починкой не срабатывает
вовсе, и прогон `unit_tests` сократился **с 10.4 с до 0.36-0.50 с** — те десять секунд были
ожиданием тревоги.

### Что это купило — не два зелёных теста, а живой оракул

Четыре мутации, четыре красных, каждая роняет ровно один тест. Две из них **продуктовые**:
`C` — `resizePty()` меняет `ws_col` и `ws_row` местами; `D` — `PtyHandleImpl::resize()` вообще
не зовёт `ioctl`. **Обе до этой правки проходили бы зелёными.** Единственный сквозной оракул
пути, который перестроила волна 5, снова работает.

`pty.cpp` и не лечится в нём — ребёнок обязан читать, — но выглядит как потеря данных и

ядра в отчёте помечены как механизм, объясняющий числа, а не как прочитанные исходники.
