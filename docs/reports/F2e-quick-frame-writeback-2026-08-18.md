## `L1` — блокер платформы, чинится первым

`applySavedQuickFrame()` звала `applyQuickFrameToWindow()` **вне какой-либо условной
компиляции**, а определена та только в darwin-only `ui_quick_hotkey.mm` (`build.py:660-666`).
`st`, `pt`, `st_test`, `unit_tests` не линковались ни на одной не-Apple платформе — через
`toggleQuickWindow()`, которая вызывается безусловно. Внесено `F2c` (`45eae88d`).

Cocoa-ветка обёрнута в `#if defined(__APPLE__)` — ровно как соседние вызовы
`createQuickHotkey()`/`createCsdTabsUi()` ниже по файлу; портируемый путь остаётся вне darwin
единственным, чем он и задумывался.

### Чем проверено, раз компилятора нет

Кросс-компиляция в этой среде недоступна, а эксперимент тестового инженера (убрать
`ui_quick_hotkey.mm` из графа) **не различает до и после**: на macOS `__APPLE__` остаётся
определён, поэтому обёрнутый код всё равно компилируется и символ всё равно требуется. Я это
проверил — вывод линкера после починки побайтово тот же, что до неё.

Различающая проверка — **аудит директив препроцессора**. Скрипт обходит каждую не-`.mm`
единицу трансляции, отслеживает вложенность `#if`/`#elif`/`#else`/`#endif` и сообщает о всяком
вызове символа, объявленного в `ui_quick_hotkey.h` или `ui_csd_tabs.h`, вне блока `__APPLE__`
(строки-комментарии пропускаются):

```
до починки:    UNGUARDED lib/shitty/application.cpp:595  applyQuickFrameToWindow
               unguarded calls: 1     exit=1
после:         unguarded calls: 0     exit=0
```

**Мои собственные правки `B6`/`B7` проверены тем же аудитом** — командир просил отдельно, и
основание есть: правка живёт ровно на стыке портируемого и Cocoa-кода. Ноль незащищённых
вызовов. Единственный новый символ, который `application.cpp` теперь зовёт,
`quickFrameRegridExtent()`, определён в портируемом `quick_frame_store.cpp` и на darwin не
завязан.

## `B6` и `B7`

### Что было не так

**`B7`.** Экран искался по одной точке — origin рамки:

```objc
    for (NSScreen* const candidate in [NSScreen screens]) {
        if (NSPointInRect(origin, candidate.frame)) {
```

Окно, стоящее на стыке двух дисплеев (или просто свисающее с края экрана), имеет origin на
одном из них. Экран **находился**, значит `quickFrameScreenGuessed == false`, значит защиты не
было; `quickFrameTarget()` подрезала всю рамку в `visibleFrame` этого экрана, и подрезанное
скрытие писало на диск.

**`B6`.** `quickFrameScreenGuessed` присваивался только внутри `applyQuickFrameToWindow()`, а
`applySavedQuickFrame()` до неё не доходит, если файла состояния нет (ранний `return` после
неудачного `loadQuickFrame()`). После показа кадра с отключённого дисплея флаг оставался
`true` навсегда: `quickRememberFrame` переставал сохранять, а документированный сброс —
удалить файл — делал только хуже.

### Три новые чистые функции

Рекомендация 6 круга 3 дословно просила вынести решение «писать или не писать» в чистую
функцию рядом с `quickFrameTarget()` и покрыть её. Вынесены обе решающие точки, а не одна:

```cpp
double quickFrameOverlap(const QuickFrameRect& a, const QuickFrameRect& b);
bool quickFrameFitsScreens(const QuickFrameRect& frame, const QuickFrameRect* screens, size_t count);
bool quickFrameShouldSave(bool computed, const QuickFrameRect& computedFrame, const QuickFrameRect& live);
```

`quickFrameFitsScreens()` — «весь ли кадр лежит на подключённых дисплеях». Сумма пересечений
кадра с **полными** рамками экранов (`NSScreen.frame`, не `visibleFrame`), сравнение с
площадью кадра. Точный дубликат рамки пропускается: зеркалирование — единственная раскладка,
где два экрана отдают одну и ту же рамку, и без пропуска окно, наполовину свисающее с дисплея,
считалось бы покрытым целиком.

Почему `frame`, а не `visibleFrame`: кадр на стыке по построению заходит в полосу меню
соседнего экрана. У пары мониторов приёмки встроенная панель занимает по y `−1117…0`, её
`visibleFrame` — `−1117…−32`; полоса `−32…0` не покрыта ничьим `visibleFrame`. По `visibleFrame`
кадр на стыке «не помещается» — и `B7` не чинится.

`quickFrameShouldSave()` — «писать ли при скрытии». `false` ровно в одном случае: окно **всё
ещё** тот кадр, который вычислил этот показ.

### Перестроенная `applyQuickFrameToWindow()`

```objc
    QuickFrameRect target = saved;
    const bool fits = quickFrameFitsScreens(saved, screenFrames.data(), screenFrames.length());
    if (!fits) {
        …экран с наибольшим пересечением, иначе window.screen/mainScreen…
        target = quickFrameTarget(frame, visible, titlebarHeight);
    }
    [window setFrame:… display:YES animate:NO];
    quickFrameComputed = !fits;
    quickFrameComputedFrame = window.frame;
```

1. Кадр, целиком лежащий на подключённых дисплеях, применяется **дословно** — `B7`.
2. Кадр, частично оказавшийся в никуда, получает экран по **наибольшему пересечению**, а не по
   попаданию origin. Это лечит и симметричный случай: кадр, в основном лежащий на одном
   дисплее, но левым верхним углом заехавший на другой, раньше втаскивался в меньшую свою часть.
3. Защита стала широкой: не «экран не найден», а «кадр вычислен этим показом», и хранится не
   флаг, а сам вычисленный кадр.

`[NSScreen screens]` спрашивается один раз и держится в локальной переменной: два цикла обязаны
сходиться в том, какая рамка какому экрану принадлежит.

### Отступление от рецепта приёмки

Приёмка назвала: «широкое условие защиты **плюс** сброс флага по
`NSWindowDidMoveNotification`/`NSWindowDidResizeNotification`». Широкое условие сделано,
подписки на нотификации нет — вместо неё сравнение кадров.

Причина: сразу после `applyQuickFrameToWindow()` тот же `applySavedQuickFrame()` делает
`composer.resize(...)` — пересчёт сетки после кросс-масштабного восстановления, добавленный
`F2c`. Этот пересчёт меняет размер окна, то есть постит ровно те `DidMove`/`DidResize`, по
которым флаг предлагалось снимать. Флаг снимался бы на **нашей собственной** правке кадра, и
скрытие писало бы вычисленный кадр на диск — `B4` вернулся бы в новой одежде.

Сравнение кадров даёт ту же семантику («подвинул пользователь → пишем»), но не зависит от
того, какие нотификации AppKit посылает и в каком порядке; level-triggered, а не
edge-triggered; не добавляет второй подписки; и **проверяется юнит-тестом**, чего подписка не
даёт. Командир отступление принял.

Живой прогон это подтвердил с той стороны, с какой я боялся: в сценарии `b6move` шаг 2 —
скрытие после подрезанного показа — файл **не** переписал, то есть `window.frame` после
`composer.resize()` всё ещё совпадал с записанным. Риск, который я честно назвал в первой
редакции этого отчёта, замерен и не реализуется.

### `B7` — какой из двух вариантов приёмки выбран

Выбран **первый** (не клэмпить кадр, который и так на дисплеях), с добавкой из второго (экран
по наибольшему пересечению — для кадров, которые клэмпить всё-таки надо).

Первый вариант дешевле и **сам** снимает возражение `F2c`. Довод `F2c` был: широкое условие
даёт тупик на уменьшившемся экране, потому что каждый показ будет клэмпить и запрещать запись.
С первым вариантом клэмп не запускается, пока кадр лежит на дисплеях; на уменьшившемся экране
он запустится один раз, ручная расстановка пользователя запишется (кадр перестал совпадать с
вычисленным) и в следующий раз уже поместится. Тупика нет ни на одном шаге — и это замерено,
шаги 5-8 сценария `b7side` ниже.

Второй вариант в чистом виде (только выбор экрана по пересечению) `B7` **не** закрывает: кадр
на стыке всё равно был бы втащен в один экран, просто в другой.

### Побочная находка живых замеров: полоса меню — не годная замена стыку

Первый вариант односкранного эквивалента `B7`, который я планировал (кадр внутри
`screen.frame`, но заходящий в полосу меню, которую `visibleFrame` исключает), **измеряет не
то**. Диагностика из живого процесса:

```
F2EDBG saved=200,680 800x432 tb=32 nscreens=1 fits=1
F2EDBG screen[0]=0,0 1728x1117 overlap=345600
```

`fits=1` — новый код применил кадр дословно, `-setFrame:(200,680,800,432)`. Окно всё равно
оказалось на `CG 200,33`, то есть по AppKit-координате `652`: это **сам AppKit** через
`constrainFrameRect:toScreen:` не даёт титульной полосе уехать под строку меню. До и после
правки результат совпадает до точки, и файл в обоих деревьях получает `y=652`.

Записывать это стоит: следующий круг приёмки иначе потратит на этот сценарий прогон и решит,
что `B7` не починен. Заодно из этого следует ограничение самой правки, названное в «Рисках»:
кадр, который AppKit не соглашается применить, переписывается на тот, который он применяет —
один раз, устойчиво, без дрейфа (шаги 2 и 4 дают одно и то же число).

## `R2-test:I11` — `./build test` впервые исполняет C++-тесты

`tst/pty_test_helper.c:7` — `#define _POSIX_C_SOURCE 200809L` занижает `__DARWIN_C_LEVEL` и
прячет `SIGWINCH`. Файл не компилировался на macOS:

```
tst/pty_test_helper.c:35:29: error: use of undeclared identifier 'SIGWINCH'
```

Узлы `unit_tests_group_*` зависят от него, поэтому в полном `./build test -k` было **ноль
узлов `[UT]`** — весь набор тестов, включая регрессии `B1`/`B4`/`B5`, официальным графом на
macOS не гонялся ни разу за три круга. Починка — `#define _DARWIN_C_SOURCE` под
`#if defined(__APPLE__)`.

### Ограничение ожидания в хелпере — и почему это не починка `Pty`

Командир просил падения `Pty` не чинить. Я их и не чинил: оба остаются красными. Но одно из
них, `Pty::ResizeReachesChildAsWinch`, обнажалось **не как падение, а как зависание**: resize
не доходит до ребёнка, ребёнок ждёт `SIGWINCH` в `sigwait()` бесконечно, а родитель блокируется
в `poll()` внутри `PtyHandleImpl::acquire()`, ожидая вывода, которого не будет. Снято
`sample`:

```
Suite_Pty::Test_ResizeReachesChildAsWinch::execute(...)
  (anonymous namespace)::PtyHandleImpl::acquire() + 800
    poll (in libsystem_kernel.dylib)
```

То есть починка `R2-test:I11` в чистом виде делает `.build/unit_tests` незавершаемым — команду,
которой мерится вся волна. `sigtimedwait()` на macOS нет, поэтому ожидание в **моём** файле
ограничено через `SIGALRM`: тест по-прежнему падает, но за 10 секунд, а не никогда, и набор
остаётся исполнимым. Продукт не тронут, диагноз не подменён. Если командир предпочтёт видеть
зависание как есть — правка снимается тремя строками.

### Формат

`clang-format -style=file -lines=A:B` по **каждому** изменённому диапазону отдельно (версия в
этой среде отвергает несколько `-lines` разом), 25 диапазонов в 7 исходниках — расхождений нет.
Два места пришлось переписать под форматтер: многострочный вызов `composer.resize()` он
складывает в одну строку, а `(float)(extent) * composerScale` читает как разыменование и
склеивает — второе обойдено именованной переменной, с комментарием почему.

`tst/pty_test_helper.c` форматтером **не покрыт**: `dev/style.py` работает по `*.cpp *.h *.hpp
*.mm`, а clang-format расходится и с предсуществующим кодом этого файла (складывает
многострочные `if`). Правки в нём написаны в стиле самого файла.

`dev/style.py` не запускался: он переписывает чужие места и чужие файлы по всему дереву (`F2c`
намерила 120+, круг 3 подтвердил 116), а по диапазонам всё чисто и без него.

Временной диагностики не осталось: `NSLog`-инструментация из живых замеров откатана,
`git status` по своим файлам чист, единственные изменения — те, что в коммитах.

## Ограничения и что осталось непроверенным

- **Дисплей один.** Кросс-дисплейный кадр «на стыке двух мониторов» физически не воспроизвести:
  подключён единственный экран `0,0,1728,1117`. Числа `B7` из круга 3 (пара экранов
  `0,0,3840,1080` и `1015,-1117,1728,1117`, кадр `1300,-100 1000×568`) закреплены юнит-тестом
  `AFrameStraddlingTwoScreensFits` дословно; **живьём `B7` снят в форме «origin на экране,
  правый край свисает»**, которая воспроизводит ровно его механизм (экран найден, кадр
  подрезан, подрезанное ушло на диск), но не его геометрию. Приёмка круга 4 должна это знать.
- **Полоса меню как замена стыку не годится** — измеряет `constrainFrameRect:toScreen:` самого
  AppKit, а не наш клэмп; замерено и описано выше.
- **`L1` проверен аудитом директив, а не компилятором.** Кросс-компиляция недоступна;
  эксперимент с исключением файла из графа до и после не различает.
- **Настоящее отключение дисплея** по-прежнему смоделировано координатами, которых нет ни на
  одном экране, — тот же приём, что у `F2c` и у приёмки. Возврат кадра после того, как монитор
  воткнули обратно, никто не проверял.
- **Чорды** не проверялись: доставка через Carbon остаётся непроверенной с волны 2. Все живые
  прогоны сняты через `SIGUSR2`.
- **Зеркалирование дисплеев** покрыто юнит-тестом, но живьём не снято; на современной macOS
  зеркальный набор может отдаваться одним `NSScreen`, и тогда дедупликация просто никогда не
  срабатывает.
- **Два падения `Pty`** оставлены как есть по решению командира. Ограничение ожидания в хелпере
  меняет их проявление (зависание → падение за 10 с), но не диагноз.
- **Wayland-реализация `setCornerRadius()`** — как и раньше, не компилировалась никем.

## Риски для ревьюера

1. **Сравнение кадров вместо подписки на нотификации** — отступление от рецепта приёмки.
   Разбирать надо связку «`composer.resize()` после восстановления постит `DidResize`»: если
   она неверна, рецепт приёмки работоспособен и моё обоснование падает. Живой прогон
   (`b6move`, шаг 2) говорит, что в нынешнем коде пересчёт кадр не меняет.
2. **`visibleFrame` больше не ограничивает кадр, целиком лежащий на дисплеях.** Окно может
   остаться поверх Дока, если пользователь его туда поставил. Сознательный размен:
   пользовательская расстановка важнее косметики. Под строку меню AppKit не пустит сам.
3. **Кадр, который AppKit не соглашается применить, переписывается на тот, который он
   применяет** (замерено: `680 → 652`). Один раз, устойчиво, без дрейфа — но саженный руками
   файл в такой ситуации будет «исправлен» терминалом.
4. **`quickFrameFitsScreens()` предполагает непересекающиеся экраны.** Верно для всех раскладок
   macOS, кроме зеркалирования, которое покрыто дедупликацией точных дубликатов.
5. **`alarm(10)` в хелпере PTY** — это моя правка в чужой по смыслу области. Она не чинит
   падение `Pty`, а превращает зависание в падение; если командир хочет видеть зависание как
   есть, правка снимается тремя строками.
