## Резюме

`B6` и `B7` закрыты одной перестройкой защиты, как и просила приёмка, но не тем рецептом,
который она назвала. Отличие одно и оно осознанное — раздел «Отступление от рецепта» ниже.

`I11`, `I12`, `I13` закрыты. `I12` — сильнее, чем просили: тест прогнан на четырёх
раскладках, включая две, на которых старые предусловия действительно падают.

**Чего в этом отчёте нет и почему:** живых прогонов `B6`/`B7` «до и после». Экран машины
залочен с 00:07, а на залоченном экране quick-окно не становится key, скрытие не порождает
`NSWindowDidResignKeyNotification`, файл состояния не пишется вовсе — ни на моём дереве, ни на
дереве «до». Это среда, а не правка; проверено на обоих бинарях. Раздел «Что осталось
непроверенным» описывает это дословно.

## Что не так было в коде

### `B7` — экран выбирался по одной точке, и подрезанное уходило на диск

`applyQuickFrameToWindow()` искала экран так:

```objc
    for (NSScreen* const candidate in [NSScreen screens]) {
        if (NSPointInRect(origin, candidate.frame)) {
```

Окно, которое пользователь одним движением мыши перетащил на стык двух мониторов, имеет
origin на одном из них. Экран **находился**, значит `quickFrameScreenGuessed == false`, значит
защиты не было; `quickFrameTarget()` подрезала всю рамку в `visibleFrame` этого одного экрана,
и подрезанное скрытие писало на диск. Приёмка замерила: позиция уехала на 520 pt, размер
срезан по сетке шрифта, исходная расстановка не восстановима.

### `B6` — флаг присваивался ровно в одном месте

`quickFrameScreenGuessed` присваивался только внутри `applyQuickFrameToWindow()`, а
`applySavedQuickFrame()` до неё не доходит, если файла состояния нет
(`application.cpp:591-594`, ранний `return` после неудачного `loadQuickFrame()`). Отсюда
тупик: после показа кадра с отключённого дисплея флаг оставался `true` навсегда,
`quickRememberFrame` переставал сохранять, а документированный сброс — удалить файл — делал
хуже, потому что без файла флаг тем более не сбрасывался.

## Что сделано

### Две решающие функции вынесены из `.mm` в чистый код

Рекомендация 6 круга 3 дословно: «`quickFrameScreenGuessed` — файловая переменная в `.mm`, ни
одним тестом не достижимая… стоит вынести решение „писать или не писать" в чистую функцию
рядом с `quickFrameTarget()` и покрыть её». Сделано, и обе решающие точки, а не одна:

```cpp
double quickFrameOverlap(const QuickFrameRect& a, const QuickFrameRect& b);
bool quickFrameFitsScreens(const QuickFrameRect& frame, const QuickFrameRect* screens, size_t count);
bool quickFrameShouldSave(bool computed, const QuickFrameRect& computedFrame, const QuickFrameRect& live);
```

`quickFrameFitsScreens()` — «весь ли кадр лежит на подключённых дисплеях». Считает сумму
пересечений кадра с **полными** рамками экранов (`NSScreen.frame`, не `visibleFrame`) и
сравнивает с площадью кадра. Зеркалирование — единственная раскладка, где два экрана отдают
одну и ту же рамку, и точный дубликат пропускается, иначе окно, наполовину свисающее с
дисплея, считалось бы покрытым целиком.

Почему `frame`, а не `visibleFrame`: кадр на стыке по построению заходит в полосу меню
соседнего экрана. У пары мониторов приёмки встроенная панель занимает по y `−1117…0`, её
`visibleFrame` — `−1117…−32`; полоса `−32…0` не покрыта ничьим `visibleFrame`. По `visibleFrame`
кадр на стыке не «помещается» — и `B7` не чинится. Заход в полосу меню чужого экрана не повод
двигать окно; пользователь всё равно не может перетащить окно под собственную строку меню.

`quickFrameShouldSave()` — «писать ли при скрытии». `false` ровно в одном случае: окно **всё
ещё** тот кадр, который вычислил этот показ.

### `applyQuickFrameToWindow()` перестроена

```objc
    QuickFrameRect target = saved;
    const bool fits = quickFrameFitsScreens(saved, screenFrames.data(), screenFrames.length());
    if (!fits) {
        …выбрать экран с наибольшим пересечением, иначе window.screen/mainScreen…
        target = quickFrameTarget(frame, visible, titlebarHeight);
    }
    [window setFrame:… display:YES animate:NO];
    quickFrameComputed = !fits;
    quickFrameComputedFrame = window.frame;
```

Три изменения смысла:

1. Кадр, целиком лежащий на подключённых дисплеях, применяется **дословно**. Экран для него не
   ищется, клэмп не запускается — `B7`.
2. Кадр, частично оказавшийся в никуда, получает экран по **наибольшему пересечению**, а не по
   попаданию origin. Это лечит и симметричный случай: кадр, в основном лежащий на одном
   дисплее, но левым верхним углом заехавший на другой, раньше втаскивался в меньшую свою
   часть.
3. Защита стала широкой: не «экран не найден», а «кадр вычислен этим показом», и записывается
   не флаг, а сам вычисленный кадр.

`[NSScreen screens]` спрашивается один раз и держится в локальной переменной: два цикла
обязаны сходиться в том, какая рамка какому экрану принадлежит.

### Наблюдатель resign-key

```objc
    if (!quickFrameShouldSave(quickFrameComputed, computed, live)) {
        return;
    }
```

`B6` закрыт этим сравнением, а не отдельным сбросом флага. Застрявший `quickFrameComputed`
больше ничего не значит сам по себе: как только окно не там, где его поставил код, кадр
пишется. Прогон приёмки шаг за шагом на новом коде:

| шаг круга 3 | что теперь |
|---|---|
| 1 показ кадра с несуществующего экрана | не помещается → клэмп; `computed = true`, кадр записан в память |
| 2 скрытие | кадр совпадает с вычисленным → не пишем, засев цел (это и раньше было верно) |
| 3 пользователь удаляет файл | — |
| 4 показ без файла | `applySavedQuickFrame()` выходит рано, окно встаёт в `quickGeometry` — а это **не** вычисленный кадр |
| 5 пользователь расставляет окно | тем более не вычисленный кадр |
| 6 скрытие | **пишем** — тупик закрыт |

И второй обязательный сценарий, без удаления файла: показ с догадкой → пользователь двигает
окно → кадр перестал совпадать с вычисленным → скрытие **пишет** новую расстановку.

## Отступление от рецепта приёмки — и почему

Приёмка назвала: «широкое условие защиты **плюс** сброс флага по
`NSWindowDidMoveNotification`/`NSWindowDidResizeNotification` на видимом окне». Широкое условие
сделано. Подписки на нотификации — нет, вместо неё сравнение кадров.

Причина конкретная. Сразу после `applyQuickFrameToWindow()` тот же `applySavedQuickFrame()`
делает `composer.resize(...)` (`application.cpp:614-617`) — пересчёт сетки после
кросс-масштабного восстановления, добавленный `F2c`. Этот пересчёт меняет размер окна, то есть
постит ровно те `DidMove`/`DidResize`, по которым флаг предлагалось снимать. Флаг снимался бы
на **нашей собственной** правке кадра, и скрытие писало бы вычисленный кадр на диск — то есть
`B4` вернулся бы в новой одежде.

Сравнение кадров даёт ту же семантику («подвинул пользователь → пишем»), но:

- не зависит от того, какие нотификации AppKit посылает и в каком порядке относительно
  `-setFrame:`;
- level-triggered, а не edge-triggered: одна пропущенная нотификация ничего не ломает
  навсегда;
- не добавляет второй подписки и второго времени жизни к уже существующему наблюдателю;
- **проверяется юнит-тестом**, чего подписка на нотификацию не даёт.

Это ровно то возражение, о котором просили сказать прямо, а не подгонять: рецепт в буквальном
виде я считаю неработающим, а его цель — достигнутой другим способом. Если ревью не согласно,
разбирать надо именно связку «пересчёт сетки постит DidResize».

## `B7` — какой из двух вариантов выбран и почему

Приёмка предложила два. Выбран **первый** (не клэмпить кадр, который и так виден), с добавкой
из второго (экран по наибольшему пересечению — для тех кадров, которые клэмпить всё-таки надо).

Обоснование: первый вариант дешевле по коду и, что важнее, он **сам** снимает возражение
`F2c`. Довод `F2c` был: широкое условие даёт тупик на уменьшившемся экране, потому что каждый
показ будет клэмпить и запрещать запись. С первым вариантом клэмп вообще не запускается, пока
кадр лежит на дисплеях, — то есть на уменьшившемся экране он запустится один раз, а дальше
ручная расстановка пользователя запишется (кадр перестал совпадать с вычисленным) и в
следующий раз уже поместится. Тупика нет ни на одном шаге.

Второй вариант в чистом виде (только выбор экрана по пересечению) `B7` **не** закрывает:
кадр на стыке всё равно был бы втащен в один экран, просто в другой.

## `I11` — рецепт с несуществующим чордом

`docs/reports/F2d-titlebar-tint-backend-guard-2026-08-18.md:228` задаёт
`quickHotkey = "cmd+shift+f19"`. Грамматика (`lib/shitty/quick_hotkey_chord.cpp:92-103`) знает
`f1`…`f12`; `f19` отвергается, хоткей выключается, окно показывается обычным — человек смотрел
бы не на quick-окно.

Полный обход дерева по рецептам, которые пойдут человеку
(`grep -rn "quickHotkey" docs/reports dev bin`): **это единственный неверный чорд**. Остальные
рецепты используют `ctrl+grave`, `space`, `cmd+shift+f12` — все в грамматике.

Отчёты предшественников не переписывались (указание командира). Вместо этого:

- **правильный рецепт — в разделе «Для человека» ниже**, он заменяет пункт из отчёта `F2d`;
- **долгоживущая правка** — в шапке `dev/quick_window_probe.sh`, канонического места «как
  вручную погонять quick-окно»: там теперь названы грамматика (`ctrl/shift/alt/super` +
  именованная клавиша или `f1`..`f12`), рекомендованный `cmd+shift+f12` и последствие чорда вне
  грамматики.

`f13`..`f20` существуют в Carbon (`kVK_F13`…`kVK_F20`) и в грамматику добавляются одной
строкой каждая, но `quick_hotkey_chord.cpp` — не мой файл и это изменение продуктового
поведения, а не починка рецепта. Оставлено как замечание.

## `I12` — тест уровней раскладки

Починка `F2d` брала ожидание у живой раскладки через `UCKeyTranslate` — это верно и осталось.
Но она же добавила три предусловия: `unshifted != 0`, `shifted != 0`, `unshifted != shifted`.
Приёмка посчитала по данным раскладок: 28 из 251 установленной их ломают.

Убраны все три. Ожидания теперь выражают то, что код действительно делает
(`platform_cocoa.mm:2421-2438`): уровень раскладки, а если раскладка на этом уровне ничего не
даёт — собственные `characters` события, задокументированный запасной путь.

```objc
    const u32 expectedLayout = unshifted != 0 ? unshifted : (u32)('A');
    const u32 expectedShifted = shifted != 0 ? shifted : (u32)('A');
```

Пропуск теста не понадобился: обе ветки выразимы, так что тест остаётся утверждающим на любой
раскладке.

**Проверено прогоном, а не выкладками** — четыре раскладки, `54 OK / 0 ERR` на каждой:

## `I13` — `errexit` из сорсимого файла

`dev/quick_window_probe.sh:83` объявлял `set -euo pipefail` на уровне файла, а сорсить его —
заявленный способ использования. Флаги доставались вызывающей оболочке, и первый же ненулевой
возврат пробника убивал измерение на середине; приёмка потеряла на этом три прогона.

Теперь флаги ставятся только при прямом запуске — тем же условием, которым внизу файла уже
диспетчеризовался `--demo`:

```bash
QWP_SOURCE="${BASH_SOURCE[0]:-$0}"
if [[ "$QWP_SOURCE" == "${0}" ]]; then
    set -euo pipefail
fi
```

`${BASH_SOURCE[0]:-$0}` заодно убирает падение по `set -u` у того, кто сорсит скрипт из zsh
(там `BASH_SOURCE` не определён вовсе).

Проверено:

```
$ bash -c 'set +e; . dev/quick_window_probe.sh; echo "errexit=$-"; false; echo survived; qwp_screens'
errexit=hBc
survived
frame=0.0,0.0,1728.0,1117.0 visible=0.0,0.0,1728.0,1084.0 scale=2.0
$ bash dev/quick_window_probe.sh ; echo exit=$?
usage: dev/quick_window_probe.sh --demo /path/to/.build/st_test
…
exit=1
```

## Что осталось непроверенным

### Живые прогоны `B6`/`B7` — среда не дала

Экран машины залочен (`CGSSessionScreenIsLocked = true`) с 00:07 и не разблокирован к моменту
сдачи. На залоченном экране:

- quick-окно появляется в списке окон CG (`onscreen=true`, layer 25), но **не становится key**,
  поэтому скрытие не порождает `NSWindowDidResignKeyNotification` — файл состояния не пишется
  вообще, никогда;
- AX отказывает на установке позиции и размера
  (`AXUIElementSetAttributeValue(kAXPosition) failed (-25205)`), то есть «пользователь подвинул
  окно» не сымитировать.

Проверено на бинаре **до** правки (`/private/tmp/r2qa3/.build/st_test`, дерево `671e301d`):
тот же паралич, файл не создаётся, AX отказывает. Значит это среда, а не регрессия.

Что это значит для приёмки: `B6` и `B7` закреплены **юнит-тестами с показанной мутационной
чувствительностью**, но не переснятыми живьём числами «до/после», как требовал критерий. Это
надо либо переснять человеку, либо принять как ограничение круга.

### Один дисплей вместо двух

К машине сейчас подключён **один** экран (`frame=0,0,1728,1117 visible=0,0,1728,1084 scale=2`),
у приёмки кругов 2 и 3 их было два. Кадр «на стыке двух мониторов» физически не воспроизвести.
Числа `B7` из круга 3 (пара экранов `0,0,3840,1080` и `1015,-1117,1728,1117`, кадр
`1300,-100 1000×568`) закреплены юнит-тестом `AFrameStraddlingTwoScreensFits` дословно.

Односкранный эквивалент, который стоит снять при разблокировке: кадр, заходящий в полосу меню
(внутри `screen.frame`, снаружи `visibleFrame`) — например
`x-points=200 y-points=680 width-points=800 height-points=400`. До правки такой кадр
клэмпится в `visibleFrame` и подрезанное пишется на диск (тот же механизм, что `B7`); после —
применяется дословно и файл не меняется. Сценарии заготовлены в
`scratchpad/scen.sh` (`b7`, `b6`, `b6move`, `plain`).

## Для человека — исправленный рецепт (заменяет пункт из отчёта `F2d`)

Отчёт `F2d` в списке для человека задаёт `quickHotkey = "cmd+shift+f19"`. Такого чорда нет;
бинарь напечатает `unrecognized chord` и покажет обычное окно. Правильно — `cmd+shift+f12`
(свободен и в грамматике есть):

```sh
git worktree add /tmp/w4 <ветка> && cd /tmp/w4 && ./build -j 8 st st_test
mkdir -p /tmp/w4cfg
printf 'bg = "#2e3440"\nquick = true\nquickHotkey = "cmd+shift+f12"\nquickCornerRadius = 12\ntransparentTitlebar = true\n' > /tmp/w4cfg/q.toml
SHITTY_FOR_TESTS=1 /tmp/w4/.build/st_test -config /tmp/w4cfg/q.toml & kill -USR2 $!
```

Перед прогоном: разблокировать экран (иначе окно не станет key и ничего не сохранится) и
остановить собственный quick-терминал (`pgrep -fl "Shitty.app"`).

Отдельно к `B7`, если снова будут подключены два монитора: перетащить окно на границу дисплеев,
спрятать, показать. **Ожидаемое после этой правки:** окно осталось ровно на стыке, а
`cat /tmp/w4cfg/q-quick-frame` после следующего скрытия показывает ту же расстановку, а не
подрезанную.

## Риски для ревьюера

1. **Сравнение кадров вместо подписки на нотификации** — главное отступление от рецепта
   приёмки. Разбирать надо связку «`composer.resize()` после восстановления постит
   `DidResize`»: если она неверна, рецепт приёмки работоспособен и моё обоснование падает.
2. **`quickFrameComputedFrame` записывается сразу после `-setFrame:`**, а `composer.resize()`
   выполняется после возврата из `applyQuickFrameToWindow()`. Если этот пересчёт **меняет**
   рамку окна, то при скрытии кадр не совпадёт с вычисленным и подрезанный кадр уйдёт на диск.
   Замеры круга 2 показывают, что после `F2c` рамка воспроизводится точно (`1000×500` три
   показа подряд), но живьём при клэмпе это в этом круге не снято — см. «Что осталось
   непроверенным». Это самое слабое место правки, и я называю его прямо.
3. **`visibleFrame` больше не ограничивает кадр, который целиком лежит на дисплеях.** Значит
   окно может остаться под строкой меню или поверх Дока, если пользователь его туда поставил
   (перетаскиванием мышью под строку меню AppKit не даёт, но кадр можно получить сменой
   раскладки мониторов). Это сознательный размен: пользовательская расстановка важнее
   косметики.
4. **`quickFrameFitsScreens()` предполагает непересекающиеся экраны.** Верно для всех раскладок
   macOS, кроме зеркалирования, которое покрыто дедупликацией точных дубликатов. Экраны,
   пересекающиеся частично, дали бы завышенное покрытие — таких раскладок macOS не строит.
