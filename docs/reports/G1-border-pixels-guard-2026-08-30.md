# G1: the border guard goes back to guarding

**Статус:** готово. Один коммит в `fix/G1-border-pixels-guard`, продуктовый код не тронут.

## Что было

`border_pixels_guard` сторожит инвариант A1 (`docs/architecture/2026-08-18-panes-and-window-chrome.md`):
`borderPixels()`/`scaledPixels()` — это пользовательская опция границы и её масштаб, раскладку читают
через `contentInsets()`. Гвард падал на двух строках `lib/shitty/application_ut.cpp`:

```cpp
STD_INSIST(drive.anchor.x == 3 + composer.borderPixels());
STD_INSIST(drive.anchor.y == 16 + composer.borderPixels());
```

Нарушение унаследованное — оно есть и на `6628ba59`, и на `master`, ни одна недавняя волна его не
вносила. Практическое следствие: гвард был красный всегда, а всегда красный гвард не отличается от
отсутствующего — новое нарушение A1 утонуло бы в уже красном выводе.

## Выбранный путь: правка теста

Тест по существу читает **раскладку**, а не опцию, поэтому расширять разрешение было бы неправильно.
Три независимых довода:

**1. Утверждение — про положение окна кандидатов, то есть про layout.** Комментарий над самими
строками это и говорит: «the anchor is the window's own content corner». Content corner — ровно то,
что возвращает `contentInsets()`.

**2. Два соседних теста в этом же файле уже проверяют то же самое через `contentInsets()`.** Строки
770 и 972 читают `const Insets insets = composer.contentInsets();` и сравнивают якорь с
`insets.left`/`insets.top`. Правленый тест был третьей копией того же утверждения, отставшей от
миграции. Расширение разрешения узаконило бы расхождение внутри одного файла.

**3. Литералы `3` и `16` — это не константы теста, а его собственные chrome-резервы.** `DriveApplication`
(строки 237-238) выставляет `setChromeReserve(ChromeSide::Left, 3)` и `(ChromeSide::Top, 16)`. То есть
`3 + borderPixels()` — вручную собранная реплика `contentInsets().left`.

И реплика **арифметически неверная**. Резервы задаются в *логических точках*, а `contentInsets()`
прогоняет их через `scaledPixels()`:

```cpp
Insets Composer::chromeInsets() const {
    return Insets{ scaledPixels(chromeReserves[Top]), ... };
}
Insets Composer::contentInsets() const { /* chromeInsets + paneInsets, поле в поле */ }
```

Правильное значение — `scaledPixels(3) + borderPixels()`, а в тесте стоял немасштабированный `3`.
Совпадение держалось только на том, что у headless-платформы `contentScale == 1`. Плюс исходный код
прибавлял **один симметричный** border к обеим осям — притом что весь смысл A1 в том, что стороны
разные (левая несёт сайдбар, верхняя — полоску заголовка).

Это не косметика ради зелёного гварда: тест был скрытно сломан на любом Retina-масштабе.

### Правка

```cpp
const Insets insets = composer.contentInsets();
STD_INSIST(drive.anchor.x == (i32)(insets.left));
STD_INSIST(drive.anchor.y == (i32)(insets.top));
```

Идиома взята у соседей по файлу — новых хелперов и новых сущностей не добавлено, `build.py` не
менялся вовсе.

Отдельно **не** стал дублировать `STD_INSIST(insets.left != insets.top)`: соседний тест на тех же
резервах `DriveApplication` это уже утверждает, второй экземпляр ничего не добавит.

## Доказательство, что гвард снова сторожит

Три пробы. Продуктовый код в них не участвовал: нарушение вносилось во временный
`lib/shitty/guard_probe.h` (плюс, для пробы количества, временная строка в разрешении `build.py`).
Обе пробы откачены, `git status` после отката показывал единственный изменённый файл — тест.

**Проба A — файл вне разрешения, одно обращение.** Гвард обязан краснеть на любом обращении:

```
$ ./build border_pixels_guard -j 4
borderPixels()/scaledPixels() are the border option and its scale, not the layout (A1): contentInsets() is what layout reads.
Unallowed uses:
  lib/shitty/guard_probe.h:2
```

**Проба B — файл в разрешении с лимитом 1, два обращения.** Проверяет вторую ветку гварда
(`len(hits) > allowance[key]`) и срез `hits[allowance[key]:]` — сообщено только лишнее, второе:

```
$ ./build border_pixels_guard -j 4
borderPixels()/scaledPixels() are the border option and its scale, not the layout (A1): contentInsets() is what layout reads.
Unallowed uses:
  lib/shitty/guard_probe.h:3
```

**Проба C — те же два обращения, сдвинутые на 500 строк вниз, лимит 2.** Зелено (см. «Разрешения и
номера строк»).

**Незапланированная четвёртая проба, самая убедительная.** Первая редакция моего же комментария
содержала слово `borderPixels()` в прозе — и гвард покраснел на нём:

```
Unallowed uses:
  lib/shitty/application_ut.cpp:888
```

Гвард считает вхождения подстроки в сырых строках файла, комментарии не исключены. Комментарий
переписан так, чтобы не называть функцию по имени. Побочно это живое доказательство, что узел
реагирует на свежий текст, а не на закешированный вердикт.

## Разрешения и номера строк

**Механизм к номерам строк не чувствителен — исходная гипотеза не подтвердилась.** Разрешение
ключуется парой «путь → количество»; номера строк живут только в тексте отчёта о падении:

```python
if key not in allowance:
    bad += hits
elif allowance[key] is not None and len(hits) > allowance[key]:
    bad += hits[allowance[key]:]
```

Проба C это подтвердила прямо: два обращения, сдвинутые на 500 строк вниз (строки 502/503 вместо
2/3), при лимите 2 дают зелёный. Сдвиг нарушения с 452 на 885 был перемещением текста в сообщении,
а не поломкой разрешения: `application_ut.cpp` в разрешении не было вовсе, ломаться было нечему.

Настоящих хрупкостей у механизма три, и они другие:

**1. Количество не помнит, *какие* обращения узаконены.** `composer.cpp: 8` означает «любые восемь».
Удалить законное обращение и добавить незаконное — счётчик тот же, гвард зелёный. Комментарий в
`build.py` обещает, что счётчик «keeps `Composer::resize()` from quietly growing a scalar of its
own», но он ловит только *рост*, не *подмену*.

**2. Считается подстрока в сырых строках** — комментарии и строковые литералы идут в зачёт (я на это
наступил). Обратная сторона: файл в разрешении может исчерпать лимит прозой, и настоящий вызов
пройдёт бесплатно.

**3. `line.count(name)` — подстрочное совпадение без границ слова.** `unscaledPixels` или
`borderPixelsForTest` засчитаются как обращения; объявление не отличается от вызова.

**Предложение (не реализовано, вне объёма задачи).** Три шага, все остаются в grep-простоте, парсер
не нужен:

- перед подсчётом выкидывать комментарии и строковые литералы — тогда счётчик отражает код, а прозу
  об инварианте можно писать свободно;
- сопоставлять по границам слова (`\bborderPixels\b`) вместо `str.count`;
- **вместо количества хранить множество нормализованных текстов строк-обращений.** Привязка
  становится содержательной: вставки выше по файлу ничего не двигают (как и сейчас), но подмена
  законного обращения незаконным краснеет, потому что текст другой. Это и есть устойчивая привязка,
  которую искала задача, — только якорь не номер строки, а сама строка.

Первые два шага стоят нескольких строк в `build.py` и применимы ко всем трём сканирующим гвардам,
которые уже делят `guard_scan_roots`.

stderr, код возврата 0.

`application_ut.cpp` линкуется только в `unit_tests`, Python-набор гоняет `st_test`/`pt_test`.
Из `tst/*.py` файлы `_ut.cpp` упоминают только `test_config.py` и `test_pane_frame_recovery.py`, и
оба — в прозе комментариев, содержимое никто не разбирает. Попадание `lib/shitty/*_ut.cpp` в
`python_test_inputs` — консервативность отслеживания зависимостей, а не чтение. Зелёным его не
объявляю: не прогонял.

`python3 dev/style.py` не запускался по указанию задачи (clang-format 23.1.0 против ожидаемого 21).

## Обнаружено

- Гвард считает вхождения и в комментариях. Объяснять инвариант A1 в прозе, называя функцию по
  имени, нельзя ни в одном сканируемом файле — узел покраснеет на объяснении самого себя.
- Пустой вывод `./build` после отката мутации ничего не проверяет: штампы восстанавливаются
  ссылками из CAS. Для настоящего прогона нужно менять содержимое входа либо исполнять программу
  гварда напрямую.
- Комментарий в `build.py` («Comments cannot trip this the way `border_pixels_allowance` can»)
  описывает соседний гвард, а не этот; для `border_pixels_guard` он не верен.

## Что осталось

- Укрепление механизма разрешений (три шага выше) — предложено, не сделано: `build.py` в части
  гвардов мой, но это отдельное изменение с собственным риском для трёх узлов сразу, и его стоит
  принимать отдельным решением.
- Разрешения `composer.h: 5` / `composer.cpp: 8` я не пересчитывал и не трогал — они зелёные.
