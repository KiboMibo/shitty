# T0.1. Эталонная зелёная линия текущего `master`

**Дата:** 2026-08-30 · **Задача:** `T0.1`, волна 1 плана `docs/plans/2026-08-29-upstream-merge.md` · **Вердикт:** готово с замечаниями

Этот документ — не отчёт о качестве, а **точка отсчёта**. Он снят до единого апстримного коммита, чтобы после каждого из восьми мержей можно было ответить на один вопрос: «это мерж сломал или было сломано?». Числа здесь сравниваются буквально; они не округлены.

## Как этим пользоваться

После каждой волны прогоните раздел «Рецепт» дословно и сверьте с разделами 4–8. Красное, которого нет в списках ниже, — регрессия мержа. Красное, которое есть, — унаследованное; трогать его в рамках мержа не нужно.

Списки падений даны в стабильном (лексикографическом) порядке — их можно сравнивать через `diff`.

### 6. Питоновский набор

Из **корня репозитория** (не из `tst/`), через собственный раннер проекта — это то, что делает `build.py:1060`, и что даёт единый разбор итогов:

```sh
export SHITTY_TEST_BINARY="$PWD/.build/st_test"
export SHITTY_PRETTY_TEST_BINARY="$PWD/.build/pt_test"   # НЕ PRETTY_TEST_BINARY
export SHITTY_TOML_DUMP_BINARY="$PWD/.build/toml_dump"
export SHITTY_TEST_FONTCONFIG=0
export SHITTY_TEST_PLATFORM=cocoa
export SHITTY_TEST_VERSION="$(date +%Y.%m.%d)"

# 20 групп, как в build.py; параллелизм 10 по числу ядер
for g in $(seq 0 19); do
  python3 tst/run_unittest_group.py --group=$g --group-count=20 > group-$g.log 2>&1 &
  [ $(( (g+1) % 10 )) -eq 0 ] && wait
done
wait
```

`run_unittest_group.py` сам кладёт `tst` в `sys.path`, поэтому `from harness import Shitty` работает из корня. Запуск `python3 -m unittest` из корня — не работает; запуск одной группой (`--group-count=1`) работает, но идёт последовательно и заметно дольше.

**Значения окружения не выдуманы:** они прочитаны из `make_python_test_groups()` в `build.py:1067–1074`. `SHITTY_TEST_FONTCONFIG=0` — потому что на darwin `optional_pkg` возвращает выключенную зависимость (`build.py:174`).

## 8. Гварды: четыре из четырёх, каждый доказанно краснеет

Пустой вывод `./build <guard>` ничего не доказывает: `.build/` адресуется содержимым, и штамп возвращается симлинком из `.build/cas/` без исполнения. Поэтому каждый гвард проверен в три шага:

- **A.** во временный файл вносится изменение **без нарушения** → узел пересчитывается (виден собственный тег гварда в выводе) → **зелёный, исполненный, а не подставленный из кеша**;
- **B.** в тот же файл вносится **нарушение** → **красный**, с сообщением гварда и точной строкой;
- **C.** файл удаляется → **снова зелёный**.

| Гвард | Тег | A: свежий зелёный | B: краснеет на нарушении | C: откат |
|---|---|---|---|---|
| `border_pixels_guard` | `[BP]` | exit 0, `[BP] {1/1} $(B)/tst/border-pixels-guard.stamp` | **exit 1** | exit 0 |
| `mouse_geometry_guard` | `[MG]` | exit 0, `[MG] {1/1} $(B)/tst/mouse-geometry-guard.stamp` | **exit 1** | exit 0 |
| `pane_grid_guard` | `[PG]` | exit 0, `[PG] {1/1} $(B)/tst/pane-grid-guard.stamp` | **exit 1** | exit 0 |
| `darwin_call_guard` | `[DA]` | exit 0, `[DA] {1/1} $(B)/tst/darwin-call-guard.stamp` | **exit 1** | exit 0 |

## 9. Находки

### Блокирующих нет

Ни одна находка не блокирует старт мержа: всё перечисленное красно **до** первого апстримного коммита и является предметом эталона, а не препятствием.

### Важная 1. Тринадцать из четырнадцати `errors` — один класс, и у этих тестов нет skip-охраны

**Где:** `tst/test_bitmap_font_render.py`, `tst/test_synthesized_symbols.py`, `tst/test_color_font_render.py`, `tst/test_font_resolver.py`.

**Что не так:** все тринадцать падают с `RuntimeError: invalid font load response` (четырнадцатый — `invalid render image response`). Коммит `62cef373` («macOS: сборка без библиотек Homebrew по умолчанию», 2026-08-25) выключил на darwin все пять опциональных зависимостей, включая freetype и harfbuzz (`build.py:174`). Тесты, которым нужен растровый загрузчик (`.bdf`) или цветной шрифт, теряют его — но, в отличие от соседей по файлу, не имеют охраны: `tst/test_font_resolver.py:32` пишет `@unittest.skipUnless(FONTCONFIG_AVAILABLE, "Fontconfig is not available")` и честно пропускается, а в `tst/test_bitmap_font_render.py` нет ни одного `skip`.

**Чем грозит:** четырнадцать постоянно красных строк — это шум, в котором утонет пятнадцатая, настоящая. Ровно так регрессия и проезжает мимо ревьюера.

**Что предлагается:** после мержа (не в его рамках) закрыть их той же охраной, что у fontconfig-тестов, — по признаку доступности freetype-бэкенда. Тогда они станут `skipped` и `errors` упадёт до 1.

**Оговорка:** диагноз выведен из устройства кода и даты коммита, бисектом не подтверждён.

### Важная 2. Девять тестов `FontResolverTest` прогоняются дважды

**Где:** `tst/test_font_fallback.py:10` — `from test_font_resolver import FontResolverTest`.

**Что не так:** импорт втягивает класс в пространство имён `test_font_fallback`, и `unittest.defaultTestLoader.discover("tst")` собирает его второй раз. Дублируются все девять тестов класса:

```
test_collection_face_and_representative_advances_define_cells
test_extra_fallback_fonts_keep_primary_metrics
test_font_file_path_is_not_treated_as_a_family
test_font_file_paths_load_primary_and_fallback_fonts
test_fontconfig_family_loads_without_a_search_path
test_fontconfig_loads_all_four_style_faces_when_available
test_fontconfig_resolves_family_and_alias
test_overlay_width_is_independent_but_vertical_metrics_must_match
test_unresolvable_family_falls_back_to_the_embedded_font
```

**Чем грозит:** три числа этого отчёта завышены и завышены останутся: из 6391 девять — дубли, из 17 `skipped` шесть, из 14 `errors` один. Хуже другое — в логе оба экземпляра печатаются под одним и тем же id (`unittest` берёт `__module__` класса), так что при разборе падения невозможно понять, какой из двух упал, а «одно падение в двух группах» читается как мигание.

**Что предлагается:** заменить импорт класса на импорт модуля (`import test_font_resolver` и обращение `test_font_resolver.FontResolverTest.write_fontconfig`) — используются только статические методы, так что правка механическая. Вне рамок мержа.

### Важная 3. Три гварда из четырёх ослепнут молча, когда код переедет в `lib/vterm`

**Где:** `build.py:1189` — `guard_scan_roots = ("lib/shitty", "ext/plt", "bin")`.

**Что не так:** это ровно риск «гварды молча ослепнут» из раздела 9 плана, и здесь у него есть измеримая деталь, которой в плане нет. `darwin_call_guard` **самозащищён**: он заканчивается проверкой

```python
if not tracked:
    sys.stderr.write("the darwin call audit tracks nothing at all, which means it stopped working\n")
    sys.exit(1)
```

У `border_pixels_guard`, `mouse_geometry_guard` и `pane_grid_guard` такой проверки **нет**. На пустом множестве отсканированных файлов они возвращают exit 0.

**Чем грозит:** если `T2.1` добавит `lib/vterm` в `guard_scan_roots` не полностью или не сразу, `darwin_call_guard` покраснеет и потребует внимания, а три остальных промолчат — инварианты `A1`, `A8`, `A9` останутся без охраны при зелёной сборке. Это и есть «регрессия, проходящая проверку».

**Что предлагается:** в `T2.1` не ограничиваться добавлением корня, а дать трём гвардам ту же самозащиту, что уже есть у четвёртого: считать просканированные файлы и падать, если их ноль. Критерий «гвард доказанно краснеет» из плана этого не покрывает — гвард можно заставить покраснеть на файле в `lib/shitty`, ничего не зная про `lib/vterm`.

### Замечание 4. Сборка и гварды зависят от виртуального окружения пользователя

`python3` разрешается в `/Users/kibomibo/.virtualenvs/shims/python3` (Python 3.12.5, окружение `cplanner4`). Все четыре гварда и все питоновские тесты исполняются им. На эталоне это работает; отмечено, потому что смена активного virtualenv между волнами изменит интерпретатор молча.

### Замечание 5. `unit_tests` печатает две строки, похожие на ошибку

В выводе есть


## 10. Допущения

1. **Отчёт назван `T0.1-baseline-2026-08-30.md`**, хотя в плане на момент постановки значилось `2026-08-29`. Взята дата, названная командиром; коммит `a8cf69ac` в `master` привёл план в соответствие.
2. **Эталон снят на `0c303cd6`, а не на `a8cf69ac`.** На старте замера это и был `master`; отличие — одна строка в документе плана. Пересъёмка не проводилась.
3. **Питоновский набор запускался из корня репозитория** через `tst/run_unittest_group.py`, а не из `tst/`, как было предложено в постановке. Основание: это то, что делает `build.py:1060` при `cwd="$(S)"` (`build.py:1066`), а раннер сам кладёт `tst` в `sys.path`. Все шесть переменных окружения выставлены по `build.py:1067–1074`; значение `SHITTY_TEST_FONTCONFIG=0` подтверждено чтением `build.py:174`, а не принято на веру.
4. **`TMPDIR` вне чекаута выставлен только для `unit_tests`.** Для питоновских тестов оставлено системное умолчание macOS (`/var/folders/…`, тоже вне чекаута) — так делает `build.py`, который `TMPDIR` не трогает.
5. **Кеш `.build/` не сносился.** Холодные числа сняты в отдельный каталог через `-B` и `--cache-dir`. Причина: снос общего CAS ничего не добавляет к измерению, но стоит времени и другим агентам.
6. **Прогонов пять, а не два.** Прогон стоит 27 секунд.
7. **Гварды проверялись на временных файлах-пробах**, а не правкой существующих исходников: откат сводится к `rm`, и исходный файл невозможно испортить. Проба видна гвардам, потому что `guard_scan_sources` — это glob (`build.py:1191`), пересчитываемый на каждом запуске.
8. **`python3 dev/style.py` не запускался** — по указанию в постановке (clang-format 23.1.0 против ожидаемого 21).
9. **Vulkan не проверялся** — на этой машине его нет; это уже учтено планом (`T4.2`, риск в разделе 9).
