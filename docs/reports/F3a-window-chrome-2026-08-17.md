# F3a. Секьюрити-исправления: S1, S2, S4, S5

**Ветка:** `feat/window-chrome` · **План:** `docs/plans/2026-08-17-window-chrome-quick-terminal.md`
**Источник:** `docs/plans/reviews/window-chrome-R3-sec.md`

## S1. Чорд без модификатора теперь отвергается

`ui_quick_hotkey.mm`, конструктор `QuickHotkeyUi`: после успешного
`parseQuickHotkey` добавлена проверка `modifiers == 0` — та же ветка отказа,
что у нераспознанного чорда, с отдельным текстом про обязательный модификатор.
Одна проверка, до любого вызова Carbon API.

Проверено живьём: `quickHotkey = "space"`, `quick = true` →

```
shitty: quickHotkey: 'space' has no modifier (ctrl/shift/alt/super); the quick-terminal hotkey is disabled
```

хоткей не регистрируется (проверка стоит раньше `InstallEventHandler`/
`RegisterEventHotKey`, ни один из них не вызывается). `ctrl+grave` при этом
по-прежнему регистрируется и работает — проверено тем же прогоном, что и
раньше (0→1→0 по нажатиям).

## S2. Недостижимое окно — решение реализовано, вариант «показать как обычно»

Решение принял team-lead, моя часть — реализация. Изменена цепочка
возврата, а не поведение при старте:

- `createQuickHotkey(ObjPool&, Composer&)` теперь возвращает `bool` —
  зарегистрировался ли хоткей по-настоящему (поле `QuickHotkeyUi::active`,
  выставляется в `true` только после успешных `InstallEventHandler` **и**
  `RegisterEventHotKey`; в объявлении в `ui_quick_hotkey.h` возврат
  задокументирован).
- `ApplicationImpl` получил поле `quickHotkeyActive`, выставляется в `run()`
  результатом `createQuickHotkey()` (только под `#if defined(__APPLE__)` —
  вне Apple-сборки поле остаётся `false` по умолчанию, что само по себе и
  есть explicit-ответ на «Linux» из задания: не потому что где-то забыли
  проверить платформу, а потому что вне `#if defined(__APPLE__)` некому
  выставить его в `true`).
- Одна диагностика в `run()`, если `quick && !quickHotkeyActive` —
  печатается независимо от причины (плохой чорд, отказ регистрации, или
  сборка вовсе без модуля хоткея).
- `showWindow()`: условие `if (!composer.opts->quick)` стало
  `if (!composer.opts->quick || !quickHotkeyActive)` — единственное место,
  которое решает, показывать окно на старте.

Живая проверка обоих путей отказа:

| Сценарий | stderr | Окно на старте |
|---|---|---|
| `quickHotkey = "space"` (S1) | `'space' has no modifier...` + `quick: no working hotkey...` | показано (1) |
| `quickHotkey = "ctrl+nonsense"` (нераспознанный) | `unrecognized chord 'ctrl+nonsense'...` + `quick: no working hotkey...` | показано (1) |
| `quickHotkey = "ctrl+grave"` (рабочий) | ничего | скрыто (0), хоткей переключает |

Ни одной конфигурации с живым процессом и недостижимым окном не осталось —
ровно критерий приёмки из плана устранения.

## S4. Критерий про снятие регистрации — заменён на наблюдаемую проверку

Прогнал ровно то, что предложил R3-sec: `quick = true`, дефолтный
`ctrl+grave`, дождался что хоткей работает (счётчик окон `System Events`
0→1), затем убил процесс тремя разными сигналами и в каждом случае сравнил
поведение чорда в TextEdit **до старта терминала** (baseline) и **после
убийства**:

| Сигнал | Хоткей работал до kill | Процесс мёртв | `ctrl+grave` в TextEdit после kill |
|---|---|---|---|
| baseline (терминал не запускался вовсе) | — | — | пусто (см. ниже) |
| `SIGKILL` | да (0→1) | да | пусто — совпадает с baseline |
| `SIGTERM` | да (0→1) | да | пусто — совпадает с baseline |
| `SIGABRT` | да (0→1) | да | пусто — совпадает с baseline |

Честно про методологию: содержимое документа TextEdit после `ctrl+grave`
пустое **и в baseline тоже** — Control-модифицированные чорды в Cocoa-полях
ввода не вставляют печатный символ независимо ни от чего, так что «символ
вводится» из формулировки плана в TextEdit не проверяемо буквально. Вместо
этого использовал вторую часть той же фразы — «чорд ведёт себя как до
запуска терминала» — и сравнил baseline с результатом после каждого из трёх
сигналов. Все три совпали с baseline. Вместе с тем, что уже установил
R3-sec чтением кода (`ObjPool` рвёт объекты LIFO, `QuickHotkeyUi` создан
позже окна → уничтожается раньше при штатном пути; при `SIGKILL`/`SIGABRT`
деструкторы не выполняются вовсе, освобождение — на системе, по
документации `RegisterEventHotKey`) и подтвердил живым прогоном на всех
трёх видах завершения — вопрос плана закрыт.

Обновляю формулировку критерия T3 (не переписывая сам отчёт T3 — история
находки должна остаться): **критерий T3 «второй процесс без already
taken» был некорректен** (см. S4 в R3-sec), заменён на «поведение чорда
после kill совпадает с поведением до старта терминала, проверено на
`SIGKILL`/`SIGTERM`/`SIGABRT`».

## S5. Убрана вводящая в заблуждение подсказка

`ui_quick_hotkey.mm`: текст ошибки регистрации был «could not register
'...' (already taken?)» — S4/S1 замерами R3-sec установлено, что
`RegisterEventHotKey` возвращает `noErr` даже при живом конкуренте на том
же чорде, то есть подсказка называла причину, которую код в принципе не
может диагностировать. Заменено на нейтральное «the system refused to
register '...'» без домыслов о причине; комментарий над строкой объясняет
это явно, чтобы подсказка не вернулась.

## За рамками

- **S3** — не моя находка, территория F3b (`ext/plt/platform_cocoa.mm`).
- Живая пересборка хоткея на SIGUSR1-релоад по-прежнему не реализована —
  не входила ни в T3, ни в F3a.

## Ревьюеру

- Главное новое решение — `bool` вместо `void` у `createQuickHotkey`. Это
  смена сигнатуры зафиксированного в W1 контракта, но в границах моего
  владения (`ui_quick_hotkey.h`/`.mm`, единственный вызывающий —
  `application.cpp`, тоже мой); альтернатива без смены сигнатуры потребовала
  бы городить состояние в `Composer` ради того же единственного бита.
- Таблица в S4 — самое дорогое место отчёта по времени (три цикла
  запуск/kill/TextEdit); честно написал, почему «символ вводится» из плана
  не проверяем буквально для этого конкретного чорда, и что проверил вместо
  этого.
