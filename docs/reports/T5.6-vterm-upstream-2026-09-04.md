## Обнаружено

1. **Пункт списка задачи может описывать апстримное устройство, а не работу.**
   «Пулы на `owner`» были одинаковы у нас и у апстрима **ещё до начала волны**
   (`e4dcbd54:lib/shitty/vterm.cpp:437, 994, 1056, 1058`). План перечислял
   апстримные признаки функции, взятые из чтения апстримного файла, и один из
   четырёх никогда не был расхождением. Проверять такой пункт надо не «есть ли
   это у апстрима», а `diff` против **merge-base**, а не против `origin/master`:
   разница между этими двумя эталонами и есть весь этот отчёт.

2. **Два пункта задачи волны 6 адресованы коммиту волны 8.** `resizedWithHistory`
   и обе проверки `saveLines` введены `7e2a3c15`, который лежит **на 14
   коммитов позже** цели последнего мерж-шага волны (`7e2a8e3e`, шаг `M6e`) и
   **позже** цели `M7` (`44d61bfc`), то есть попадает в `M8`. План писался по
   диффу против `origin/master` целиком, и в задачу волны 6 попали строки,
   которых в её диапазоне физически нет. Стоит проверить тем же способом
   оставшиеся задачи хвоста — `T5.3` и `T5.2` (см. ниже, для `T5.3` проверено).

   Третья разновидность той же ошибки — у `T5.3`: «`CellExtraClient` на
   `VtCellExtras::changedListeners`» звучит как взятие апстримного, а
   `CellExtraClient` **не существует у апстрима вовсе** (`git grep -c
   CellExtraClient origin/master` пуст). Итог по трём проверенным
   формулировкам: одна была работой (`Screen::createPrimary(extras_, …)`),
   одна описывала неизменную общую часть (пулы), две — код, который у апстрима
   либо ещё не написан (`resizedWithHistory`), либо не написан никогда
   (`CellExtraClient`).

3. **`M7` не приносит `lib/embed` целиком, вопреки формулировке плана.**
   План (`### M7`): «`git merge 44d61bfc` — включает `lib/embed`». Каталог там
   действительно есть, но два фасадных входа появляются **позже**:

   ```
   $ git show 44d61bfc:lib/embed/shitty_vt.h | grep -c "shitty_vt_memory_usage\|shitty_vt_set_save_lines"  → 0
   $ git show origin/master:lib/embed/shitty_vt.h | grep -n …
   163:    void shitty_vt_memory_usage(const shitty_vt*, shitty_vt_memory* out);
   168:    void shitty_vt_set_save_lines(shitty_vt*, uint16_t save_lines);
   ```

   Это тот же `7e2a3c15`. Следствие для `T6.1` (сборка `lib/embed` в `build.py`)
   и `R7-test`: набор публичных символов фасада после `M7` **не окончательный**,
   и `tst/test_embed_example.py` после `M8` вырастет на 60 строк. Если `T6.1`
   зафиксирует список экспортов по состоянию `M7`, `M8` его сломает.

4. **`7e2a3c15` чинит латентный дефект, который живёт у нас сегодня.** Из тела
   его сообщения: понижение потолка истории заставляло пересборку переносить
   все строки истории в кольцо меньшего размера, и излишек затирал живые
   строки. У нас потолок нельзя понизить на лету вовсе (`ScreenInfo` не несёт
   `saveLines`, `configChanged()` историю не пересобирает — `vterm.cpp:9020`
   сравнивает только колонки и строки), поэтому дефект **недостижим**: перезагрузка
   конфига, меняющая только `saveLines`, у нас просто не даёт эффекта. То есть
   мы носим не порчу памяти, а **тихое игнорирование опции** — наблюдаемое
   следствие: правка `saveLines` в конфиге с последующим reload не меняет
   глубину прокрутки до перезапуска. Это не регрессия волны и не повод чинить
   руками; это то, что `M8` закроет вместе с фичей.

5. **Пофункциональный `diff` с нормализацией — дешёвый способ отделить «наше»
   от «не приехало».** Расхождение `vterm.cpp` с merge-base — 283 строки в 33
   хунках, и глазами это разбирать дорого. Замена `geometry.` → `pane_.` в
   эталоне перед `diff` схлопывает всю работу `T5.5` и оставляет ровно
   содержательное: шесть хунков по ключевым словам, все шесть — `A8`/`A11`/`R7`.
   Скрипт занял пятнадцать строк и заменил бы, судя по объёму задачи в плане,
   несколько часов чтения. Рекомендую `T5.3` и `T5.2` начать тем же.

## Что осталось `T5.3`

`T5.3` — следующее звено цепочки (`T5.6` → `T5.3` → `T5.2`), владеет
`lib/vterm/cell_extra_store.{h,cpp}`, `cell_extra_store_ut.cpp` и хвостом в
`vterm.cpp`. Формулировка плана: «`CellExtraClient` на
`VtCellExtras::changedListeners`; сохранить дедуп корней и `cellCapacity()`».

**В `vterm.cpp` это, судя по измерению, уже стоит** — и это второй случай того
же, что описано в «Обнаружено» пункт 1:

| Что | Где сегодня | Состояние |
|---|---|---|
| `CallVtermCollectExtras: public CellExtraClient` | `vterm.cpp:296-301` (объявление), `8937-8943` (тела) | есть |
| Регистрация в `changedListeners` | `vterm.cpp:8934`, `extras_.changedListeners.pushBack(owner.make<CallVtermCollectExtras>(this))`, в `resetTerminal()` | есть |
| `cellCapacity()` как `override` | `vterm.cpp:621` (объявление), `3272` (тело) | есть |
| `collectExtras()` с дедупом корней | `vterm.cpp:619`, `3326` | есть, проверить дедуп телом |
| `IntrusiveList changedListeners` | `lib/vterm/cell_extra_store.h:38` (у апстрима `:37`) | есть, апстримное |
| `struct CellExtraClient` | `lib/vterm/cell_extra_store.h:59` | есть, **наше — у апстрима такого имени нет вовсе** |

Последняя строка стоит отдельного слова. `CellExtraClient` во всём
`origin/master` не встречается ни разу:

```
$ git grep -c "CellExtraClient" origin/master -- .   → пусто
$ git grep -c "CellExtraClient" HEAD -- .            → 17 файлов, из них код:
    lib/vterm/cell_extra_store.h:2   lib/vterm/cell_extra_store.cpp:4
    lib/vterm/vterm.cpp:1            lib/shitty/span_shaper.cpp:1
    lib/shitty/cell_extra_store_ut.cpp:2   lib/shitty/composer_ut.cpp:1
```

То есть формулировка плана «`CellExtraClient` на
`VtCellExtras::changedListeners`» описывает **сохранение нашей конструкции
поверх апстримного списка слушателей**, а не взятие апстримного кода. Это
третий случай того же класса, что пункты 1 и 4 моей задачи, — и «взять
апстримное» здесь неисполнимо буквально.

Апстримный `vterm.cpp` (и на `origin/master`, и на merge-base) **не содержит
ни одного упоминания** `CellExtraClient`, `changedListeners` или
`collectExtras` — там `updateExtraCellCount()` считает по двум своим экранам
(`origin/master:3206-3208`). Значит расхождение в `vterm.cpp` по этой теме —
**наше и намеренное** (`R7` плюс `A11` из `R5-qa`, комментарий в
`updateExtraCellCount`), а не остаток мержа.
