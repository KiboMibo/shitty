# T8. `quickCompanion` — второй процесс с quick-панелью

**Ветка:** `feat/window-chrome-upstream`
**Коммиты:** `7f363f6e` (спавн/гашение спутника), `c09ddbc2` (`Accessory` для quick-окон)
**Границы владения:** `lib/shitty/options.cpp`, `options.h`, `bin/st/shitty.toml`,
`bin/pt/pretty.toml`, `lib/shitty/test_mode.cpp` (не тронут, см. ниже),
`lib/shitty/application.cpp`, `ext/plt/platform_cocoa.mm`, `ext/plt/window.h`
(не тронут — контракт `plt::Window`/`WindowOptions` не менялся, `options.quick`
уже был публичным полем `WindowOptions`), новые `lib/shitty/quick_companion.{h,cpp}`
+ юнит-тест, README (раздела про `quick` в README нет — трогать нечего, как и в T7).

## Что сделано

Опция `quickCompanion = "<путь>"` задаёт конфиг для quick-панели, которую основной
процесс спавнит сам собой при старте и гасит при своём выходе:

```toml
# ~/.config/shitty/shitty.toml — основной
transparentTitlebar = true
quickCompanion = "~/.config/shitty/quick.toml"

# ~/.config/shitty/quick.toml — панель
import = ["~/.config/shitty/shitty.toml"]
quick = true
no-decorations = true
quickHotkey = "ctrl+grave"
```

Основной процесс перезапускает себя же (`argv[0]`, тем же способом, каким его
запустил пользователь) с `-config <resolved-path>`. Спутник — обычный `st`,
ничем не отличимый от запущенного вручную, кроме родителя.

## Как устроен спавн и гашение

- **Точка спавна** — `ApplicationImpl::run()`, сразу после `setupSignals()`,
  до `createPty()`. Не раньше: `setupSignals()` ставит собственный обработчик
  `SIGCHLD`; спавн раньше него означал бы, что мгновенная смерть спутника
  словится под старой (`SIG_DFL`, «игнорировать», но не «автоматически
  reap-ить») диспозицией и оставит зомби, который никогда не заберётся —
  следующий `SIGCHLD` от чего угодно другого не придёт, если спутник больше
  никогда не пошлёт сигналов. Не позже: до `createPty()`/`createRenderer()`,
  то есть по-настоящему «при старте».
- **`lib/shitty/quick_companion.{h,cpp}`** (новые) — по прецеденту
  `quick_geometry.{h,cpp}`/`quick_hotkey_chord.{h,cpp}`: чистая, юнит-тестируемая
  половина (`resolveQuickCompanionConfig` — `~`-раскрытие + `realpath` +
  сравнение с текущим конфигом) отделена от половины с сайд-эффектами
  (`spawnQuickCompanion` — `fork()`/`execvp()`, тем же способом, что
  `lib/shitty/pty.cpp`, без новых зависимостей). Файл не обёрнут в
  `#if defined(__APPLE__)` — `fork`/`execvp`/`realpath` портируемы, и глоб
  `lib/shitty/*.cpp` в `build.py` подхватывает такие файлы на всех платформах
  без правки `build.py` (тот же нюанс, что T7 нашла для `quick_geometry.cpp`).
- **`lib/shitty/quick_companion_ut.cpp`** (новый) — 5 юнит-тестов на
  `resolveQuickCompanionConfig`: успешное разрешение существующего файла,
  отказ на несуществующем (out не тронут), самоссылка через **разные
  написания одного файла** (`.../x` против `..././/x` — доказывает, что
  сравнение канонических путей, а не строк), два разных файла не путаются
  друг с другом, пустой `ownConfigPath` никогда не даёт самоссылки.
- **`lib/shitty/options.h`/`options.cpp`** — поле `Options::quickCompanion`
  (строка, парсится без формата валидации, как `-dump`/`-shell`/`-title`:
  пустая строка = «спутника нет», не ошибка). Второе новое поле —
  `Options::configPath`: путь, который `loadConfigFile()` реально разрешил
  для *этого* процесса (записывается **до** попытки чтения файла, так что
  остаётся верным даже когда файла ещё нет). Только он используется гардом
  самоссылки — больше нигде.
- **`lib/shitty/application.cpp`** — `argv0` захватывается первой строкой
  `run()` (ни `takeTestFd()`, ни `Config::initialize()` его не трогают, только
  сдвигают то, что после него). `quickCompanionPid` — файловый статик
  `volatile sig_atomic_t`, а не поле `ApplicationImpl`: его обязан читать и
  писать `childSignalHandler` (сигнальный обработчик, он же уже читает/пишет
  такой же `lastChildStatus`), так что он либо файловый статик, либо это
  усложнение с указателем в `siginfo_t`. `stopQuickCompanion()` — `kill(pid,
  SIGTERM)` + сброс в `-1`; вызывается и из `close()` (перед `_exit()`), и из
  `~ApplicationImpl()` (страховка на путях, где `close()` не добегает —
  исключение после спавна, либо `SHITTY_FOR_TESTS`, где `close()` останавливает
  цикл вместо `_exit()`, и `run()` возвращается штатно). Идемпотентна: второй
  вызов — no-op.

## Ключевые решения

**Сравнение путей — только `realpath`, никогда строк.** И у ownConfigPath
(разрешается ещё раз внутри `resolveQuickCompanionConfig`, хотя `options.cpp`
уже записал путь как есть — CLI `-config relative/path.toml` не гарантированно
канонический), и у `quickCompanion` (после `~`-раскрытия). Юнит-тест
`SelfReferenceDetectedThroughDifferentSpelling` — не гипотетический: ровно тот
случай из постановки, `~/.config/shitty/shitty.toml` против
`/Users/kibomibo/.config/shitty/shitty.toml`, только через `.../x` vs `..././/x`
как деterministic-эквивалент (без мутации `$HOME` теста, см. «Что честно не
проверено»).

**`quick == true` — гарантированный, не «probable», обрыв рекурсии.** Гейт
стоит первым делом в `spawnQuickCompanion()`, до всякого чтения файловой
системы: панель **физически не может** дойти до спавна, что бы ни лежало в её
`quickCompanion` (унаследованном через `import`). Живой прогон ниже гоняет
ровно этот сценарий — `quick.toml` импортирует `main.toml`, в котором есть
`quickCompanion` — и подтверждает **два** процесса, не три.

**Найденный и починенный по ходу баг: `SIGCHLD` от спутника мог испортить
код выхода основного терминала.** `childSignalHandler` реапит **любого**
ребёнка (`waitpid(-1, ...)`), записывая его код выхода в `lastChildStatus`,
которым `close()` пользуется, чтобы отдать код выхода **настоящей** сессии
шелла. Спутник — тоже ребёнок этого процесса, и без спецкейса его код выхода
(если он умер раньше последней сессии) молча подменил бы код выхода основного
терминала. Правка — три строки в `childSignalHandler`: реап спутника не
записывает `lastChildStatus`, только сбрасывает `quickCompanionPid`.

**Спутник умирает сам — не респавним, ничего не логируем.** Проверено
живьём (см. ниже): основной процесс продолжает работать как обычно, никакой
попытки поднять спутника заново нет. Именно так и задумано — «держи просто».

**`SIGKILL` по основному процессу — спутник осиротеет, это ограничение, не
дефект.** `SIGKILL` необрабатываем в принципе, ни `close()`, ни
`~ApplicationImpl()` не запустятся. Честно, но не единственный такой случай:
**обычный `SIGTERM`, посланный основному процессу напрямую (не через закрытие
окна и не через конец последней сессии), тоже обходит `close()`** —
`setupSignals()` не трогает диспозицию `SIGTERM` вовсе (только `SIGINT`/
`SIGQUIT` сброшены на `SIG_DFL`, `SIGTERM` остаётся тем, что было при старте
— обычно тоже `SIG_DFL`, то есть немедленное завершение без единой строки
C++-кода). Не чинил: это тот же класс ограничения, что и у PTY-детей
сегодня (`PtyHandleImpl`-деструктор с `kill(-pid, SIGHUP)` тоже не добежит на
голом `SIGTERM`/`SIGKILL`) — компаньон не хуже и не лучше остальных дочерних
процессов в этом отношении, специальный обработчик `SIGTERM` только ради
спутника было бы асимметричным усложнением, которого просили избегать.
**Штатные же пути гашения — закрытие окна и конец последней сессии шелла —
проверены живьём и работают.**

**Мусорный путь / несуществующий файл не блокирует основной терминал.**
Решение: диагностика в `stderr`, `spawnQuickCompanion()` возвращает `-1`,
`run()` продолжает как ни в чём не бывало. Обоснование то же, что для
самоссылки — спутник придаточная фича, а не критическая часть запуска
терминала; ломать сам терминал из-за опечатки в пути к панели было бы хуже,
чем просто не показать панель.

## `Accessory` для quick-окон — решено, сделано

**Факт проверен до правки, как и просили.** `ensureApplication()` (единственное
место, где выставляется `activationPolicy`, вызывается ровно один раз на
процесс из `createWindow()`, у которой уже есть `options.quick`) стала
принимать `quick` и ставить `NSApplicationActivationPolicyAccessory` вместо
`Regular` **только когда `quick == true`**. Живой прогон (см. ниже) подтвердил
и то, что без иконки в Dock (`NSWorkspace`-факт снаружи процесса, не
самооценка), и то, что **ввод с клавиатуры доходит до шелла** — набранные
символы дошли до пайпа PTY побайтово, через реальный `ctrl+grave`-хоткей.
`Regular` для всех остальных окон не тронут — условие строго на `quick`, не на
`quickCompanion`.

### Опция в тестовом протоколе — сознательное отклонение от буквы задачи

Задача просила «добавить опцию в ответ `OPTIONS`, иначе она не видна
python-тестам». Не сделано, и вот почему: `quickCompanion` — свободный текст
(путь), а `OPTIONS` в `test_mode.cpp` сегодня отдаёт **только** числа/булевы —
ни `quickHotkey`, ни `title`, ни `shell`, ни `dump` (все точно такие же
свободные строки) там тоже нет ни в каком виде. Пропихнуть путь в
пробел-разделённый формат `key=value` было бы либо ломким (путь с пробелом
порвал бы парсер), либо потребовало бы hex-кодирования, которого сегодня нет
ни у одного строкового поля. Вместо слома этого паттерна — ничего не
добавлено, ровно как для `quickHotkey`. Что действительно проверяемо
python-тестами сегодня — и проверено — сама проводка опции через `optionsTable`
(`-quickCompanion` виден в `-help`, документация `# CLI:` сверяется
существующим тестом `test_example_config_documents_every_public_cli_option`).
Реальное поведение спавна тестовым режимом вообще не достигается: `runTestMode()`
возвращается из `run()` раньше точки спавна, так что живая проверка (ниже) —
единственный способ проверить его функционально.

### Живой прогон (реальный бинарь, реальный хоткей)

Все прогоны — на реальных `.build/st`, без синтетических пробников. Конфиги
лежали в `scratchpad/`, не в дереве.

**Основной сценарий — два конфига из постановки, `pgrep` вживую:**

```
$ .build/st -config main.toml -e sleep 60 &
$ pgrep -fl '\.build/st'
65102 .build/st -config .../main.toml -e sleep 60
65104 .build/st -config .../quick.toml
```

Ровно **два** процесса. `quick.toml` при этом делает `import = ["main.toml"]`
— то есть содержит `quickCompanion` унаследованным из `main.toml` — и третий
процесс **не появляется**: гейт `quick == true` в `spawnQuickCompanion()`
отработал. `stderr` основного процесса пуст (никакой диагностики — спавн
прошёл штатно).

**Активационная политика в том же прогоне** (`NSWorkspace.runningApplications`,
внешний факт, не самооценка процесса):

```
main (pid=65102):       policy=0 (Regular)
companion (pid=65104):  policy=1 (Accessory)
```

**Выход основного → спутник погас.** Основной процесс запущен с `-e sleep 60`;
конец сессии смоделирован убийством именно дочернего `sleep` (не самого `st` —
первая попытка через `pkill -f "sleep 60"` случайно словила и сам `st`, чья
командная строка тоже содержит `sleep 60`, и убила его сырым `SIGTERM` в обход
`close()` — методическая ошибка теста, не баг кода; починено переходом на
`kill <точный pid>`):

```
$ kill $(pgrep -x sleep)
$ pgrep -fl '\.build/st'
(пусто)
```

Оба процесса исчезли — путь «конец последней сессии → `close()` →
`stopQuickCompanion()`» подтверждён.

**Спутник умер сам — не респавнится.** Убит напрямую (`kill <companion-pid>`);
основной процесс остался жить в одиночку, `stderr` пуст (никакой попытки
поднять его снова, никакого лишнего лога):

```
до:    23627 main   23631 companion
после: 23627 main
```

**Самоссылка — оба варианта.** Текстуально одинаковый путь и путь с другим
написанием того же файла (канонический тест, не строковый):

```
quickCompanion = "<file>"           (в самом <file>) → "refers to this process's own config file; not spawning a companion"
quickCompanion = "<dir>/./<file>"   (в <file>)        → то же
```

В обоих случаях — **один** процесс, основной терминал не заблокирован.

**Мусорный/несуществующий путь:**

```
quickCompanion = "/private/.../does_not_exist.toml"
→ "cannot resolve /private/.../does_not_exist.toml; not spawning a companion"
```

Основной процесс отработал свою команду (`-e sleep 1`) и вышел штатно — не
заблокирован отсутствующим файлом спутника.

**`~`-раскрытие сквозь весь путь.** Отдельный `HOME`, подставленный только
этому процессу (не трогая настоящий `$HOME`): `shitty.toml` с
`quickCompanion = "~/.config/shitty/quick.toml"`, найден через
`XDG_CONFIG_HOME`-less дефолтный путь, спутник поднялся с уже развёрнутым
абсолютным `-config`:

```
$ env -u XDG_CONFIG_HOME HOME=<fakehome> .build/st -e sleep 60 &
$ pgrep -fl '\.build/st'
main       .build/st -e sleep 60
companion  .build/st -config <fakehome>/.config/shitty/quick.toml
```

**`Accessory` и клавиатурный ввод — доказано побайтово, не «предположительно
работает».** `-e python3 echo_input.py <файл>` (нестандартный процесс: читает
`stdin` по одному байту и пишет его без буферизации сразу в файл — обычный
`cat > файл`, перенаправленный не через `-e` напрямую, буферизуется полностью
на запись в файл и не годится для проверки без досылки EOF). Реальный хоткей
(`osascript ... key code 50 using control down`, тот же путь, что F4/F5/T7),
затем три нажатия и `Return`:

```
до показа: NSWorkspace policy=1 (Accessory)
osascript key code 50 using control down     → окно показано
osascript keystroke "abc" + key code 36      → Return
$ od -c typed_output.txt
ф ф ф \n
```

(`ф` — то, что физическая клавиша "a"/"b"/"c" даёт на активной в этой сессии
кириллической раскладке; важен сам факт **трёх** символов + `\n`, не их
конкретные глифы — раскладка та же особенность среды, что задокументирована
в предыдущих отчётах волны.) Первая попытка без `Return` дала пустой файл —
это не провал теста, а канонический (line-buffered) режим самого pty: без
перевода строки ядро не отдаёт буфер читающему процессу вообще, будь то
`Regular` или `Accessory` окно — обнаружено и учтено, не имеет отношения к
активационной политике.

Все конфиги и вспомогательные скрипты — в
`scratchpad/` этой сессии, не в дереве репозитория.

## Критерии приёмки — поимённо

| Критерий | Статус |
|---|---|
| Один запуск даёт обычный терминал + отдельный процесс с quick-панелью | Да — `pgrep`, два процесса, разные `-config` |
| `quickCompanion` игнорируется при `quick = true` (обрыв рекурсии) | Да — гейт первым делом в `spawnQuickCompanion()`, живой прогон с реальным `import`-циклом даёт ровно 2 процесса, не 3 |
| Отказ на самоссылку, сравнение канонических путей | Да — `realpath` с обеих сторон, юнит-тест на разное написание одного файла, живой прогон обоих вариантов |
| `~` раскрывается | Да, живой прогон с изолированным `HOME` |
| Гашение спутника при выходе основного | Да, живой прогон (закрытие последней сессии) |
| Спутник, умерший сам, не респавнится | Да, живой прогон, `stderr` пуст |
| `SIGKILL` основного — спутник осиротеет | Задокументировано как ограничение, не чинилось (по постановке) |
| Мусорный путь не блокирует основной терминал | Да, живой прогон + диагностика в `stderr` |
| `Accessory` для quick-окон, ввод по-прежнему доходит | Сделано и доказано побайтово; `Regular` для остальных не тронут |
| Опция добавлена в оба toml с `# CLI:`/em dash | Да, `test_example_config_documents_every_public_cli_option` зелёный |
| Опция видна в ответе `OPTIONS` тестового режима | **Не сделано осознанно** — свободный текст, как `quickHotkey`/`title`/`shell`/`dump`; см. раздел выше |
| Спавн средствами проекта (`fork`/`execvp`, без новых зависимостей) | Да, тем же способом, что `pty.cpp` |

## Что честно не проверено

- **Настоящий `SIGTERM` мимо `close()`.** Задокументирован как тот же класс
  ограничения, что `SIGKILL` (см. «Ключевые решения») — не почищено
  (решение осмысленное, не забывчивость), но и не измерено на живом
  процессе намеренно (последствие очевидно из чтения `setupSignals()`:
  диспозиция `SIGTERM` не трогается вовсе).
- **`~`-тест без юнит-теста.** `expandTilde()` — `static` в анонимном
  namespace `quick_companion.cpp`, не выставлена в заголовок (как и
  `resolveImportPath()` в `options.cpp` — там она тоже не юнит-тестируется
  отдельно, только через python `test_import_nests_and_expands_home`).
  Проверено живым прогоном (см. выше), не изолированным C++ юнитом с
  подменой `$HOME` — мутация `$HOME` в процессе, где юнит-тесты **всех**
  сьютов делят один бинарь, звучала опаснее пользы.
- **Linux/Wayland — спавн, но не поведение спутника.** `quick_companion.cpp`
  не обёрнут в `#if defined(__APPLE__)` намеренно (см. выше) — `fork`/`execvp`
  портируемы, спавн и гашение должны работать на Linux тем же кодом. Но
  сама фича `quick` там сегодня не более чем флаг: `ShowPlacement::TopOfActiveScreen`
  на Wayland равна `Centered`, хоткей-модуля нет вовсе — то есть спутник на
  Linux поднялся бы **обычным видимым окном**, а не скрытой панелью. Это не
  регрессия этой задачи (то же самое верно для голого `-quick` на Linux уже
  сегодня), но не проверено на реальной Linux-машине — нет локального
  IX-реалма, та же оговорка, что у T1/F1/T7 в этой ветке.
- **Второй монитор** — не проверялся, вне скоупа задачи (геометрия/экран не
  трогались).
- **Визуальное** — Screen Recording недоступен в этой среде (см. предыдущие
  отчёты волны). Все факты выше — `pgrep`, `NSWorkspace.activationPolicy`,
  байты в файле — не требуют этого разрешения. Человеку стоит визуально
  подтвердить отсутствие второй иконки в Dock и что панель действительно
  выглядит как панель:
  ```sh
  cd /Users/kibomibo/Projects/github.com/shitty
  cp bin/st/shitty.toml /tmp/main-demo.toml   # раскомментировать/задать quickCompanion
  ./.build/st -config /tmp/main-demo.toml
  ```
