# T7. `quickGeometry` — размер и позиция quick-окна

**Ветка:** `feat/window-chrome-upstream`
**Границы владения:** `lib/shitty/options.cpp`, `options.h`, `bin/st/shitty.toml`,
`bin/pt/pretty.toml`, `lib/shitty/test_mode.cpp`, `ext/plt/window.h`,
`ext/plt/platform_cocoa.mm`, `lib/shitty/application.cpp`, новые
`lib/shitty/quick_geometry.{h,cpp}` + юнит-тест, README (раздела про `quick` в
README не оказалось — трогать нечего).

## Что сделано

Новая опция `quickGeometry = "<W>x<H>+<X>+<Y>"` задаёт размер и позицию
quick-окна одной строкой. Каждое из четырёх чисел — пиксели или проценты от
рабочей области (`visibleFrame`) экрана, на котором сейчас курсор (логика
выбора экрана не тронута). `X`/`Y` — смещение от левого верхнего угла рабочей
области. Дефолт `100%x40%+0+0` воспроизводит прежнее зашитое поведение —
проверено побитово (см. ниже).

```toml
quick = true
quickHotkey = "ctrl+grave"
quickGeometry = "80%x60%+10%+10%"
```

## Изменённые файлы

- `lib/shitty/quick_geometry.h`, `lib/shitty/quick_geometry.cpp` (новые) —
  чистый парсер `bool parseQuickGeometry(StringView, plt::QuickGeometry&)`, без
  платформенных зависимостей, вынесен по прецеденту `quick_hotkey_chord.{h,cpp}`
  именно ради юнит-теста. Делает всю валидацию: формат, пустые/недостающие

- `ext/plt/window.h` — контракт: `plt::QuickGeometryDim` (пиксель/процент +
  значение), `plt::QuickGeometry` (width/height/x/y, дефолты воспроизводят
  старое жёсткое размещение), поле `WindowOptions::quickGeometry`. Поправлен
  устаревший комментарий у `ShowPlacement` — раньше там было сказано, что
  геометрия «ничем не настраивается через `WindowOptions`», теперь настраивается.
- `lib/shitty/options.h` — поле `Options::quickGeometry` (тип `plt::QuickGeometry`,
  отсюда `#include <plt/window.h>`).
- `lib/shitty/options.cpp` — запись в `optionsTable`, `OptionsParser::getQuickGeometry()`
  (валидация до применения, диагностика при отказе — по образцу `getGeometry()`),
  вызов в `parse()`.
- `lib/shitty/application.cpp` — одна строка: `.quickGeometry = composer.opts->quickGeometry`
  при сборке `WindowOptions`, тем же способом, что `quick`/`transparentTitlebar`.
- `ext/plt/platform_cocoa.mm` — `WindowImpl` хранит `quickGeometry` (мирроринг
  паттерна поля `quick`), `topOfActiveScreenFrame()` стала методом класса вместо
  свободной функции и считает фрейм по `quickGeometry` вместо жёстких `visible.size.width`/
  `visible.size.height * 0.4`. Добавлены `resolveQuickGeometryDim()` и `clampRange()`
  (безымянный namespace, `static`, по `STYLE.md`).
- `bin/st/shitty.toml`, `bin/pt/pretty.toml` — строка документации `# CLI:
  -quickGeometry <W>x<H>+<X>+<Y> — ...` (настоящий em dash) и `quickGeometry =
  "100%x40%+0+0"`, сразу под `quickHotkey`.
- `lib/shitty/test_mode.cpp` — 8 полей в ответе `OPTIONS`:
  `quick_geometry_{w,h,x,y}` и `quick_geometry_{w,h,x,y}_percent` (процент/пиксель —
  отдельным булевым полем, т.к. `terminal.options()` в python-харнессе парсит
  каждое поле как `int`, строку принять не может).

## Ключевые решения

**Дефолт обязан быть побитово идентичен старому поведению.** Опасность была в
порядке операций с плавающей точкой: старый код считал высоту как
`visible.size.height * 0.4` (один литерал, одна операция), а наивная формула
`extent * value / 100` для `value=40` считает `(extent*40)/100` — два деления/умножения
вместо одного, с риском разойтись в последнем бите из-за двойного округления.
Решение — `resolveQuickGeometryDim()` сначала делит `value/100.0` (что при
`value=40` даёт **тот же самый** double, что и литерал `0.4` — оба являются
ближайшим представимым double к истинному 0.4), и только потом умножает на
`extent`, то есть повторяет исходную пару операций дословно. Для `width` (100%)
`extent * 1.0 == extent` точно по IEEE 754. Подтверждено не только рассуждением,
но и живым замером (см. «Проверка» — оба варианта дефолта дали идентичный
фрейм `x=0 y=33 w=1728 h=434`).

**Клэмп, а не отказ, при геометрии, не помещающейся на экран.** `quick_geometry.cpp`
валидирует каждый компонент **по отдельности** (процент в 0..100, пиксели в
0..`UINT16_MAX`) — но не может знать, помещаются ли эти четыре числа вместе на
**конкретный** экран: `1200px` ширины + `90%` смещения по X каждое в отдельности
корректно, но вместе уводят окно за правый край экрана уже на самом узком
дисплее. Экран известен только в `platform_cocoa.mm`, в момент показа — там
`width`/`height` клэмпятся в `[1, extent]`, а `x`/`y` — в `[0, extent - size]`
уже после клэмпа размера. Так окно гарантированно остаётся целиком на экране
при любых числах, а не только при разумных, и дефолтные значения ни разу не
задевают ни один клэмп (проверено — см. вывод формулы выше).

**Отвергнуто:** отказ на старте при потенциально неподходящей геометрии — экран
на момент парсинга опций ещё не известен (мультимониторность, окно выбирает
экран под курсором в момент показа, а не при старте), поэтому такая проверка
либо ничего не значила бы, либо требовала произвольного «эталонного» экрана,
неверного для части машин.

### Живой прогон (GUI, реальный хоткей)

**Важная находка про окружение:** самодельный `RegisterEventHotKey`-пробник
(без `NSApplication`, голый `CFRunLoopRun()`) синтетический хоткей через
`osascript`/System Events и через сырой `CGEventPost` **не получал вовсе**
(0 из 5 попыток каждым способом) — по всей видимости, доставка Carbon
hot-key событий требует настоящего Cocoa/Carbon app-контекста
(`[NSApplication sharedApplication]` + `finishLaunching`), которого у
голого `CFRunLoopRun()` нет. **Реальный `.build/st` этой проблемы не имеет** —
ниже это подтверждено количественно тем же методом, что и в отчётах F4/F5
(`osascript ... key code 50 using control down`, тот же путь
`RegisterEventHotKey`, каким сработало бы физическое нажатие; геометрия и
`kCGWindowLayer` — через `CGWindowListCopyWindowInfo`, Screen Recording не
нужен). Экран этой сессии: `visibleFrame = (0,0) 1728×1084` (полный кадр
`1728×1117`, `33px` под меню-бар).

Таблица «заданная геометрия → полученный фрейм» (формат вывода пробника,
координата Y — от **верха** экрана):

| Конфиг | Ожидание (расчёт по формуле) | Измерено (`CGWindowListCopyWindowInfo`) |
|---|---|---|
| без `quickGeometry` | `x=0 y=33 w=1728 h=433.6` | `x=0 y=33 w=1728 h=434 layer=25` |
| `"100%x40%+0+0"` (явный дефолт) | то же | `x=0 y=33 w=1728 h=434 layer=25` |
| `"1200x600+100+50"` | `x=100 y=83 w=1200 h=600` | `x=100 y=83 w=1200 h=600 layer=25` — точное совпадение |
| `"80%x30%+10%+0"` | `x=172.8 y=33 w=1382.4 h=325.2` | `x=172 y=33 w=1383 h=326 layer=25` — расхождение ≤1px, snapping к сетке backing store (экран Retina, scale=2.0), не ошибка вычисления |
| `"3000x3000+0+0"` (клэмп размера) | клэмп до `x=0 y=33 w=1728 h=1084` | `x=0 y=33 w=1728 h=1084 layer=25` — точное совпадение, окно не вылезло за экран |
| `"500x300+90%+90%"` (клэмп смещения) | смещение `1555.2,975.6` клэмпится до `1228,784` (bottom-up) → top-down `x=1228 y=817` | `x=1228 y=817 w=500 h=300 layer=25` — точное совпадение |

Оба варианта дефолта (опция не задана / задана явно строкой `"100%x40%+0+0"`)
дали **идентичный** фрейм — побитовое воспроизведение старого поведения
подтверждено не только формулой, но и живым замером.

**Показ по хоткею — количественно, дефолтная геометрия:** 24 цикла
показ/скрытие подряд (пауза 0.6с между действиями, тот же темп, что и в
отчёте F5). **24 из 24 показов** дали ровно `x=0 y=33 w=1728 h=434 layer=25`,
0 аномалий; ни одного случая, когда скрытие не увело окно с экрана
(`count=0` каждый раз).

**`quick = false` не задет:** `quick = false` + `quickGeometry = "1200x600+100+50"`
в конфиге → окно открылось как обычное, `layer=0`, `x=869 y=39 w=854 h=1073` —
дословно то же значение, что задокументировано как эталонная геометрия
обычного окна в предыдущих отчётах волны (`869,39 854x1073`).

Все временные пробники и конфиги — в `scratchpad/t7/` и `/tmp/qgtest/`, не в
дереве репозитория, не коммитились.

## Критерии приёмки — поимённо

| Критерий | Статус |
|---|---|
| Дефолт побитово воспроизводит старое поведение | Да — расчёт (порядок float-операций сохранён) + живой замер (два варианта дефолта дали идентичный фрейм, совпадающий с задокументированным `x=0 y=33 w=1728 h=434`) |
| Экран выбирается тот же, логика не менялась | Да — `screenUnderPointer()` не тронута, только потребитель её результата (`topOfActiveScreenFrame()`) стал читать `quickGeometry` вместо жёстких констант |
| Окно не уезжает за экран при абсурдных значениях | Клэмп в `topOfActiveScreenFrame()`: размер в `[1, extent]`, смещение в `[0, extent - size]` после клэмпа размера. Подтверждено живьём двумя случаями (переразмер и переизбыток смещения) |
| Опция трогает все обязательные файлы | `options.cpp`/`.h`, оба toml, `test_mode.cpp` — сделано |
| Документация `# CLI:` с настоящим em dash, тест `test_config.py` зелёный | Да, `test_example_config_documents_every_public_cli_option` проходит |
| Валидация до применения, диагностика на старте | Да, 9 невалидных случаев дают `rc=255` и понятное сообщение, ни одного молчаливого фолбэка |
| Стиль (`stl::`, брейсы, одна строка, методы вне класса) | Соблюдено; `topOfActiveScreenFrame()` объявлена в классе, определена вне |
| `./style.py` полным прогоном не запускался | Верно, только `clang-format -lines=` |
| Парсер вынесен отдельно + юнит-тест | `quick_geometry.{h,cpp}` + `quick_geometry_ut.cpp`, 14 тестов |

## Что честно не проверено

- **Второй монитор.** На машине один экран; выбор геометрии относительно
  экрана под курсором на нескольких дисплеях не проверялся ни в этой задаче,
  ни в предыдущих волнах.
- **Визуально** (совпадает ли то, что человек увидит, с числами) — Screen
  Recording недоступен в этой среде (нет TCC-разрешения), как и во всех
  предыдущих отчётах волны. Числа (позиция/размер/layer) проверены
  Accessibility- и CGWindowList-путями, которые разрешения не требуют;
  человеку остаётся визуально подтвердить, что окно на экране выглядит так,
  как ожидается, например:
  ```sh
  cd /Users/kibomibo/Projects/github.com/shitty
  ./.build/st -quick -config <(echo 'quick = true
  quickHotkey = "ctrl+grave"
  quickGeometry = "80%x60%+10%+10%"')
  ```
  и нажать `ctrl+grave`.
- **Wayland/headless-сборка.** `WindowOptions::quickGeometry` — новое поле в
  общей структуре; Wayland/Headless-бэкенды его не читают (как и `quick`
  сегодня), так что заглушки не понадобились. Кросс-компиляция под Linux
  из-под macOS не проверялась (нет локального IX-реалма для этой опции, та же
  оговорка, что у T1/F1 в этой ветке).
- **Один самодельный вывод, который стоило задокументировать отдельно:**
  голый `RegisterEventHotKey` без `NSApplication`-контекста синтетический
  хоткей вообще не получает в этой среде — если будущей задаче понадобится
  лёгкий пробник хоткея без полного бинаря `st`, это нужно учесть заранее
  (пробник должен звать `[NSApplication sharedApplication]` +
  `finishLaunching`, не голый `CFRunLoopRun()`).

## Ревьюеру

Смотреть в первую очередь: `resolveQuickGeometryDim()`/`clampRange()` и
`topOfActiveScreenFrame()` в `platform_cocoa.mm:1277-1332` — комментарий там
объясняет порядок float-операций и зачем клэмп именно там, а не в
`quick_geometry.cpp`. Остальное — прямое проведение уже существующего
паттерна (`quick`/`transparentTitlebar`) через `options.h` → `WindowOptions` →
`WindowImpl`.
