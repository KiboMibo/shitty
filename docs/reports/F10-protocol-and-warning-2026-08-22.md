# F10 — опции волны 10 в тестовом протоколе, и предупреждение вместо молчания

Ветка `feat/F10-protocol-and-warning`, база `master` = `b6480ea7` (`git rev-parse`).

**Статус: готово.** Плюс одна находка сверх задания, подтверждённая мутацией с положительным
контролем.

## Сверка с деревом прежде работы

Командир написал, что `F10` не начата. Верно **для `master`** и неверно вообще: работа была сделана
на ветке `feat/T10-followup` от `c8b25900` и не смержена — командир смотрел
`feat/T10-translucency`, где её и не могло быть. Проверено содержимым, а не памятью:

```
git show master:lib/shitty/test_mode.cpp | grep -c background_opacity   -> 0
git show master:lib/shitty/options.cpp   | grep -c "nothing to blur"    -> 0
git log --oneline feat/T10-followup -5                                  -> пять коммитов
```

Обе находки в `master` действительно отсутствовали. Перенесены сюда `cherry-pick`, ветка заведена
от `b6480ea7`, старая не мержится.

## 1. Тестовый протокол

`test_mode.cpp` печатал все оконные опции волн 3–9 и не печатал две опции волны 10 — чёрный ящик
не мог отличить значение, доехавшее до приложения, от потерянного по дороге, в волне, чей результат
в остальном судят глазами. Оба ключа дописаны рядом с `transparent_titlebar`.

Три теста, а не один: умолчания, значение из конфига и **командная строка поверх конфига**. Третий
нужен потому, что без него ключ, прибитый к константе, прошёл бы первые два — и это не рассуждение,
а мутации `MO`/`MO2`, сделанные ровно так.

## 2. Предупреждение вместо молчания

```
shitty: -backgroundBlur has nothing to blur while -backgroundOpacity is 100;
        lower -backgroundOpacity to let the desktop show through
```

Названа опция, за которую браться, а не только факт игнорирования. Предупреждение, а не отказ, по
той же причине, по которой опция не отвергается вовсе: `backgroundOpacity` перезагружаема, и
конфиг, законный при одном её значении и фатальный при другом, превращает правку строки в отказ
старта.

Место — `options.cpp`, где обе величины уже известны: работает на всех платформах и не зависит от
того, пришло значение из конфига или с командной строки.

**Два теста, а не один.** Второй — контроль: при прозрачном фоне строки быть не должно. Без него
оба утверждения прошли бы и на сборке, ругающейся при каждом старте (мутация `MQ`).

### Побочно: набор не умел проверять stderr живого терминала

`run_startup_failure()` годится только для запусков, которые **падают**; при валидном конфиге
терминал живёт, и обёртка упирается в таймаут. `Shitty` stderr не перехватывал вовсе. Добавлены
`capture_stderr=False` и `stderr_text()`, читаемый после `close()` — трубу никто не разгребает,
пока процесс жив, а стартовые предупреждения пишутся до `READY` и помещаются многократно.

## 3. `MG` жива на голове `master` — отчёт `R10-test` в этой строке неверен

### Что заявлено и что измерено

`panes-R10-test.md` сообщает `MG` (`storeSolidPixel()`: `1.0` → `backgroundAlpha ()`) **убитой**
утверждением `underline.marks > 0 && underline.disagreements == 0` (`render_reference_ut.cpp:1815`).

На голове `b6480ea7` мутация **выживает**:

```
MG-shader-solid-pixel-follows-alpha: SURVIVED OK=944 ERR=0 TOTAL=944 (lost 0)
                                   | pytest passed=51 failed=0 (lost 0)
```

Оба названных им теста в этом прогоне **присутствовали и были зелёными** — проверено по имени в
логе, а не по числу:

```
+ MetalPanes::TheSolidMarksReachTheTextureUnfadedAtAnyOpacity
+ RendererFrameContract::EverySolidMarkKeepsItsBytesWhateverTheBackgroundOpacity
```

### Положительный контроль — чтобы это не оказалось поломкой прибора

Утверждать «мутация выжила» на основании зелёного прогона опасно: точно так же выглядит стенд, до
которого правка шейдера не доехала. Поэтому в **тот же файл**, тем же драйвером, поставлена
мутация, которая двигает **цвет**, — `MH`, блочный курсор вне `solidCell`:

```
CONTROL-MH-block-cursor-not-solid: KILLED OK=943 ERR=1 TOTAL=944 (lost 0)
```

Убита. Значит правки `render.comp` доезжают до бинаря и тесты их читают, а `MG` выживает **по
природе дефекта**, а не по вине стенда.

### Почему она невидима, и почему тест `R10-test` тут ни при чём

Мутация меняет **альфу и только альфу**: `storePixel (position, color, ...)` пишет
`vec4 (color, alpha)`, цвет в выражении не участвует. Все пути чтения кадра в дереве отдают
**RGB** — `captureOutput()` (`render.h:110`), `plt::HeadlessPixelFormat` с единственным значением
`RGB8`, `putPixel()` эталонного рендерера, выбрасывающий альфу. То есть дефект живёт ровно в той
половине, которую ни один прибор не читает.

**Тест `R10-test` написан правильно.** Его конструкция — «один кадр при 100 и при 50, каждый
пиксель марки обязан держать те же байты, и марок должно быть больше нуля» — сильнее моей
исходной, и она ловит всё, что двигает цвет. Она была слепа к одному дефекту не из-за формулировки,
а из-за того, что цвет и альфа в шейдере писались **порознь**.

### Починка — и его же тест начинает видеть

В premultiplied-альфе цвет и альфа обязаны ездить вместе. `storeAtAlpha()` ставит умножение и альфу
в одно выражение, так что взять одно без другого нельзя:

```glsl
void storeAtAlpha (ivec2 position, vec3 color, float alpha)
{
   storePixel (position, color * alpha, alpha);
}
```

После этого та же мутация краснеет — **на той самой строке, которую `R10-test` и назвал**:

```
MG-after-fix: KILLED OK=943 ERR=1 TOTAL=944 (lost 0)
    underline.marks > 0 && underline.disagreements == 0 failed, at render_reference_ut.cpp:1815
    - MetalPanes::TheSolidMarksReachTheTextureUnfadedAtAnyOpacity
```

**Ни одного теста не добавлено.** Правка не приносит нового прибора — она делает дефект видимым для
уже написанного. Поведение не меняется: при `1.0` умножение — тождество, набор дал те же **951**.

Контрольная мутация на саму починку — `MU`, `storeAtAlpha()` теряет умножение — убита двумя
тестами, то есть новая функция не пустая.

`storePixel()` остался примитивом для единственного вызывающего, чей цвет уже композит и не должен
умножаться второй раз; это сказано у него в комментарии, чтобы следующий не «починил» его
единообразия ради.

## Дублирование работы, о котором надо знать

Борд в `c8b25900` поручал мне закрытие дыры `R10-test`. Я его сделала на `feat/T10-followup`; его
же **параллельно** сделал `R10-test`, и его версия в `master`. Две команды делали одну работу по
одному поручению.

Сошлись независимо, включая неочевидное: **двух панелей для шва не нужно** — цикл полос в
`render_metal.mm` идёт после цикла панелей и обходит то, что передали в `setSeams()`, независимо от
их числа. Записано в обоих отчётах.

Его версия шире моей (свойство «те же байты при 100 и при 50» вместо моего «множество цветов
ячейки») и остаётся в `master`; своё дублирующее покрытие я сюда **не несу** — только починку `MG`,
которой у него нет.
