# F3c. Разбор чорда вынесен в тестируемый вид

**Ветка:** `feat/window-chrome` · **План:** `docs/plans/2026-08-17-window-chrome-quick-terminal.md`
**Источник:** `docs/plans/reviews/window-chrome-R3-test.md`, находка 1

## Сигнатура вынесенной функции

```cpp
bool parseQuickHotkey(stl::StringView text, u32& modifiers, u32& keyCode);
```

Объявлена в `quick_hotkey_chord.h`, определена в `quick_hotkey_chord.cpp`.

## Что сделано

Чистое перемещение, как и предлагал R3-test: `quickHotkeyKeyNames[]`,
`quickHotkeyModifierBit()` и `parseQuickHotkey()` перенесены из анонимного
`namespace` в `ui_quick_hotkey.mm` в новую пару `quick_hotkey_chord.h`/`.cpp`
— обычный `.cpp`, без Objective-C. `ui_quick_hotkey.mm` подключает новый
заголовок и зовёт функцию вместо собственного определения.

Тело `parseQuickHotkey` не изменилось ни на строку — тот же цикл разбора
токенов, та же таблица имён клавиш, та же логика модификаторов. Внутренние
локальные переменные оставлены как `UInt32` (Carbon-тип, используется
только внутри `.cpp`, который уже подключает `<Carbon/Carbon.h>`), а на
границе с публичной сигнатурой пишутся в `u32&` — оба типа резолвятся в
`unsigned int`/`uint32_t` одинаковой ширины, неявная конверсия работает без
приведений.

### Тип в заголовке — без `<Carbon/Carbon.h>`

Задание допускало «если избежать нельзя — так и напиши» — избежать
получилось. Вместо `UInt32` в публичной сигнатуре используется
`u32` (`stl::sys::types.h`, `uint32_t`) — Carbon-специфика (`kVK_*`,
`controlKey`/`shiftKey`/`optionKey`/`cmdKey`, сам `UInt32`) целиком осталась
внутри `.cpp`. `quick_hotkey_chord.h` подключает только
`<std/str/view.h>` и `<std/sys/types.h>` — будущий `quick_hotkey_chord_ut.cpp`
сможет собираться без единого Objective-C или Carbon заголовка.

### Проверка исходного утверждения про `build.py`

Team-lead просил проверить самому, а не полагаться на утверждение R3-test:
собрал без единой правки `build.py`, чистым прогоном
`./build -j 8 st pt` — `quick_hotkey_chord.cpp` подхвачен глобом
`all_libshitty_sources = [source for source in build.glob("$(S)/*.cpp") ...]`
(`build.py:647`) автоматически, скомпилирован и слинкован в `libshitty_prod.a`
с первого раза. `libshitty_test_sources` строится из того же
`all_libshitty_sources` (`build.py:688-708`), то есть файл точно так же
попадёт в `unit_tests`, куда его понадобится линковать будущему
`quick_hotkey_chord_ut.cpp`. Подтверждение — не только чтением, но и живой
сборкой.

### Почему весь новый файл под `#if defined(__APPLE__)`

В отличие от `.mm`-файлов, которые попадают в сборку только через явный
дарвин-список в `build.py`, обычный `.cpp` подхватывается тем же глобом
**на всех платформах**, Linux включая. `<Carbon/Carbon.h>` там не существует
— без `#if defined(__APPLE__)` вокруг всего содержимого `.cpp` сборка на
Linux сломалась бы прямо на этом файле. Обернул оба новых файла целиком (не
только объявление функции) — на Linux это пустая единица трансляции, ничего
не компилирует и не линкует, ровно как сейчас ведёт себя (в теории —
никогда не собирался) `ui_quick_hotkey.mm`.

### Проверка S1 осталась на месте, не перенесена в `parseQuickHotkey`

R3-test предлагал два варианта: занести отказ на `modifiers == 0` прямо в
`parseQuickHotkey` (новым параметром) либо оставить отдельной проверкой
сразу после вызова. Выбрал второй — он же нынешнее поведение без единого
изменения:

- `parseQuickHotkey` возвращает `true`, если строка разобралась как чорд
  грамматически, **независимо** от того, есть ли модификатор — ровно то,
  что делала функция до переноса.
- Проверка `if (modifiers == 0) { ... }` со своей диагностикой
  (`'...' has no modifier (ctrl/shift/alt/super)`) осталась в конструкторе
  `QuickHotkeyUi`, сразу после вызова — как и была.

Почему не занёс внутрь: у отказа «нераспознанный чорд» и отказа «нет
модификатора» **разные тексты диагностики** на stderr — это часть
поведения, которое задание просило сохранить дословно
(«отказ на чорде без модификатора, отказ на нераспознанном» перечислены
как два разных пункта). Слив их в один `bool` из `parseQuickHotkey` заставил
бы вызывающую сторону терять эту разницу или городить второй возврат ради
неё. Вынесенная функция и так даёт R3-test всё нужное для теста
«зеркального случая» из плана: вызов `parseQuickHotkey("space", m, k)`
вернёт `true`, `k == kVK_Space`, но `m == 0` — ровно тот наблюдаемый факт,
который тест обязан поймать.

## Изменения

| Файл | Что |
|------|-----|
| `quick_hotkey_chord.h` (новый) | объявление `parseQuickHotkey`, MIT-шапка, весь файл под `#if defined(__APPLE__)` |
| `quick_hotkey_chord.cpp` (новый) | перенесённые `quickHotkeyKeyNames[]`, `quickHotkeyModifierBit()`, `parseQuickHotkey()`; MIT-шапка; весь файл под `#if defined(__APPLE__)` |
| `ui_quick_hotkey.mm` | удалён перенесённый код; подключает `quick_hotkey_chord.h`; локальные `UInt32 modifiers/keyCode` в конструкторе стали `u32` |

`build.py` не тронут — гипотеза подтверждена сборкой, не только чтением.

## За рамками

- Тесты в `quick_hotkey_chord_ut.cpp` не пишу — по заданию это территория
  R3-test.
- Поведение не менялось нигде, кроме физического расположения кода —
  никаких «заодно улучшил» не делал, поле для этого специально не искал.

## Ревьюеру

Главное решение — держать проверку `modifiers == 0` **вне**
`parseQuickHotkey`, а не заносить её внутрь. Обоснование в разделе выше;
если R3-test или ревью сочтёт, что тест всё равно проще писать при слитой
проверке — перенос обратно тривиален, весь код уже отделён в свой файл.
