# F-guard: гвард границы снова доказывает, что читал дерево

Ветка `fix/F-guard-selfcheck` от `master` = `67da3da3`. Правка — `1846d878`.
Файлы: `lib/vterm/check_includes.py`, `lib/shitty/render_vk.cpp` (только
комментарии). `build.py` не тронут.

## Что было сломано

**Прочитано** (`docs/plans/reviews/upstream-merge-R8-qa.md`, находка `T7.1`) и
**измерено** повторно здесь: на каталоге, где нет ни одного исходника, гвард
отвечал `EXIT=0`. Критерий, который не может покраснеть.

**Выведено** из истории файла: самозащита у гварда была, но как побочное
свойство. `G15` завела `ALLOWANCE` с ключом «файл + включение» и проверку
осиротевших ключей: ключ на файл, которого скан не встретил, краснит. Пока в
словаре что-то лежало, зелёный ответ означал «скан дошёл до дерева». Задача «А»
закрыла все шесть нарушений, `ALLOWANCE` стал пуст — и доказательство ушло
вместе с содержимым, не изменив цвета. Пустой `ALLOWANCE` при этом —
**желаемое** состояние, а не поломка: граница закрыта полностью.

## Что сделано

Три ворот перед записью штампа. Ни одни не требуют числа, которое пришлось бы
подкручивать при появлении нового файла в `lib/vterm` (сейчас 33 `*.h` и 48
`*.cpp` — **измерено**; порог по этому счёту был бы ровно тем, что «правят не
глядя»).

**1. Корень — это каталог, в котором лежит сам скрипт.**
`Path(sys.argv[1]).resolve() != Path(__file__).parent.resolve()` → красный.
Верно **по устройству**: гвард живёт внутри дерева, которое охраняет, и это не
меняется ни от переименования, ни от добавления, ни от удаления файлов. Ловит
пустой каталог, отсутствующий каталог, чужой каталог и устаревший путь из
`build.py`.

**2. Скан обязан засвидетельствовать формы, без которых не бывает C++-ядра:**
заголовок, файл реализации, угловое включение, включение в кавычках,
разрешившееся внутри ядра. Свидетельство собирается **самим сканом из того, что
он реально сопоставил**, поэтому «корень правильный, а glob/чтение/регулярка
молча перестали что-либо возвращать» — тоже красный. Формы выбраны как свойства
устройства библиотеки, а не её размера; **измерено**, что все четыре встречаются
в `lib/vterm` в изобилии (27 × `<std/str/view.h>`, 6 × `"color.h"`,
5 × `<lib/vterm/terminal_types.h>`, …).

**3. Классификатор обязан всё ещё классифицировать.** Это главное. При закрытой
границе и пустом `ALLOWANCE` **ни один файл `lib/vterm` не исполняет ни одну
ветку поиска нарушений** — весь смысл гварда стоит мёртвым кодом относительно
настоящего дерева. Поэтому ветки прогоняются по образцу, который несёт сам
скрипт, а ожидаемый ответ выписан целиком: два написания перехода в
`lib/shitty`, включение, не разрешающееся никуда, выход за пределы ядра,
трата разрешения и донос на повтор, осиротевший ключ. Это приём `F7` — премисса
внутри теста — приложенный к гварду: он утверждает, что ещё способен видеть,
прежде чем доложить, что видеть нечего. Плюс встречная проверка: скан по пустому
списку обязан не засвидетельствовать ничего, иначе свидетельство не собирается,
а объявляется.

Все трое живут **в скрипте**, по причине `G15`: узел уже держит скрипт во
входах, перестраивается сам, и второму месту правды взяться неоткуда. `build.py`
не менялся.

## Контроли (все — измерено)

Запуск прямой, минуя `./build`, — иначе штамп подставит CAS (`CLAUDE.md`).

**1. Отрицательный контроль.**

```
$ python3 lib/vterm/check_includes.py $S/empty $S/x.stamp
this check guards the directory it lives in, and was pointed at .../empty
instead of .../lib/vterm: ...
EXIT=1
```

То же на каталоге с исходниками, но чужом (`$S/decoy` c `a.h` + `a.cpp`) —
`EXIT=1`; на несуществующем каталоге — `EXIT=1`. Штамп в каждом случае **не
записан** (`ls $S/x.stamp` → `No such file or directory`).

**2. Положительный контроль.**

```
$ python3 lib/vterm/check_includes.py lib/vterm $S/k.stamp   # EXIT=0, штамп "ok"
$ python3 $PWD/lib/vterm/check_includes.py $PWD/lib/vterm $S/k.stamp   # как зовёт build.py: EXIT=0
$ ./build vterm_boundary --clear                              # [VB] {1/1}, EXIT=0
```

**3. Гвард не разучился ловить своё.** Проба: `#include <lib/shitty/composer.h>`
седьмой строкой в `lib/vterm/screen.cpp`.

```
the VT core cannot see the GUI: ...
  screen.cpp:7: <lib/shitty/composer.h> crosses into lib/shitty
EXIT=1
```

Названа пара «файл + включение», а не счёт. Проба снята, `EXIT=0` вернулся.

**4. `ALLOWANCE` жив.**

- Ключ на несуществующее нарушение (`{"vt_headless.cpp": {"lib/shitty/session.h": 1}}`)
  → `the boundary allowance names files this check never read` + `vt_headless.cpp`,
  `EXIT=1`. Свойство `G15` не сломано.
- Трата счёта: две одинаковые пробы в `screen.cpp` + ключ
  `{"screen.cpp": {"lib/shitty/composer.h": 1}}` → первая прощена, вторая
  (`screen.cpp:8`) доложена, `EXIT=1`.

## Мутационная проба самой защиты

Восемь мутаций в `check_includes.py`, каждая — прогон по настоящему `lib/vterm`.
Колонка «старый гвард» — **измерено** отдельно: `check()` по настоящему дереву
без новых ворот.

| # | Мутация | Старый гвард | Теперь |
|---|---|---|---|
| M1 | `*.cpp` → `*.cxx` в glob | зелёный | красный: `never saw a source file` |
| M2 | `read_text()` → `""` | зелёный | красный: не встретил ни углового, ни локального включения |
| M3 | регулярка `INCLUDE` перестала совпадать | зелёный | красный на премиссе (violations `[]`, свидетельство неполно) |
| M4 | ветка `if "lib/shitty" in include:` → `if False:` | **зелёный** | красный на премиссе |
| M5 | `if counted[...] > allowed.get(...):` → `if False:` | **зелёный** | красный на премиссе |
| M6 | проверка осиротевших ключей отключена | **зелёный** | красный на премиссе |
| M7 | ветка «выход за пределы ядра» → `elif False:` | **зелёный** | красный на премиссе |
| M8 | свидетельство предзаполнено `set(WITNESSES)` | зелёный | красный: `witness over no sources: [...] != []` |

M4–M7 — ровно тот класс, который настоящее дерево поймать не может: **измерено**,
что при каждой из них `check(lib/vterm)` даёт `violations 0, stale []`, то есть
до этой правки CI остался бы зелёным с выпотрошенным гвардом.

## Комментарии в `render_vk.cpp`

`render_vk.cpp:247` и `:2295` обещали, что «в день, когда бэкенд покажет две
панели», понадобится `PaneArenaMirror` из `render_arena.h`. **Прочитано**:
`2a11ffa7` снёс этот тип, и снёс с обоснованием — один `SpanShaper` на окно,
значит одна арена на план на всё окно, и смещения полос любой панели уже
указывают в неё. То есть ответ этих комментариев не просто устарел, а
**перевёрнут**: аренам вторая панель не стоит ничего.

Приведено в соответствие с сохранением назначения (оба по-прежнему объясняют,
что понадобится для двух панелей): `stripGeneration` вместе с per-plane
`uploaded` в `FontResources` — та же пара, что Metal пишет как `ArenaMirror`;
цена лежит не на панелях, а на предположении «один шейпер на окно», о котором
`render_arena.h` говорит подробно. Во втором комментарии пункт про арены назван
тем, чем стал, — пунктом, который список потерял.

`PaneArenaMirror` в `lib/` больше не упоминается (**измерено**: `grep -rn` пуст;
одно историческое упоминание осталось в `tst/test_gpu_parity.py:216`, оно про
прошлое и верно).
