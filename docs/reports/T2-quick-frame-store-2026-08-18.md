# Отчёт T2: файл состояния фрейма quick-окна

- **План:** `docs/plans/2026-08-18-panes-and-window-chrome.md`, секция T2
- **Архитектура:** `docs/architecture/2026-08-18-panes-and-window-chrome.md`, решение A6
- **Ветка:** `feat/window-chrome-upstream`, коммит `8f7f9006`
- **Статус:** готово, все критерии приёмки подтверждены прогонами ниже

## Что сделано

Новый модуль `lib/shitty/quick_frame_store.{h,cpp}` — чистая логика чтения/записи
сохранённой позиции и размера quick-окна, без завязки на платформу, по форме
`quick_hotkey_chord.{h,cpp}`/`quick_geometry.{h,cpp}` (T1's precedent, который
я сам делал в прошлой волне). Плюс `quick_frame_store_ut.cpp` — 11 юнит-тестов.

Ни `build.py`, ни другие файлы не тронуты — оба глоба (`lib/shitty/*.cpp` и
`lib/shitty/*_ut.cpp`) подхватили новые файлы автоматически (проверено:
`grep -n "unit_sources\|lib/shitty/\*" build.py`).

## Сигнатуры модуля (для T3)

```cpp
// lib/shitty/quick_frame_store.h

struct QuickFrame {
    i32 x = 0;
    i32 y = 0;
    u32 width = 0;
    u32 height = 0;
};

// Путь по умолчанию: рядом с Options::configPath, с заменой расширения
// (последняя '.' после последней '/') на "-quick-frame". Пусто на входе
// -> false, out нетронут (Options::configPath пуст только когда нет ни
// HOME, ни XDG_CONFIG_HOME - тогда и главному конфигу негде храниться).
bool defaultQuickFramePath(stl::StringView configPath, stl::StringBuilder& out);

// false + out нетронут: файла нет, не читается, или не хватает хотя бы
// одного из четырёх полей (частичный/битый файл трактуется как
// отсутствующий целиком, без частичного применения).
bool loadQuickFrame(stl::StringView path, QuickFrame& out);

// Атомарная запись: временный файл `path + ".tmp." + getpid()` в том же
// каталоге, затем rename() поверх path. Имя временного файла содержит
// pid - оба процесса quickCompanion не столкнутся друг с другом. false,
// если записать не удалось вовсе (каталога нет, недоступен на запись,
// иная I/O-ошибка) - свой временный файл удаляется перед возвратом.
bool saveQuickFrame(stl::StringView path, const QuickFrame& frame);
```

`QuickFrame` намеренно зеркалит поля `plt::WindowInfo::x/y/width/height` (i32
для x/y — окно может стоять левее/выше начала экрана на мультимониторных
раскладках, u32 для width/height). Модуль **не клэмпит и не валидирует против
живого экрана** — это работа T3 в момент применения (`plt::Window` доступен
только там), здесь только хранение того, что дали.

## Ключевые решения

- **`defaultQuickFramePath` берёт `Options::configPath`, а не `Brand`.**
  Мне разрешено читать только `options.h` и `quick_geometry.h` — не `brand.h`.
  `configPath` уже учитывает `-config`, `XDG_CONFIG_HOME`, `HOME` в правильном
  приоритете (см. `OptionsParser::loadConfigFile()`), так что переизобретать
  этот путь заново значило бы дублировать логику и рисковать разойтись с тем,
  что реально загрузил процесс. Расширение (`.toml` или любое другое) просто
  заменяется на `-quick-frame` в той же директории — совпадает с примером из
  архитектуры (`~/.config/shitty/shitty.toml` → `~/.config/shitty/shitty-quick-frame`).
- **Формат файла — `key=value` построчно** (`x=`, `y=`, `width=`, `height=`),
  не TOML. Полноценный TOML-парсер (`toml.h`) заточен под конфиг с
  предупреждениями и импортами — избыточно для четырёх целых чисел. Простой
  построчный формат человекочитаем (можно открыть и посмотреть/поправить
  руками), устойчив к мусорным строкам (игнорируются, не валят весь файл) и
  не тянет лишней зависимости.
- **Требуются все четыре поля разом.** Файл с одним-двумя полями (обрезанный,
  отредактированный вручную наполовину) трактуется как отсутствующий целиком —
  нет частичного применения кривого состояния.
- **Имя временного файла содержит `getpid()`.** Единственная причина —
  `quickCompanion` всегда даёт два живых процесса на один и тот же бренд-конфиг,
  и оба могут писать в один файл состояния; разные pid → разные временные
  файлы → нет гонки за один и тот же дескриптор, только за финальный
  `rename()`, который на POSIX атомарен сам по себе.
- **Отклонённые альтернативы:** сохранение per-screen конфигураций отклонено
  архитектурой заранее (A6, «открытый вопрос»: один фрейм, клэмп при
  отсутствии экрана — не моя часть); TOML-формат отклонён как избыточный (см.
  выше); `setFrameAutosaveName:`/`NSUserDefaults` отклонены архитектурой
  (подерётся с явной установкой фрейма на каждом показе, прячет состояние в
  неочевидное место) — и в любом случае вне зоны этого модуля (Cocoa-специфично,
  T2 платформы не касается вовсе).

## Критерии приёмки — с доказательством

- **Юнит-тесты: запись/чтение, битый файл, отсутствующий файл, отсутствующий
  каталог, значения за границами экрана.** Все покрыты:
  - `RoundTripWritesAndReadsAllFourFields` — базовый цикл.
  - `OffScreenAndOversizedValuesRoundTripUnchanged` — x=-12000, y=-9000,
    width=999999 — сохраняются и читаются без клэмпа/отбрасывания.
  - `MissingFileIsTreatedAsAbsent`, `MissingDirectoryIsTreatedAsAbsent` —
    `loadQuickFrame` даёт `false`, `out` нетронут (проверено сентинелом `x=7`).
  - `CorruptFileIsTreatedAsAbsent` — бинарный мусор вместо текста → `false`.
  - `PartialFileIsTreatedAsAbsent` — файл только с `x`/`y` без `width`/`height`
    → `false`, никакого частичного `out`.
  - `.build/unit_tests` — все 11 тестов `QuickFrameStore::*` зелёные.
- **Атомарность доказана подменой, не рассуждением.**
  `FailedWriteLeavesThePreviousFrameIntactAndNoTempFileBehind`: сохраняет
  кадр A, делает каталог `chmod 0500` (без права записи), пытается сохранить
  кадр B — `saveQuickFrame` возвращает `false`; после возврата прав каталогу
  проверяется, что (а) `loadQuickFrame` всё ещё даёт кадр A, (б) файла
  `path + ".tmp." + getpid()` не осталось на диске (`access(..., F_OK) != 0`).
  Тест сам вычисляет то же имя временного файла, что и продакшен-код, по той
  же документированной формуле — не заглядывает во внутренности модуля.
- **Чувствительность тестов** — точечно ломал и возвращал (полный лог ниже,
  диффов после возврата нет — `diff /tmp/quick_frame_store.cpp.orig ... `
  дал пустой вывод оба раза):
  1. Убрал проверку `!sawX || !sawY || !sawWidth || !sawHeight` в
     `loadQuickFrame` → покраснели `CorruptFileIsTreatedAsAbsent` и
     `PartialFileIsTreatedAsAbsent` (оба ожидаемо, т.к. частично/полностью
     нечитаемый файл вдруг стал бы "успешно" разбираться нулями). Вернул.
  2. Подменил запись во временный файл на прямую запись в `path` (сломал саму
     идею atomic-write) → покраснели `FailedWriteLeavesThePreviousFrameIntactAndNoTempFileBehind`,
     `OffScreenAndOversizedValuesRoundTripUnchanged`, `RoundTripWritesAndReadsAllFourFields` —
     то есть мутация поймана сразу тремя тестами, не только целевым. Вернул.
- **`./build test -k` — базис по именам не вырос.** Сверил с базисом из
  отчёта T1 (`docs/reports/T1-panes-contract-2026-08-18.md`): тот же набор из
  12 узлов плюс `plt-tests.stamp`, который в этот раз прошёл сам (прогнал
  `.build/ext/plt/plt_unit_tests` напрямую — `OK: 54`, без единого падения;
  `plt-tests.stamp` в T1 падал из-за известной флакующей внешней обвязки
  `run_timed.py` с таймаутом 120с, не из-за самих тестов — ловушка описана в
  плане). Итог: **13 узлов вместо 14**, разница объяснена, ни один узел не мой
  и не новый.

## Стиль

`clang-format` (полный файл, не `-lines=` — файлы новые) — чисто по всем трём.
MIT-шапка на месте во всех трёх. Без `std::` — только `stl::`. `git status --short`
после коммита показывает ровно эти три файла.

## Что осталось за рамками (не моя часть)

- Вызов `defaultQuickFramePath`/`loadQuickFrame`/`saveQuickFrame` из
  `platform_cocoa.mm`/`application.cpp`, подписка на перемещение/ресайз окна,
  применение сохранённого фрейма с приоритетом над `quickGeometry` — весь
  **T3**.
- Клэмп значений против реального экрана при показе — тоже **T3**, этому
  модулю нужен только `plt::Window`/`NSScreen`, которых здесь нет и не должно
  быть.
