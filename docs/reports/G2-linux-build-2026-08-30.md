# G2: сборка под Linux — неопределённая ссылка из `render_vk.cpp`

- **Задача:** вне плана, делегированная — починить сборку форка под Linux, красную с 2026-08-20
- **Дата:** 2026-08-30
- **Дерево:** `scratchpad/g2`, detached на `wave/upstream-merge-w4`
- **Статус:** **исправлено локально; зелёный Linux подтверждает CI, а не этот отчёт**

---

## 1. Что было сломано

`lib/shitty/render_vk.cpp:2282` передавал в `raiseError` сырые литералы:

```cpp
raiseError(u8"vulkan: this backend presents one pane per frame, not ", count, u8" - splits are not supported here yet");
```

Линковка `st` и `pt` падала на двух неопределённых символах:

```
undefined reference to stl::output<stl::ZeroCopyOutput, stl::PassByRef, char8_t[55]>(...)
undefined reference to stl::output<stl::ZeroCopyOutput, stl::PassByRef, char8_t[37]>(...)
```

Происхождение — коммит `8325f312` от 2026-08-20, «F6: the Vulkan backend
says why it refuses a split, instead of going dark».

---

## 2. Гипотеза проверена, а не принята на веру

Гипотеза командира («нет инстанциации `stl::output` для сырых массивов»)
подтверждена тремя независимыми способами.

**По исходникам.** `stl::output` в `ext/libstd/std/ios/outable.h:12-16`
только **объявлен** — определений в заголовке нет:

```cpp
template <typename O, PassByVal T> void output(O& out, T t);
template <typename O, PassByRef T> void output(O& out, const T& t);
```

Все определения — явные специализации в `.cpp` библиотеки, для поимённо
названных типов: `StringView` (`std/str/view.cpp:179`), `U64`/`I64`,
`const char*`, `int`/`long`/`short`/`long long` и их `unsigned`-варианты
через макрос `DEF_OUT` (`std/ios/out_zc.cpp:72-85`), плавающие, `Buffer`,
`Color`, манипуляторы, DNS-типы. Специализации для `char8_t[N]` нет и
быть не может — их бесконечное число.

Путь литерала до этой дыры: `raiseError` (`lib/vterm/fatal.h:31`) сворачивает
пакет через `text << part`; `stl::operator<<` (`std/ios/out_zc.h:48-53`)
вызывает `output<ZeroCopyOutput, T>(out, t)` с `T`, **выведенным из
`const T&`**. Строковый литерал выводится как `char8_t[N]`, а не как
`StringView` — вывод шаблонного параметра не выполняет пользовательских
преобразований, поэтому неявный конструктор `StringView(const u8 (&)[N])`
(`std/str/view.h:19-22`) в этой позиции не участвует. `sizeof` 55 и 37
больше `2 * sizeof(long double)` = 32, поэтому выбирается ветвь `PassByRef` —
ровно та, что в мангле CI.

**Экспериментом без Vulkan.** Дефект воспроизводится изолированным TU
на этой машине, штатным Apple clang, без единого заголовка Vulkan:

```
c++ -std=c++26 -O2 -I. -Iext/libstd -c probe.cpp && nm -u probe.o | c++filt
```

| Вариант вызова | Неопределённые `stl::output` |
|---|---|
| `raiseError(u8"…55…", count, u8"…37…")` | `char8_t [55]`, `char8_t [37]`, `unsigned long` |
| `raiseError(StringView(u8"…55…"), count, StringView(u8"…37…"))` | `stl::StringView`, `unsigned long` |

Длины массивов совпали с CI побайтово. `unsigned long` определён
(`DEF_OUT(long)`) и в списке ошибок CI не значится — это подтверждает, что
проблема именно в массивах, а не в вариадике `raiseError` как таковом.

**На самом файле.** См. §6: `render_vk.cpp` удалось собрать локально.
Объектник до и после правки:

| | неопределённые `stl::output` |
|---|---|
| версия `HEAD` | `char8_t [37]`, `char8_t [55]`, `long long`, `Manip::EndLine`, `StringView`, `unsigned long`, `unsigned long long` |
| после правки | те же **минус оба `char8_t[N]`**, ничего нового |

Оба символа из ошибки CI исчезли, новых не появилось.

## 3. Исправление

`lib/shitty/render_vk.cpp:2282` — литералы обёрнуты в `StringView(...)`,
как во всех прочих вызовах `raiseError` в этом файле (`:363`, `:464`,
`:552`) и в остальном дереве (30 вызовов, все обёрнуты). Текст сообщения
не изменился ни на символ.

`lib/vterm/fatal.h` — **доккомментарий над `raiseError` демонстрировал
именно сломанную форму**:

```cpp
// raiseError(u8"-border: expected unsigned, max. ", limit) - every part
```

Это единственное место в дереве, которое учит писать так, и `8325f312`
почти наверняка списан с него. Комментарий приведён к рабочей форме и
дополнен объяснением, почему бывает именно ошибка компоновки, а не
компиляции. Правка чисто документационная, поведения не меняет; файл
холодный (один коммит в истории — переезд `9a5f67c8`).

## 4. Остальные места того же класса — их нет

Дефект возникает ровно в двух точках входа, через которые сырой литерал
попадает в `stl::output` по выводу шаблонного параметра:

1. `raiseError(...)` — единственная свёртка `<<` в дереве
   (`lib/vterm/fatal.h:33`);
2. `stl::operator<<` для `ZeroCopyOutput` (`std/ios/out_zc.h:48`) и для
   `UnboundBuffer` (`std/ios/unbound.h:17`) — других шаблонных вызовов
   `output<...>` в заголовках нет.

Прогнан многострочный скан 644 файлов (`lib`, `bin`, `tst`, `dev`,
`ext/plt`, `ext/libstd`; `.cpp/.h/.hpp/.cc/.mm/.inc`): комментарии
вырезаются, `raiseError(` разбирается по сбалансированным скобкам,
аргументы верхнего уровня проверяются на голый `u8"…"`; отдельно ищется
`<<` с сырым литералом, в том числе через перевод строки.

- **до правки:** одно попадание — `render_vk.cpp`;
- **после правки:** ноль в обеих категориях.

Сканер проверен негативным контролем: на версии `render_vk.cpp` из `HEAD`
и на заведомо сломанном пробнике он срабатывает.

Ограничение честно: скан покрывает **известные** точки входа. Если кто-то
заведёт новый шаблон, форвардящий в `output`, он под этот скан не попадёт.

## 5. Это ли единственная поломка Linux

Единственная **на этапах компиляции и компоновки** — да, с высокой
уверенностью. Про поведение в рантайме сказать нечего.

**Компоновщик не останавливается на первой ошибке.** И `ld.bfd` в CI,
и `lld` в Release печатают весь список неопределённых символов. Список
состоит ровно из двух наших.

**Две независимые тулчейны прошли почти весь граф:**

| Прогон | Тулчейн | Собрано узлов | Отказы |
|---|---|---|---|
| CI «Build Linux» `33312379600` | Nix, clang 21.1.8, `ld.bfd` | 241 из 243 | только линковка `st` |
| Release `32834146088` | IX, `lld`, граф больше | **471 из 478** | только линковка `pt` |

Release-граф на 478 узлов (против 243 у CI) включает тестовые бинарники;
он тоже компилируется целиком и умирает на тех же двух символах.
`render_vk.cpp` (узел 238/243) и `platform_wayland.cpp` (235/243)
компилируются без единого предупреждения.

**Чего это не доказывает — и это важнее.** «Build Linux» — корневой гейт
**всего** CI: `needs: build` стоит у Tests Alpine, Tests Fedora, Sandboxed
0..4/5, Coverage, Tests ASan, Tests UBSan, Nix Linux **и у `build-darwin`**,
а от `build-darwin` зависят все шесть Darwin-джобов и Nix Darwin. В
прогоне `33312379600` все они — `0s`, то есть не запускались.

Отсюда два вывода для борда:

- **весь рантайм Linux не проверялся ни разу с 2026-08-20** — за этой
  стеной может стоять что угодно, и одна зелёная линковка это не снимет;
- **macOS в CI тоже тёмный ровно столько же**. Все пять прогонов CI на
  форке красные, зелёного не было никогда. Локальные прогоны на этой
  машине — единственное, что вообще проверялось десять дней.

## 6. Можно ли проверять `render_vk.cpp` локально: **да, и это дёшево**

Ответ отличается от ожидаемого, поэтому по пунктам.

**Из коробки — нет.** Vulkan на машине отсутствует полностью: нет
`/usr/local/include/vulkan`, `/opt/homebrew/include/vulkan`,
`~/VulkanSDK`, `pkg-config --exists vulkan` не проходит. Попытка
`-fsyntax-only` упирается ровно в один барьер:

```
lib/shitty/render_vk.cpp:43:10: fatal error: 'vulkan/vulkan.h' file not found
```

**Всё остальное на месте.** `-DHAVE_VULKAN_WAYLAND=1` — обычный `-D`;
`plt/window.h` есть в `ext/plt`; генерируемый `render_spv.h` собирается
локально командой `./build render_spv` — `glslangValidator` и
`spirv-cross` на машине **установлены** (18 узлов, `exit 0`).

**С заголовками — компилируется полностью.** Заголовки Khronos
header-only; после `git clone --depth 1 KhronosGroup/Vulkan-Headers`
в скретчпад (машина не трогалась, в `/usr` ничего не ставилось):

```
c++ -std=c++26 -O2 -DHAVE_VULKAN_WAYLAND=1 \
    -I. -Ilib/shitty -Iext/libstd -Iext -I.build -I<vkh>/include \
    -c lib/shitty/render_vk.cpp -o render_vk.o        # exit 0, без предупреждений
```

Именно так получено сравнение объектников из §2.

**Но `-fsyntax-only` этот дефект не поймал бы.** Он умирает в
компоновщике; синтаксически код безупречен. Ловит его `-c` **плюс**
`nm -u … | c++filt`, то есть проверка неразрешённых символов объектника.
Полная локальная линковка невозможна и с заголовками — нет `libvulkan`.

**Практический вывод для борда.** Самый дешёвый гвард на весь класс
дефектов Vulkan вообще не требует: пробник из §2 (`raiseError` с сырыми
литералами, `fatal.h` + libstd, обе платформо-нейтральны) ловит его
штатным clang за долю секунды. Скан из §4 ловит его же статически, без
компиляции. Оба пригодны как узел сборки; ни то, ни другое я не заводил —
это правка `build.py`, а она мне запрещена.

## 9. Что не сделано и почему

- **`build.py` не тронут**, `render_vk.cpp` в сборку на macOS не заводился —
  прямой запрет в постановке.
- **`raiseError` не защищён от повторения.** Технически лечится шестью
  строками в `fatal.h`: перегрузка-нормализатор, сводящая `const u8 (&)[N]`
  к `StringView`, и `(text << ... << fatalPart(part))`. Не стал: обёртка
  `StringView(...)` — сложившаяся конвенция, ей следуют все 30 вызовов, а
  снятие этого требования — решение об API общего заголовка, а не
  починка сборки. Вынесено сюда как предложение.
- **Узел сборки под гвард из §6 не заведён** — это `build.py`.
- **Rebase/pull не делались**, ветка не переключалась, коммит в detached HEAD.

## 10. На что смотреть ревьюеру

- Правка `render_vk.cpp` — одна строка, текст сообщения не изменился.
  Ветка `count > 1` не покрыта тестами ни до, ни после; проверить её
  можно только руками на Linux при расщеплении панели.

  они покажут, к этой правке отношения не имеет и в её зелёность не

## Обнаружено

1. **`Build Linux` — корневой гейт всего CI, включая macOS.** `build-darwin`
   стоит на `needs: build`, а на нём — все шесть Darwin-джобов и Nix Darwin.
   Одна неопределённая ссылка в Linux-only файле гасила проверку обеих
   платформ целиком. Заметить это по строке «Build Linux красный» нельзя —
   надо смотреть на `0s` у остальных джобов.

2. **`render_vk.cpp` компилируется на этой машине** — нужен только
   `git clone Vulkan-Headers` в скретчпад плюс `-DHAVE_VULKAN_WAYLAND=1`
   и `-I.build`. `glslangValidator` и `spirv-cross` уже установлены,
   `render_spv.h` генерируется штатным `./build render_spv`. Ставить
   что-либо в систему не потребовалось.

3. **`-fsyntax-only` бесполезен против этого класса.** Дефект живёт в
   компоновщике. Дешёвая замена полной сборке — `-c` плюс
   `nm -u … | c++filt` на объектнике.

4. **Дефект воспроизводится вообще без Vulkan.** `raiseError` живёт в
   `lib/vterm/fatal.h`, `stl::output` — в libstd; обе платформо-нейтральны.
   Пятистрочный TU ловит его на macOS за долю секунды.

5. **Доккомментарий в `fatal.h` учил сломанной форме** — единственное
   место в дереве, где `raiseError` показан с сырым литералом. Полезное
   правило для следующего: если правка «как в примере из заголовка» ломает
   сборку, проверять сам пример.

6. **`tr` на этой машине — алиас `task add project:rt`, и я на нём
   обжёгся.** `... | tr -d '{}' | ...` создало задачу `4` («`-d {}`»,
   project `rt`, UUID `6059b1c5-62f8-41dd-b073-9c82b23e4759`) в
   taskwarrior пользователя. Удалить не смог — `task 4 delete` заблокирован
   классификатором разрешений. Мусор нужно убрать вручную: `task 4 delete`.
   Предупреждение в постановке было, я его прочитал и всё равно набрал
   `tr` в длинном пайпе — значит, помнить о нём недостаточно; безопаснее
   не писать `tr` вообще, `sed 's/[{}]//g'` делает ровно то же.
