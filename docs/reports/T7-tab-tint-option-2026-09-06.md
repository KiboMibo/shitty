# T7. Прозрачность пилюли вкладки выносится в конфиг

- **Дата:** 2026-09-06
- **Ветка:** `feat/T7-tab-tint-option`, от `master` `c53cc547`
- **Коммит правки:** `cb40653c`
- **Повод:** пользователю нравится нынешний вид пилюли и он хочет крутить её
  прозрачность из конфига; `T6` зашила её константой `sidebarPillTint = 0.65`
- **Машина:** macOS 26.5.2, arm64, Apple clang 21

Пометки: **[и]** измерено — запущено и увидено; **[п]** прочитано — написано в
нашем коде, со ссылкой на строку; **[в]** выведено — рассуждение.

## Ответ одной строкой

**`sidebarTabTint`**, целое `0..100`, умолчание `65`; в конфиге —
`sidebarTabTint = 65`, на командной строке — `-sidebarTabTint 65`.

Шкала и смысл — как у `backgroundOpacity`: `100` — цвет `bg` темы плашмя, `0` —
чистое стекло `Clear` с рабочим столом насквозь, то есть ровно то, что
отгружала `T5`. Действует только при `-backgroundBlur glass`: под `blur` и `off`
пилюли не существует, активная строка там красится в `drawRect:`.

### Правка в самой пилюле

Дифф против `master`, по существу — три строки:

```
-    static const CGFloat sidebarPillTint = 0.65;
...
-                    sheet.tintColor = nsColorFromTerminalColor(composer.vtConfig.config->bg, sidebarPillTint);
+                sheet.tintColor = nsColorFromTerminalColor(composer.vtConfig.config->bg, (CGFloat)(composer.opts->sidebarTabTint) / 100.0);
```

Выражение то же самое, тот же `nsColorFromTerminalColor`, тот же `opts->bg`;
подменён **только второй аргумент**, и `65 / 100.0 == 0.65` — то самое число,
которое `T6` выбрала измерением **[п]**.

Два сопутствующих изменения, оба вынужденные:

1. **Присваивание переехало из ветки «создать» в общий хвост.** Было внутри
   `if (pill == nil)`, то есть выполнялось один раз за жизнь пилюли; стало после
   `if/else`, то есть на каждом проходе `applyPill()`. Это и есть половина,
   которую видит перезагрузка (критерий 4).
2. **Заведена локальная `NSGlassEffectView* sheet`.** Поле `pill` объявлено как
   `NSView*` (`:146`), чтобы файл собирался и против SDK без стекла, а
   `tintColor` — свойство стеклянного класса. Первая сборка на этом и упала:
   `error: property 'tintColor' not found on object of type 'NSView *'` **[и]**.
   В ветке «создать» `sheet` — новый объект, в ветке «уже есть» — приведённый
   `pill`.

### 1. Значение доходит до тинта — **выполнен, без пикселей**

Постановка изменена командиром по ходу задачи: снимков не делать (раздел
«Почему в отчёте нет ни одного снимка»). Критерий закрыт двумя половинами.

**Половина первая, чтением [п].** Дифф выше: выражение, вычисляющее цвет, не
тронуто — подменён один аргумент. Значит вопрос «правильный ли это цвет» уже
отвечен `T6` измерением для `0.65`, и остаётся только вопрос «доходит ли туда
число из конфига».

**Половина вторая, измерением [и].** Число, доехавшее до `Options`, печатает
дамп режима теста — то же поле `composer.opts->sidebarTabTint`, которое читает
`:993`:

```
-sidebarTabTint   0  ->  sidebar_tab_tint=0
-sidebarTabTint  65  ->  sidebar_tab_tint=65
-sidebarTabTint 100  ->  sidebar_tab_tint=100
-sidebarTabTint  42  ->  sidebar_tab_tint=42
(без опции)          ->  sidebar_tab_tint=65
конфиг = 65          ->  sidebar_tab_tint=65
```

Последняя строка — не то же самое, что первые: она идёт из файла через
`XDG_CONFIG_HOME`, а не с командной строки, то есть проверен и путь TOML.

**Честно о том, чего эти две половины не дают [в].** Между полем `Options` и
пикселем на экране стоит одна строка кода и весь Cocoa. Что `NSGlassEffectView`
с `tintColor` альфы `1.00` выглядит как непрозрачный `bg`, а с `0.00` — как
нетонированное стекло, **этой задачей не измерено**. `T6` измерила три точки
этой кривой (`0.00` → 3.48:1 и 2.66:1, `0.35` → 4.82:1, `0.65` → 6.38:1 и
5.72:1, `0.80` → 7.35:1 и 6.92:1) и все они монотонны и осмысленны, так что
поведение на концах — **вывод, а не измерение**.

### 2. Границы и мусор — **выполнен [и]**

```
$ st -sidebarTabTint 101      rc=255
Error: -sidebarTabTint: expected 0..100!
Try -help for usage options.

$ st -sidebarTabTint abc      rc=255
Error: -sidebarTabTint: expected 0..100!
Try -help for usage options.

$ st -sidebarTabTint -1       rc=255
Error: -sidebarTabTint: expected 0..100!
```

Диапазон назван в самой строке. `-1` отвергается тем же сообщением; какая из
двух причин сработала — разбор или нижняя граница, — снаружи неразличимо, и
здесь это не важно: сообщение одно и называет диапазон.

Две формы без значения — та подсказка, которую `T1` сделала общей:

```
$ st -sidebarTabTint          rc=1
Error: -sidebarTabTint: missing value; -sidebarTabTint takes a value, as in -sidebarTabTint 65

$ st +sidebarTabTint          rc=1
Error: +sidebarTabTint: '+' is invalid here; -sidebarTabTint takes a value, as in -sidebarTabTint 65
```

Хвост `as in -sidebarTabTint 65` взят из `hardDefault`, и для числовой опции это
правильно: `valueNames` заводят там, где умолчание — инертный режим и отвечает
«как это включить?» словом «выключено» (`options.cpp:64`-`:71` **[п]**). У
`65` такой беды нет.

Справка (`-help`) печатает строку с хвостом `(default: 65)` **[и]**.

### 3. Без опции — ничего не изменилось — **выполнен, без пикселей**

**Чтением [п].** Единственное место, где новое значение вообще участвует в
рисовании, — `ui_sidebar_tabs.mm:993`. Умолчание поля — `65` (`options.h:127`),
`hardDefault` таблицы — `"65"` (`options.cpp:122`), оба конфига несут `65`.
`65 / 100.0` в `CGFloat` — ровно `0.65`, то есть **тот самый литерал**, который
стоял в удалённой константе; выражение вокруг него посимвольно то же.

Это довод о **точном равенстве**, а не о близости: `0.65` не представимо в
двоичной плавающей точке точно, но `65 / 100.0` и литерал `0.65` дают
**один и тот же** `double` — оба суть корректно округлённое до ближайшего
представление одного вещественного числа, и `CGFloat` на arm64 есть `double`.

**Измерением [и].** `blur` и `off` не тронуты вовсе: ни одна строка вне
`applyPill()` не изменилась, а `applyPill()` целиком стоит под
`windowBackdropIsGlass()` (`:955`) и при прочих подложках уходит в `dropPill()`.

`unit_tests` и питоновский набор — поимённо совпадают с `master` (критерии 9 и
10); ни один тест не покраснел и не позеленел.

**Чего здесь нет.** Попиксельного `max=0` против `master` в этом отчёте нет, и
я не выдаю за него довод о равенстве литералов. Первую партию таких снимков
пришлось забраковать, вторую удалил командир (см. ниже), после чего съёмка была
отменена. Это **единственный критерий задачи, потерявший в силе
доказательства**, и об этом сказано прямо.

### 4. Перезагрузка — **выполнен, путь назван построчно**

**Путь есть, и он полный [п].** Восемь звеньев, все в дереве:

| # | Где | Что |
|---|---|---|
| 1 | `configuration.cpp:114`, `:117` | `SIGUSR1` → `reloadSignalHandler` |
| 2 | `configuration.cpp:33`-`:35` | обработчик дёргает `EventFD` |
| 3 | `configuration.cpp:162` | `ConfigImpl::reload()` строит **новый** `Options` из файла и argv |
| 4 | `configuration.cpp:148` | `publish()` → `composer.setOptions(next)` (`composer.cpp:288`) |
| 5 | `configuration.cpp:150` | обход `composer.configChangedListeners` |
| 6 | `ui_sidebar_tabs.mm:710` | сайдбар в этом списке (`configChanged_`) |
| 7 | `ui_sidebar_tabs.mm:186`, `:1028` | `CallConfigChanged::onListen` → `configChanged()` → `applyReserve(); project()` |
| 8 | `ui_sidebar_tabs.mm:809`, `:904`, `:942`, `:993` | `project()` → `dispatch_async` главной очереди → `apply()` → `applyPill()` → `sheet.tintColor = …` |

Звено 8 — то, ради чего присваивание переехало из ветки `pill == nil` в общий
хвост. **До этой правки путь обрывался на седьмом звене:** `applyPill()` на
существующей пилюле переставлял только `frame`, и тинт остался бы тем, с
которым окно родилось. То есть «перезагрузка меняет прозрачность» — не
свойство, доставшееся даром, а половина правки.

**Измерением [и].** Живой процесс, конфиг переписан под ним, `SIGUSR1`, без
перезапуска, дважды подряд:

```
конфиг = 65             ->  sidebar_tab_tint=65
конфиг -> 12, SIGUSR1   ->  sidebar_tab_tint=12
конфиг -> 97, SIGUSR1   ->  sidebar_tab_tint=97
```

Это доказывает звенья 1–4 целиком: значение доехало до `Options` того же
процесса. Звенья 5–8 доказаны чтением; их измерение — это и есть снимок
«до/после», которого в отчёте нет.

## Почему в отчёте нет ни одного снимка

Прямо: **оснастка съёмки на этой машине негодна, и две партии подряд захватили
рабочий стол пользователя.** Первую я забраковала сама, увидев в кадре чужое
окно; вторую удалил командир, не открывая. После этого съёмка была отменена
постановочно, и критерии 1, 3 и 4 закрыты чтением кода и дампом.

Что это значит для доверия к отчёту, без смягчений:

- критерий **1** потерял визуальную часть на концах шкалы (`0` и `100`) — она
  выведена из измерений `T6`, а не измерена;
- критерий **3** потерял попиксельное `max=0` против `master` — вместо него
  довод о точном равенстве литералов, `unit_tests` и набор;
- критерий **4** потерял снимок «до/после» — вместо него построчный путь и
  двойное измерение значения в живом процессе после `SIGUSR1`.

Остальные восемь критериев снимков не требовали и не потеряли ничего.

## Обнаружено

### 1. Подложка на уровне `-1` больше не композитится в стекло; на уровне `0` — композитится

Самое дорогое из найденного и, вероятно, причина части сегодняшних неудач всей
сессии. Оснастка `T4`–`T6` поднимает синтетический фон окном на уровне `-1`
(`t6back -1 bands`) — ниже обычных окон, но выше виджетов Центра уведомлений — и
все числа `T5` и `T6` про «что видно сквозь стекло» стоят на том, что окно
терминала композитит **этот** фон.

Измерено сегодня **[и]**: при живой подложке на `-1`, при полностью чистом
экранном стеке (окно на уровне 0, прямо под ним `t6back` на `-1`, между ними
ничего, обои — на `-2147483624`), сквозь стекло видны **обои пользователя**, а
не подложка. Проверка, которая это ловит и которой ни у кого не было: подложка
несёт вертикальные волоски шагом 8 pt, то есть период 16 px при 2x; в кадре
такой периодичности нет вовсе, а два разных поля подложки (`bands` и `bright`,
далеко разнесённые по яркости) дают **побайтово одинаковый** кадр.

Тот же прогон с `t6back 0 …` — подложка композитится: поля различаются
(`(34,53,94)` против `(73,75,73)` в одной и той же области), строка кадра
плоская там, где под стеклом сплошная полоса, и красный канал сходится с
арифметикой `0.4·bg + 0.6·полоса` до единицы.

**Следствие для будущих задач:** синтетический фон ставить на уровень `0`, а не
`-1`. Он тогда — обычное окно и закрывает собой всё прочее на space, что
изоляцию только усиливает. Уровень `-1` даёт «подложка в стеке есть, а в стекле
её нет» — отказ, который проверка «что между окном и подложкой» пропускает
целиком, потому что между ними действительно ничего.

**Чего я не знаю:** когда именно это перестало работать. `T6` мерила на `-1` и
получала осмысленные числа; сегодня первые прогоны на `-1` тоже показывали
полосы, а поздние — уже нет. Разницы в оснастке между теми и другими я не нашла.

### 2. `pkill -f <полный путь>` не убивает процесс, запущенный по относительному пути

Оснастка снимает предыдущую подложку через `pkill -f "$HERE/t6back"`. Подложка,
запущенная руками как `./t6back -1 bright` из того же каталога, под этот шаблон
**не подходит** — в её командной строке нет полного пути. Измерено: в экранном
стеке одного из кадров оказалось **три** живых `t6back` разом.

Лечится `pkill -x t6back` — по имени процесса. Но важнее второе: **проверка «что
между окном и подложкой» этого не видит**, потому что самая свежая подложка
действительно лежит прямо под окном, а лишние — под ней. В оснастку добавлен
счёт: если подложек на экране не ровно одна, кадр отвергается.

### 3. Липкое окно ломает предикат «пустой space»

`T4`–`T6` ищут space так: `[s for s in spaces if not s['windows']]`. На этой
машине браузер держит окно с `is-sticky`, и `yabai` перечисляет его **на каждом
space** — пустых не остаётся ни одного, предикат возвращает пусто, оснастка
проваливается сквозь `if` и снимает кадр там, где стояла. Первый же снимок вышел
с чужой страницей во весь прямоугольник.

Правильный предикат — вычесть липкие окна из списка каждого space. Плюс поднять
своё окно (`yabai -m window --focus`) уже после переезда: липкое окно на том же
уровне иначе остаётся сверху.

### 4. Панель на уровне 21 не перебивается ничем, и лечится геометрией

Один окклюдер не уходит ни от какого поднятия: плавающая панель приложения на
уровне окна 21 в правом верхнем углу дисплея. Обойдено тем, что окно выводится
из-под неё — `--toggle float` и `--resize abs:1200:1073` при том же начале
координат, что сохраняет все прямоугольники, которыми `T6` мерила (все они в
левых 440 px, а полоса шва адресуется по строкам).

Отдельно: **Центр уведомлений поднимает окно на весь экран на уровне 21** и
глушит съёмку целиком на несколько десятков секунд. Это единственный окклюдер,
который надо **ждать**, а не перебивать.

### 5. `cmd+t` через `osascript` не открывает вкладку — как и `cmd+1..9`

`CLAUDE.md` знает про `cmd+1..9`; тот же отказ у `cmd+t`. Два нажатия открыли
**ноль** вкладок, и первая пара кадров разошлась по строкам 0 и 1 вместо строки
2 — то есть выглядела осмысленно и была неверна.

Детерминированная замена: кликать по строке «`+`» самого списка. При `k`
вкладках плюс стоит строкой `k`, и открытая им вкладка становится активной, так
что два клика дают ровно три вкладки с активной строкой 2.

### 6. Прямоугольник окна от сервера тоже бывает мусорным, и это надо проверять

`CLAUDE.md` уже велит перечитывать прямоугольник перед каждым кликом и не брать
его у `yabai`. Этого мало: перечитанный у **сервера** прямоугольник один раз
вернул `x = 2753` для окна, которое стоит на `x = 5`, и клик ушёл на `2863` —
за правый край дисплея шириной 1728 pt. Ни звука: кадры валидны, коды нулевые,
вкладка не открылась.

Точка вне дисплея должна отвергаться, а прямоугольник — перечитываться.

### 7. Список окклюдеров печатался, но ни на что не влиял

Во всей оснастке `T4`–`T6` окклюдеры **печатаются рядом с кадром**, и решение о
годности кадра принимает человек, читая лог. Первый снимок этой задачи вышел с
чужим окном, при том что список окклюдеров это чужое окно **назвал** — просто
никто не остановил съёмку.

Отказ должен быть механическим: кадр с непустым списком (кроме курсора и рамки)
не снимается вовсе.

### 8. У новой опции есть наблюдатель в конфигах и нет ни одного в рисовании

Разбор, границы и дамп покрыты: мутация в `getSidebarTabTint()` покраснит
поимённо проверяемые строки ошибок; мутация «убрать ключ из одного конфига»
покраснит `ExampleConfigParityTest` (показано выше живьём).

А вот **`ui_sidebar_tabs.mm:993` не наблюдает ничто** **[в]**. Мутации
«поделить на 255 вместо 100», «взять `fg` вместо `bg`», «вернуть константу
`0.65`» не покраснят ни один тест ни в `unit_tests`, ни в наборе: это код Cocoa,
и единственный его наблюдатель — глаз или снимок. То же верно и про строку
дампа `sidebar_tab_tint=`: её не читает ни один тест, `harness.options()` просто
кладёт поле в словарь.

Это не регрессия задачи — так же не наблюдаема была и константа `T6`, — но
теперь у места есть входное значение из конфига, и цена незамеченной мутации
выше.

### 9. Сокращения опций: новое имя ничего не сломало, и это проверено

Опции разрешаются по **однозначному префиксу** (`optionTrie->resolve`,
`options.cpp:253`), поэтому новое имя может сделать неоднозначным сокращение,
работавшее вчера. Проверено против бинарника `master` **[и]**:

| Сокращение | `master` | T7 |
|---|---|---|
| `-sidebar` | `ambiguous option` | `ambiguous option` |
| `-sidebarT` | `unknown option` | принимается (`sidebarTabTint`) |
| `-sidebarW` | принимается | принимается |
| `-sidebarC` | принимается | принимается |

Ни одно работавшее сокращение не потеряно: до `T7` ни одна опция не начиналась
на `sidebarT`.

## Что осталось следующим задачам

- **Визуальная проверка концов шкалы.** `0` и `100` не сняты. Когда оснастка
  снимков будет починена (пункты 1–7 выше), это один прогон.
- **Разделитель `sidebarGlassSeam = 0.70`** остался константой. Пользователь про
  него не просил, и задача его не трогала.
- **Наведение на активную строку** и **неактивное окно** — наследуются от `T6`
  нетронутыми.
- **Тема с заданным `sidebarColor`.** Тинт берёт `opts->bg`, а не цвет панели;
  на такой теме не измерялось ни `T6`, ни здесь.
