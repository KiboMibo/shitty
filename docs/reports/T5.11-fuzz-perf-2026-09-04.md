# T5.11. `main_fuzz` и `core_perf` — вызывающие на нашу сигнатуру

**Дата:** 2026-09-04 · **Задача:** `T5.11`, волна 6 плана `docs/plans/2026-08-29-upstream-merge.md` · **Ветка:** `feat/T5.11-fuzz-perf` от `de35963a` · **Коммиты:** `f9bcf953`, `c8d5e030` · **Вердикт:** `ГОТОВО, с одним критерием, невыполнимым по причине вне задачи`

Утверждение `T5.9` — «одна строка на файл» — **подтвердилось буквально**. Оба вызывающих держали `Composer` в руках строкой выше, замена свелась к передаче его самого вместо двух вынутых из него полей.

Сверх задачи вскрылось одно: **`main_fuzz` не линкуется и не линковался никогда**, независимо от этой правки. Ошибка компиляции его просто заслоняла. Критерий 1 из брифа («ноль сломанных») поэтому не достигнут — и достигнут быть не может, о чём ниже подробно.

---

## 1. Что было сломано

Обе программы звали апстримную четырёхаргументную форму, у нас форма трёхаргументная:

```
$ git checkout de35963a && ./build -k st pt … core_perf                        ; EXIT=1
bin/core_perf/main.cpp:84:103: error: too many arguments to function call, expected at most 3, have 4
bin/main_fuzz/main.cpp:121:24:  error: too many arguments to function call, expected at most 3, have 4; did you mean 'Options::create'?
build: 4 node(s) failed, 2 requested target(s) broken
```

Сломано с мерж-шага `M6c`. Возврат к апстримной сигнатуре исключён: наш `Vterm::create` несёт 11 параметров против апстримных 9 ради `A1`/`A8`, а откат сломал бы точку входа `st` (`lib/shitty/main.cpp:104`). Основания — `docs/reports/T5.9-vt-headless-2026-09-04.md`, §2.

## 2. Что изменено

Три строки в трёх файлах, два коммита.

**`f9bcf953`** — по одной строке на вызывающего, ровно как предсказал `T5.9`:

```cpp
// bin/main_fuzz/main.cpp:121
-  headless = VtermHeadless::create(*composer->pool, *composer->vtConfig.config, &capture, pty);
+  headless = VtermHeadless::create(*composer, &capture, pty);

// bin/core_perf/main.cpp:84
-  VtermHeadless* const host = VtermHeadless::create(*pool, *composer->vtConfig.config, nullptr, nullptr);
+  VtermHeadless* const host = VtermHeadless::create(*composer, nullptr);
```

Оба `Composer` создаются строкой выше вызова (`main_fuzz:118`, `core_perf:78`), так что ни новых полей, ни новых включений не понадобилось. Четвёртый аргумент `core_perf` был `nullptr` в позиции `ptyCapture`, у которого в нашей сигнатуре есть значение по умолчанию, — он просто ушёл.

**`c8d5e030`** — одна строка в `build.py`, ответ на вопрос брифа; см. §3.

## 3. Ответ: стоит ли добавить их в цель сборки

**Да — `core_perf` и `parser_perf`, одной строкой. `main_fuzz` — нет, и это не выбор.**

Сделано, потому что уложилось в бюджет брифа (`build.py:4346`):

```python
# The perf programs link no test of their own, so nothing else builds them:
# they went uncompilable for a whole merge without CI noticing (T5.11).
add_test(parser_perf, core_perf, instrumented=False)
```

Проверено исполнением, а не рассуждением. Кеш-хиты раннер в лог не печатает, поэтому обе программы были сделаны некеш-хитами (проба кодом — строка `static const int t511CacheBuster`), после чего цель `test` их построила:

```
$ ./build test -k -j 16                                                        ; EXIT=1
[CC] {1/50} $(B)/obj/core_perf/bin/core_perf/main.cpp.o
[CC] {2/50} $(B)/obj/parser_perf/bin/parser_perf/main.cpp.o
[LD] {3/50} $(B)/core_perf
[LD] {18/50} $(B)/parser_perf
```

Пробы откачены, в коммит не вошли.

**`main_fuzz` в цель ставить нельзя.** Он определяет `LLVMFuzzerTestOneInput` и не определяет `main` — `main` даёт рантайм libFuzzer, которого нет ни в Apple-тулчейне, ни в Homebrew-llvm на этой машине:

```
$ /usr/bin/c++ -fsanitize=fuzzer -o /tmp/fz /tmp/fz.cpp
ld: library '…/lib/clang/21/lib/darwin/libclang_rt.fuzzer_osx.a' not found
```

Штатный способ его собрать — `dev/fuzz.sh`, который поднимает nix-shell с `llvmPackages.stdenv` и передаёт `LDFLAGS="-fsanitize=address,fuzzer"`. Поставь `main_fuzz` в цель — цель покраснеет везде, где этого shell нет. Если сигнал по нему всё же нужен, ловить надо **компиляцию, а не линковку**: завести рядом `library(name="main_fuzz_obj", srcs=[fuzz_source], …)` и добавить в `test` уже её. Это ~6 строк, за бюджет брифа, поэтому только называю. Такой узел поймал бы ровно ту поломку, которая случилась: она была на компиляции.

### 4.1. Питоновский набор: почему одного прогона достаточно

Набор гоняет `st_test`, `pt_test` и `toml_dump`. Ни один из них не зависит от `bin/core_perf` или `bin/main_fuzz`, поэтому два прогона сравнивали бы одно и то же с самим собой. Вместо этого сравнены **сами артефакты**, собранные на `de35963a` и на `f9bcf953`:

```
$ diff base-hashes.txt branch-hashes.txt                                       ; EXIT=0
(пусто: st_test, pt_test, toml_dump, unit_tests, pty_test_helper, st, pt — семь из семи
 указывают на один и тот же объект CAS, то есть побайтово равны)
```

Красные — по модулям, совпадают с эталоном `T5.9` посимвольно; все средовые (`fontconfig`/`freetype`/`harfbuzz` выключены `optional_pkg()` на macOS):

```

2 test_font_resolver        2 test_contour_input_generator
1 test_italic_overhang      1 test_ghostty_key_encoding_tail   1 test_color_font_render
```

## 5. Критерий 1 не выполним, и вот почему

Бриф ждал «после — ноль сломанных», исходя из того, что обе цели ломает только сигнатура. Это верно для `core_perf` и **неверно для `main_fuzz`**: ошибка компиляции заслоняла вторую, независимую поломку.

```
$ ./build -k st pt … core_perf                                                 ; EXIT=1
FAIL $(B)/main_fuzz: … Undefined symbols for architecture arm64:
  "_main", referenced from: <initial-undefines>
build: 1 node(s) failed, 1 requested target(s) broken
```

Это **не регрессия и не следствие правки**. Состояние зафиксировано трижды до этой волны:
`docs/plans/state/panes-status.md:994` («компилируется, но не линкуется — нет libFuzzer в тулчейне, **проверено в обе стороны**»), `docs/plans/reviews/panes-R3-test.md:315`, `docs/plans/reviews/panes-R5-qa.md:364`. `main_fuzz` не линковался ни разу с тех пор, как файл несёт только `LLVMFuzzerTestOneInput`: `git log -S'int main('` по нему пуст, а `-fsanitize=fuzzer` в `build.py` нет и не было.

Точный итог правки, в узлах: **4 упавших узла / 2 сломанных цели → 1 / 1**, ошибок компиляции **2 → 0**.

### 5.1. Что `main_fuzz` тем не менее запускается — доказано

Раз линковку блокирует только отсутствие `main`, он был выдан извне: 25-строчный standalone-драйвер (по мотивам `StandaloneFuzzTargetMain.c` из LLVM) скомпилирован **вне репозитория**, в scratchpad, и передан сборке через штатный `LDFLAGS` — тем же каналом, которым пользуется `dev/fuzz.sh`. Репозиторий не тронут.

```
$ LDFLAGS="$D/fuzz_driver.o" ./build main_fuzz                                 ; EXIT=0
[LD] {1/1} $(B)/main_fuzz
$ python3 dev/fuzz_seeds.py $D/seeds 300 && ./.build/main_fuzz $D/seeds/*       ; EXIT=0
Done: 300 file(s).
```

300 направленных seed'ов приняты и исполнены. **Собранная, но ничего не делающая программа — ровно та ловушка, о которой предупреждал бриф**, поэтому проверено и то, что тело действительно работает. Проба кодом — `check(false, …)` в `comparePty`, ядре дифференциального сравнения:

```
$ ./.build/main_fuzz $D/seeds/seed-00000                                       ; EXIT=134
fuzz invariant violated: T511 probe: comparePty reached (0, 0) seq=1
```

`EXIT=134` — это `SIGABRT` из `invariantViolation()`. Проба откачена; чистый бинарник те же 300 seed'ов проходит с `EXIT=0`.

`core_perf` печатает числа, и `save_lines` действительно меняет путь исполнения:

```
$ ./.build/core_perf …/vt.txt 3 1000     → 133925 bytes in 532 us, 240 MiB/s, save_lines=1000  ; EXIT=0
$ ./.build/core_perf …/vt.txt 2          → 133925 bytes in 560 us, 228 MiB/s, save_lines=0     ; EXIT=0
$ ./.build/core_perf                     → usage: core_perf <corpus-path> [runs] [save-lines]  ; EXIT=2
```

## 6. Четыре гварда, четыре пробы кодом

Гварды запускались **напрямую**, минуя `./build` — программы извлечены из `build.py` разбором `ast` (импортировать `build.py` нельзя, он ждёт синтетический модуль от раннера). Скрипт — `scratchpad/rung.py`. Это закрывает ловушку «штамп из CAS».

Каждая проба — строка кода. Проверка «проба зеленит все четыре сразу» пройдена наоборот: каждая краснит **ровно один** гвард и оставляет три зелёными, чего комментарий дать не может — `blanked()` вычищает тела комментариев.

| Гвард | Проба | Результат |
|---|---|---|
| `border_pixels` | `(void)composer->borderPixels();` в `bin/core_perf/main.cpp` | `exit=1`, `bin/core_perf/main.cpp:87`; остальные три `exit=0` |
| `mouse_geometry` | `(void)mouseGeometry(*composer);` в `bin/main_fuzz/main.cpp` | `exit=1`, `bin/main_fuzz/main.cpp:123`; остальные три `exit=0` |
| `darwin_call` | `(void)createMetalRenderer(*composer, *pool, …);` в `bin/core_perf/main.cpp` | `exit=1`, `bin/core_perf/main.cpp:87 createMetalRenderer`; остальные три `exit=0` |
| `pane_grid` | `(void)composer.geometry.columns;` в `lib/shitty/render_reference.cpp` | `exit=1`, `lib/shitty/render_reference.cpp:122`; остальные три `exit=0` |

`pane_grid` пришлось пробовать чужим файлом: он фильтрует `path.name.startswith("render")` (`build.py:1600`), то есть моих файлов не видит вовсе. Это подтверждает `О4` из `T5.9`.

Все пробы откачены, финальный прогон на дереве коммита `c8d5e030` — четыре `exit=0`.

## Обнаружено

**О1. `main_fuzz` не линкуется, и критерий «ноль сломанных» из плана недостижим на любом тулчейне без libFuzzer.** Формулировку критерия `T5.11` в плане (`docs/plans/2026-08-29-upstream-merge.md:372`) стоит поправить: «ноль **ошибок компиляции**; единственный допустимый упавший узел — линковка `main_fuzz`». Иначе следующий исполнитель потратит сессию, упираясь в то же самое, — как уже потратили трое до него (`panes-R3-test`, `panes-R5-qa`, `panes-status`), каждый раз записывая находку в свой отчёт и каждый раз заново.

**О2. Инвариантный набор фаззера не исполняется на направленных seed'ах.** `validateRig()` — весь блок проверок целостности рига — вызывается **единственный раз**, в `bin/main_fuzz/main.cpp:652`, и только для «диких» терминалов. Проба `check(false, …)` в `validateRig` на 300 seed'ах из `dev/fuzz_seeds.py` **не сработала ни разу**, тогда как та же проба в `comparePty` падает на первом же seed'е. То есть генератор seed'ов не создаёт wild-терминалов, и направленная часть кампании проверяет только дифференциальное равенство пары, но не инварианты. Это тихая дыра в покрытии: `dev/fuzz_seeds.py` стоит научить выдавать опкод создания wild-инстанса.

**О3. Питоновский набор и `unit_tests` не могли отличаться, и это доказуемо дешевле, чем прогоном.** Семь артефактов (`st_test`, `pt_test`, `toml_dump`, `unit_tests`, `pty_test_helper`, `st`, `pt`) на `de35963a` и на ветке указывают на один объект CAS. Для правок в `bin/**`, не входящих ни в одну библиотеку, сравнение хешей CAS — более сильное свидетельство, чем два прогона по 130 секунд, и стоит секунду. Стоит внести в `CLAUDE.md` как приём.

**О4. Ловушка №2 из брифа сработала дважды, и второй раз — тихо и дорого.** После `./build -k` симлинков нет вовсе, и это дало **6708 ложных ошибок** в питоновском наборе (`Ran 6027` вместо `6399`) — потому что `SHITTY_TEST_BINARY` указывал на несуществующий `.build/st_test`, а `harness.py:16` берёт путь без проверки. Отказ выглядел как катастрофа в коде, а был отсутствием файла. `tst/harness.py` стоило бы заставить падать внятно, если бинарник по пути не существует.

**О5. `./build --list` игнорирует аргумент цели.** `--list test`, `--list st` и `--list` дают побайтово один вывод (3104 имени — все узлы графа). Проверить состав цели им нельзя, хотя выглядит он ровно как инструмент для этого.

**О6. Знаменатель в `{N/M}` — это оставшиеся узлы, а не размер графа.** Тот же `./build test` на соседних прогонах дал `3056`, `3003`, `3004`, `3000`. Сравнивать составы целей по этому числу нельзя — я попробовал, и оно едва не дало неверный ответ на вопрос §3.

**О7. Цель `test` красная сама по себе — на `vterm_boundary`.** `check_includes.py` даёт 7 нарушений в 3 файлах (`mouse_frontend.h`, `vt_headless.cpp`, `vterm.cpp`) — известное состояние волны, закрывается `T5.2`/`T5.4`/`T5.8`. Пока оно держится, `./build test` без `-k` останавливается на нём **раньше**, чем доходит до чего-либо ещё, — то есть добавленный в §3 сигнал начнёт работать только после того, как граница позеленеет. Само добавление верное, но пользы от него до `T5.2` не будет.
